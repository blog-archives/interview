

## 1. 基础核心概念（先建立层级认知）

MongoDB 存储层级：**数据库 → 集合 → 文档 → 字段**

**数据库**：和 MySQL 库概念一致，用于业务数据隔离。

**集合 Collection**：等价 MySQL 的表，一个集合存放同一类业务数据；**无固定 Schema**，不需要提前定义字段结构，不同文档字段可以不一样。分片、索引均作用于集合维度。

**文档 Document**：等价 MySQL 的一行数据，BSON 格式，支持嵌套对象、数组，是最小数据存储单元。

**字段 Field**：等价 MySQL 的列。

## 2. 基础定位与选型

**分类**：文档型 NoSQL 数据库。

**核心痛点**：解决半结构化数据存储、Schema 频繁变更问题；提供数据库原生分片能力，规避 MySQL 手动分库分表的高开发成本，支持海量数据水平扩容。

**适用场景**：数据结构多变、存在大量嵌套数据、用户画像、内容资讯、日志、IoT 设备数据。

**不适用场景**：金融账务、强 ACID 事务、大量多表关联 JOIN 查询场景。

**竞品对比**：Mongo 不替代 MySQL、ES。相比 MySQL，它 Schema 灵活、原生分片扩容、无需手动分库分表，但事务与关联查询能力弱；相比 ES，它是完整的业务主库，支持完备 CRUD、事务、高可用，无需依赖外部数据同步，仅重度全文检索场景不如 ES。

## 3. 集群架构核心（核心必背）

MongoDB 共三种部署形态：**单机、副本集集群、分片集群**。

**单机**：单 mongod 进程，无集群、无高可用、无分片能力，仅用于开发测试。

**副本集集群**：只做高可用、不拆分数据。所有节点存储**全量数据**，包含主节点、从节点、仲裁节点；主节点负责写入，故障后自动投票选主，保障容灾，但无法实现海量数据扩容。

**分片集群（核心扩容架构）**：在副本集基础上实现数据拆分、水平扩容，由三层组件组成：

1. **Mongos 路由节点**：无状态统一入口，不存业务数据，负责接收请求、根据元数据路由转发、合并多分片查询结果。

2. **Config 配置节点**：以副本集部署，存储集群元数据、分片规则、Chunk 与分片映射关系，是集群路由的核心依据。

3. **Shard 分片节点**：真正存储业务数据，**每个 Shard 本身就是一套副本集**，兼顾分片扩容与单分片高可用。

### 分片机制

分片的最小单元是 **Chunk**，以集合的 **ShardKey（分片键）** 为拆分依据，**同一个集合只能使用一套固定分片键，不可文档自定义**，不同集合可独立配置分片键。

**范围分片**：按分片键数值范围切分，范围查询性能好，但新数据易扎堆，产生写入热点、数据倾斜。

**哈希分片**：对分片键哈希打散，数据分布均匀、无热点，但分片键范围查询会广播所有分片，性能差。

集群支持动态重平衡，可迁移 Chunk 实现扩容缩容。

### 副本机制

副本集用于高可用、故障容灾、读写分离；主节点负责写，从节点异步同步数据，可承担读请求。推荐奇数投票节点，仲裁节点仅参与选举、不存业务数据，规避脑裂。

### 完整读写流程（分片集群）

**写入流程**：客户端 → Mongos → 拉取 Config 元数据定位 Shard → 转发至对应 Shard 主节点 → 主节点写入、同步副本 → 确认返回 Mongos → 响应客户端。

**读取流程**：客户端 → Mongos → 读取 Config 元数据路由分片 → 默认读主节点，可配置读偏好走从节点，分担读压力（存在数据延迟）。

### 底层存储结构

默认 WiredTiger 引擎，基于 **B+ 树** 存储，支持 MVCC 多版本并发、数据压缩，以磁盘页为单位管理数据。

## 4. 关键机制与核心概念

### 持久化机制

采用 **WAL 预写日志（Journal）+ Checkpoint 快照** 持久化。数据先写内存与日志，定时刷盘落盘；故障时通过日志重放恢复数据。通过**writeConcern** 控制写可靠性，w:1 存在丢数据风险，majority 多数节点确认安全性更高、性能更低。

### 高可用与脑裂处理

副本集通过心跳检测故障，主节点失联后自动选举新主，旧主恢复后自动降级为从节点。采用**奇数投票节点**机制，杜绝双主脑裂问题。

### 扩容与性能问题

新增分片会触发后台 Chunk 迁移重平衡，占用 IO 与网络资源，业务高峰期会产生性能抖动；核心性能瓶颈为：分片键选择不当导致数据倾斜、跨分片聚合查询、无索引全表扫描、重平衡流量冲击。

### 核心专有概念

Document 文档（行）、Collection 集合（表）、Chunk 分片最小单元、ShardKey 分片键、writeConcern 写关注、readPreference 读偏好。

## 5. 基础实操最简 CRUD

仅单机 Docker 测试，不搭建复杂集群

// 隐式创建集合、增删改查  
db.createCollection("user")  
db.user.insertOne({name:"test",age:20})  
db.user.find({age:{$gt:10}})  
db.user.updateOne({name:"test"},{$set:{age:21}})  
db.user.deleteOne({name:"test"})

核心常用参数：writeConcern（写确认级别）、readPreference（读写节点选择）、projection（字段过滤）

执行逻辑：单机直接读写内存与日志；分片集群需经 Mongos 路由定位分片执行。

## 6. 高频面试题（推导思路）

### 架构类

1. 分片集群三大组件作用：Mongos 路由入口、Config 存元数据、Shard 存真实业务数据，三层配合实现分片扩容。

2. 分片选型：范围分片适配范围查询、易倾斜；哈希分片数据均匀、范围查询弱；分片键需兼顾查询场景与数据分布，且选定后不可随意修改。

### 读写流程类

1. 分片写入流程：客户端请求经 Mongos 路由，依据 Config 元数据定位分片主节点，写入后副本同步完成响应。

2. 从节点读优势与风险：分担主节点压力，但存在同步延迟，会读取到旧数据。

### 故障高可用类

1. 副本集奇数节点：防止脑裂，保证选举能产生唯一主节点；仲裁节点零存储、仅投票，节省资源。

2. 数据丢失场景：writeConcern=1、主节点宕机未完成副本同步、关闭 Journal 日志。

### 性能踩坑类

1. 数据倾斜：分片键不合理导致数据集中在单个分片，丧失集群扩容能力。

2. 跨分片聚合慢：Mongos 需要汇总所有分片数据，消耗大量网络与内存资源。

### 选型对比类

结构多变、海量数据扩容选 Mongo；强事务、多表 JOIN、金融场景选 MySQL；重度全文检索选 ES。

## 7. 面试口述小抄（300字内）

MongoDB是文档型NoSQL数据库，以数据库、集合、文档为核心存储层级，集合无固定Schema，适配多变业务数据。集群分为副本集和分片集群，副本集保障高可用、不拆分数据，分片集群由mongos路由、config元数据节点、shard分片组成，每个分片自带副本集，通过分片键做范围或哈希分片，实现海量数据水平扩容。底层基于WiredTiger的B+树存储，依靠Journal日志+检查点实现持久化，可通过写关注调整数据可靠性。它适合结构多变、嵌套数据多、需快速扩容的场景，不适合强事务和多表关联业务。核心痛点是分片键选型不当易数据倾斜，跨分片聚合性能较差，扩容重平衡会带来性能抖动。

## 8. 学习避坑点

跳过生产集群复杂部署调优、底层源码、冷门语法、复杂聚合管道、老旧引擎、专业运维备份方案，仅掌握核心架构、机制、面试考点即可。

## 9. 无项目经验面试模板

我项目中没有生产落地经验，但研究过整体架构、读写流程和核心机制。MongoDB主要解决半结构化数据存储和海量数据水平扩容问题，依靠分片集群实现横向扩容，副本集保障高可用。写入经mongos路由转发至对应分片主节点，优势是Schema灵活、原生分片扩容成本低；局限是跨分片事务弱、聚合性能差。如果业务引入，我会重点做好分片键选型，规避数据倾斜和热点问题。
