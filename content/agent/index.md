title: Agent 项目面试问题清单
---

- 设计范式

> ReAct, Plan-and-Execute, Reflection / Self-Correction, Multi-Agetn

- 推理模式

> Chain of Thought, ReAct, Tree of Thought, Reflection

## 一、项目背景与个人贡献

- 这个项目解决了什么业务问题？
  - 原来的人工处理流程是什么？最耗时的环节在哪里？
  - 为什么选择 Agent？普通搜索、规则系统或固定工作流能否解决？
  - 目标用户是谁？最初上线的核心场景是什么？
- 你在项目中具体负责什么？
  - 哪些模块是你独立设计和实现的？
  - 哪些能力来自模型、框架或已有平台？你补充了什么？
  - 你做过最关键的技术决策是什么？当时有哪些备选方案？
- 项目的实际效果如何证明？
  - “排查效率提升”“准确率提高”的统计口径是什么？
  - 上线前后的对照是否使用了相近难度的任务？
  - 能否讲清一次成功案例和一次失败案例的完整过程？

## 二、整体架构与完整请求链路

- 能否画出项目架构，并解释一次告警从进入系统到生成结论的全过程？
  - 每一步的输入、输出和存储位置分别是什么？
  - 哪些步骤由程序控制，哪些步骤由模型决定？
  - 哪些步骤可以并行，哪些必须串行？
- 系统为什么这样拆分模块？
  - Agent 编排、模型调用、知识检索和工具执行之间如何划分边界？
  - 如何替换模型、向量数据库或工具，而不修改整个系统？
  - 如果模型服务、检索服务或监控平台不可用，系统如何降级？

## 三、Agent 基础与方案选型

- 你如何定义 Agent？这个项目的“自主性”体现在哪里？
  - Agent 与普通大模型对话、RAG 问答、Workflow 有什么区别？
  - 给模型增加工具调用，是否就足以构成你所说的 Agent？
  - 哪些任务适合开放式决策，哪些应该使用确定性流程？
- 为什么选择当前 Agent 架构？
  - ReAct、Plan-and-Execute、路由工作流分别适合什么场景？
  - 为什么不直接使用一个长 Prompt 完成所有任务？
  - 在什么情况下，你会减少 Agent 的自主决策范围？

## 四、模型选择与大模型基础

- 你如何选择项目使用的模型？
  - 如何评估中文理解、工具调用、结构化输出和长上下文能力？
  - 如何权衡效果、延迟、成本与部署要求？
  - 什么任务适合小模型，什么任务需要更强的模型？
- 大模型的哪些特性直接影响项目实现？
  - Token、上下文窗口、最大输出长度分别限制什么？
  - Temperature 等采样参数会影响哪些行为？低温度是否意味着结果一定一致？
  - 为什么模型可能编造事实、工具名称或工具参数？
- 如果岗位涉及模型适配，你如何判断是否需要微调？
  - Prompt 优化、RAG 和微调分别解决什么问题？
  - SFT、LoRA 的基本思路是什么？训练数据从哪里来？
  - 如何验证微调收益，并防止评估数据泄漏？

## 五、任务规划与执行循环

- Agent 如何把“帮我排查这个告警”转成可执行步骤？
  - 如何识别服务、环境、时间范围等必要信息？
  - 信息缺失时，什么时候追问用户，什么时候可以自行查询？
  - 计划中的步骤依赖如何表示和执行？
- Agent 如何根据中间结果调整下一步？
  - 新证据推翻原假设时，如何修改计划？
  - 如何识别重复查询、无效尝试和循环调用？
  - 如何设置最大步数、时间预算和费用预算？
- Agent 如何判断任务已经完成？
  - 如何区分“已经调用完工具”和“已经解决问题”？
  - 证据不足时，如何决定继续调查、输出不确定结论或转人工？
  - 如何避免模型过早宣布成功？

## 六、工具调用与接口设计

- 从模型决定调用工具到拿到结果，完整流程是什么？
  - 模型输出什么？真正执行工具的是哪个组件？
  - 工具名称、描述和参数 Schema 如何设计？
  - 如何把工具结果与对应的调用关联起来？
- 如何提高工具选择和参数生成的可靠性？
  - 多个工具能力相似时，如何减少误选？
  - 必填参数缺失、类型错误、资源不存在时如何处理？
  - JSON 格式合法，是否代表参数在业务上也合法？
- 工具执行失败时如何恢复？
  - 超时、限流、权限不足和业务失败是否采用相同策略？
  - 哪些错误适合重试，哪些需要模型换一种方法？
  - 工具返回的数据太多时，如何过滤、分页或摘要？

## 七、MCP 与外部系统集成

- MCP 解决什么问题？它与 Function Calling、普通 HTTP API 有什么关系？
  - Host、Client、Server 分别负责什么？
  - Tools、Resources、Prompts 的区别是什么？
  - 把已有 API 接入 MCP，需要增加哪些工作？
- 如果项目使用 MCP，生产接入如何设计？
  - 工具如何发现、筛选和更新？
  - 如何完成身份认证、权限校验和凭证管理？
  - MCP Server 不可用或接口版本变化时如何处理？
- 如果没有使用 MCP，你为什么选择直接调用 API？
  - 当前规模下，引入 MCP 的收益和维护成本分别是什么？
  - 将来迁移时，哪些接口可以复用？

## 八、Prompt 与上下文管理

- 你如何组织 Agent 的提示词和上下文？
  - 系统规则、用户请求、工具说明和检索材料分别放在哪里？
  - 不同阶段是否使用不同的 Prompt？
  - 如何区分用户指令与文档、日志中的普通内容？
- 上下文越来越长时如何处理？
  - 哪些信息必须保留，哪些可以删除、摘要或按需检索？
  - 如何避免压缩时丢失告警时间、关键证据和已经执行的操作？
  - 如何判断效果下降来自上下文噪声，还是模型能力不足？
- Prompt 如何迭代和管理？
  - 如何记录版本，并验证一次修改确实有效？
  - Few-shot 示例如何选择，如何避免只适配少数样例？
  - 哪些约束可以写进 Prompt，哪些必须由代码强制执行？

## 九、RAG：知识入库与更新

- 项目知识库包含哪些数据？如何转成可检索内容？
  - 文档、表格、日志片段和历史工单分别如何解析？
  - 分块大小和重叠长度如何选择？
  - 如何保留标题层级、代码块和表格的完整语义？
- Embedding 模型和存储方案如何选择？
  - 如何评估向量对错误码、服务名、缩写的检索效果？
  - 更换 Embedding 模型后，已有向量如何迁移？
  - 为什么选择当前向量数据库或数据库向量扩展？
- 知识如何持续更新？
  - 文档新增、修改和删除后，索引如何同步？
  - 如何处理重复、过期和相互矛盾的知识？
  - 文档权限、版本和来源如何随分块保留？

## 十、RAG：检索、重排与答案生成

- 用户提问到检索结果之间经历了哪些步骤？
  - 是否进行查询改写、关键词提取或多查询扩展？
  - 向量检索、关键词检索和混合检索如何选择？
  - 服务名称、时间范围、环境等条件如何参与过滤？
- 检索结果如何筛选和排序？
  - Top K 如何确定？为什么不是越大越好？
  - 是否使用重排模型？如何衡量收益和额外延迟？
  - 如何避免多条近似内容挤占上下文？
- 如何保证最终结论有依据？
  - 如何区分“没有检索到”“检索到了但模型没用好”？
  - 如何让答案中的关键判断关联到原始证据？
  - 历史故障文档与实时监控冲突时，如何处理？
  - 普通 RAG 与由 Agent 决定何时、如何检索的方式有什么区别？

## 十一、记忆与会话状态

- 你如何区分上下文、任务状态、短期记忆和长期记忆？
  - 当前排查进度、用户偏好和历史故障结论分别存在哪里？
  - 哪些信息适合长期保存，哪些只属于当前任务？
  - 知识库与长期记忆的边界是什么？
- 记忆如何写入和使用？
  - 谁决定写入？如何避免把错误推断保存成事实？
  - 如何解决新旧记忆冲突、过期和重复问题？
  - 如何支持用户、团队、租户之间的隔离与删除？
- 多轮对话如何保持一致？
  - 用户中途纠正服务名或时间范围后，旧结论如何失效？
  - 同一会话同时收到两条请求时，状态如何更新？
  - 如何避免上一次故障的信息污染当前排查？

## 十二、框架、状态机与持久化执行

- 为什么选择当前框架？不使用框架能否实现？
  - 框架替你解决了哪些具体问题？
  - 哪些封装增加了调试或维护难度？
  - 能否解释核心执行流程，而不只介绍框架 API？
- 如果使用 LangGraph 或类似图编排框架，如何建模？
  - 节点、边、条件分支和共享状态分别如何设计？
  - 并行节点更新同一个字段时如何合并？
  - 子流程的输入、输出和状态边界如何定义？
- 长时间任务如何暂停和恢复？
  - 检查点保存什么？在什么时机写入？
  - 进程崩溃后，如何确定从哪里继续？
  - 恢复执行时，如何避免重复触发外部操作？
  - 工作流版本升级后，旧任务还能否恢复？

## 十三、多 Agent 协作（扩展）

- 什么情况下需要多 Agent？
  - 为什么不采用单 Agent 配合多个工具？
  - 拆成日志分析、指标分析和知识检索 Agent，有什么实际收益？
  - 如何证明收益来自分工，而不只是更多模型调用？
- 多 Agent 如何协作？
  - 谁分配任务？子 Agent 拿到哪些上下文？
  - 如何控制重复劳动、消息数量和总 Token 消耗？
  - 多个 Agent 得出冲突结论时如何处理？
- 如何管理协作过程中的失败？
  - 某个子 Agent 超时或失败，整体是否继续？
  - 如何限制递归委派和 Agent 数量？
  - 子 Agent 是否继承全部权限？结果如何验证？

## 十四、安全、权限与人工审批

- Agent 能访问什么数据、执行什么操作？
  - 如何区分只读查询和有副作用的操作？
  - 权限基于用户身份、Agent 身份还是服务账号？
  - 如何防止跨团队、跨租户读取数据？
- 如何防范提示注入？
  - 日志或知识文档里出现“忽略之前规则”时，系统如何处理？
  - 工具返回内容诱导 Agent 调用其他敏感工具时，如何限制？
  - 凭证、个人信息和内部敏感数据如何脱敏？
- 人工审批如何实现？
  - 哪些动作必须审批？审批页面需要展示哪些信息？
  - 用户批准后，如何确保执行参数没有被替换？
  - 审批期间系统状态发生变化，是否需要重新检查或审批？
  - 如何记录谁批准了什么，以及实际执行了什么？

## 十五、评估、测试与效果归因

- 如何定义 Agent 的“效果好”？
  - 最终结论正确率、任务完成率、工具调用正确率分别如何衡量？
  - 如何区分完全成功、部分成功和表面成功？
  - 如何同时评价正确性、成本、耗时和安全性？
- 评估数据集如何构建？
  - 数据来自真实历史故障、人工编写还是合成？
  - 如何覆盖正常、异常、无答案、权限不足和恶意输入？
  - 如何划分开发集与测试集，避免针对题目调参？
- 多步、非确定性的 Agent 如何测试？
  - 正确执行路径不唯一时，应该检查结果还是执行过程？
  - 同一道题多次运行结果不同，如何衡量稳定性？
  - 哪些测试使用模拟工具，哪些必须连接真实或隔离环境？
- 如何判断一次优化有没有价值？
  - 如何通过对照实验定位 Prompt、检索、模型或工具的贡献？
  - 使用 LLM-as-a-Judge 时，如何校验评判可靠性？
  - 如何防止自动评判只偏爱语言流畅、篇幅较长的回答？

## 十六、可观测性与问题定位

- 一次 Agent 执行需要记录哪些信息？
  - 模型调用、工具调用、检索结果和状态变化如何串成一条执行记录？
  - 如何记录模型、Prompt、知识库和工具的版本？
  - 如何兼顾问题复现与日志脱敏？
- 用户反馈“答案错了”，你如何排查？
  - 如何判断是检索错误、推理错误、参数错误还是数据源问题？
  - 如何还原当时的上下文和外部工具返回值？
  - 是否需要模型完整内部推理才能排障？可依靠哪些可验证记录？
- 系统上线后监控什么？
  - 如何发现失败率、循环次数、费用和人工接管率异常？
  - 如何区分模型变更、知识更新与业务流量变化造成的影响？
  - 修复过的问题如何沉淀成回归用例？

## 十七、后端工程与可靠性

- 长时间运行的 Agent 任务如何提供服务？
  - 哪些接口同步返回，哪些进入异步任务队列？
  - 如何设计任务状态、进度查询和结果获取接口？
  - 用户断开连接后，任务继续还是取消？
- 如何处理并发和重复请求？
  - 同一告警重复投递时，如何去重？
  - 同一任务被多个 Worker 获取时，如何防止重复执行？
  - 如何限制单用户或单租户的并发与资源消耗？
- 如何处理外部操作的一致性？
  - 工具执行成功，但结果保存失败时，如何恢复？
  - 外部接口超时，无法确定是否执行成功时，是否可以直接重试？
  - 多步操作只成功一部分时，如何补偿或转人工？
- 流式响应如何实现？
  - 如何通过 SSE 或 WebSocket 展示进度、工具状态和最终结果？
  - 断线重连后，如何补发事件并避免重复展示？
  - 取消操作如何传递到正在执行的模型和工具调用？

## 十八、性能、成本与上线发布

- 一次请求的耗时主要分布在哪里？
  - 如何分别测量模型、检索、重排和工具调用耗时？
  - 如何缩短首条反馈时间和整个任务完成时间？
  - 哪些步骤可以并行，哪些可以减少或跳过？
- 如何控制模型使用成本？
  - 如何统计单任务、单用户和单租户的费用？
  - 如何采用模型路由、上下文裁剪、结果缓存或预算控制？
  - 故障排查数据具有时效性时，缓存如何失效？
- 新版本如何安全上线？
  - 模型、Prompt、工具或知识库更新后，需要哪些发布检查？
  - 如何灰度发布，并在效果下降时回滚？
  - 是否需要影子运行？如何避免产生真实副作用？
  - 流量增加十倍时，哪个环节最可能先成为瓶颈？

## 十九、围绕假想项目的现场追问

- 用户只说“线上很慢”，没有服务名和时间范围，Agent 下一步应该如何决定？
- 告警显示接口错误率上升，但当前日志没有异常，Agent 如何继续排查？
- 日志指向数据库问题，监控指向网络问题，历史文档指向缓存问题，如何组织证据和验证假设？
- 某次发布与故障时间接近，如何避免直接把时间相关性当作因果关系？
- 一小时内产生几千条相关告警，如何聚合成故障事件，避免重复调查？
- 日志内容超过上下文窗口几十倍，如何设计查询与逐步分析流程？
- Agent 连续多轮调用同一工具，却没有获得新信息，如何发现并终止？
- Agent 引用了一篇已经过期的处理手册，如何从系统设计上减少此类问题？
- Agent 建议重启服务，但用户只要求分析原因，系统应如何约束后续动作？
- 审批通过后，服务已经被其他值班人员修复，如何避免继续执行过时操作？
- 工具调用返回超时，但重启操作可能已经发生，系统如何确认真实状态？
- 离线评估表现很好，上线后用户仍然不信任，如何定位原因？
- 成功率提高了，但平均费用翻倍、响应时间增加，如何判断是否值得发布？
- 如果只允许两周完成第一版，你会保留哪些能力？如何定义验收标准？

## 二十、现场编码与设计题

- 不使用 Agent 框架，如何实现一个包含模型调用、工具执行和终止条件的最小 Agent Loop？
- 如何实现一个支持参数校验、超时、错误分类和权限检查的工具执行器？
- 如何实现相互独立工具的并行调用，并处理部分失败？
- 如何设计支持暂停、人工审批、恢复和取消的任务状态机？
- 如何实现带检查点的执行流程，并处理恢复后的重复操作？
- 如何实现一个支持知识入库、检索、来源引用和增量更新的最小 RAG 服务？
- 如何设计一个不超过给定 Token 预算的上下文构建器？
- 如何编写 Agent 评估程序，统计任务成功率、耗时、费用和多次运行稳定性？
- 给出一段失败的 Agent 执行记录，你能否找出根因并提出最小修复方案？

## 二十一、项目深挖与复盘

- 项目中最难解决的问题是什么？为什么最初的方案没有奏效？
- 你尝试过哪些没有效果甚至带来退步的优化？如何确认它们无效？
