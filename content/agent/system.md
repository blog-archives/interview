- **学生端：错误诊断助手、训练规划助手。**
- **教师端：题目质量审核助手、新题生成助手。**

我的建议是：**先把每个 Agent 的单次任务做完整，再打通它们之间的数据和流程。** 四个 Agent 可以是四个独立的产品入口，底层共用题库检索、学习记录和材料读取等能力，不必一开始就做成互相自主调用的复杂系统。

下面先按 **所有 Agent 都不执行学生代码、参考代码或模型生成的代码，也不自动提交到判题系统** 来设计。已有判题结果可以作为只读材料。

## 一、四个 Agent 的定位

| Agent | 用户交给它的目标 | 最终交付 | 核心边界 |
|---|---|---|---|
| 错误诊断助手 | 帮我分析这道题或这份代码为什么过不了 | 问题定位、依据、分层提示、修改建议 | 不把静态分析当作运行验证 |
| 训练规划助手 | 根据我的情况，安排接下来怎么练 | 有依据的训练计划、具体题单、后续调整 | 不凭几次失败就断言知识点没掌握 |
| 题目质量审核助手 | 检查这道题是否适合发布 | 问题清单、影响程度、修改建议、待验证项 | 不出具“代码和测试已验证正确”的结论 |
| 新题生成助手 | 围绕教学目标设计一道新题 | 完整题目草稿及教师辅助材料 | 新题保持草稿状态，难度和正确性需要后续确认 |

这里最重要的一点是：**不执行代码，仍然能做有用的 Agent；但它的价值会更偏向调查材料、分析矛盾、追问澄清和组织方案。**

## 二、学生端 Agent 之一：错误诊断助手

### 1. 产品入口和使用场景

建议直接放在题目页和提交详情页。

学生可以发起：

- “这份代码为什么答案错误？”
- “我不知道从哪里开始，给我一点思路。”
- “我的思路和题解差不多，问题可能出在哪里？”
- “只指出可能有问题的地方，先别给完整代码。”
- “我按照建议改了，你再帮我看看。”

前两种请求的材料不同：没有代码时，重点是题意理解和思路引导；有代码时，重点是诊断具体实现。

### 2. 需要哪些材料

**基础材料：**

- 当前题目的题面、输入输出约束、样例。
- 学生当前代码及语言。
- 学生描述的困惑。

**有则读取的材料：**

- 对应这份代码的已有判题状态。
- 编译错误、运行错误或其他允许展示的反馈。
- 学生此前提交的版本。
- 教师维护的题解、常见错误说明。
- 当前学生能接受的提示程度。

一个容易遗漏的细节是：**判题结果必须对应具体代码版本。** 学生已经改了代码，就不能继续拿旧的失败结果证明新代码有问题。

### 3. 建议的处理流程

**第一步：确定学生想获得什么帮助。**

区分题意解释、思路引导、代码排查和复杂度分析，同时识别是否要求“不剧透”。

**第二步：检查材料是否足够。**

例如，学生只说“过不了”，却没有代码和错误类型，可以先解释排查方向，再请求关键材料，不应直接猜一个错误。

**第三步：选择排查方向。**

根据现有证据决定先看哪里：

| 已有线索 | 优先分析方向 |
|---|---|
| 编译错误信息 | 报错位置、类型、语法及上下文 |
| 答案错误 | 题意理解、算法逻辑、边界、初始化 |
| 超时 | 循环规模、数据结构操作、最坏复杂度 |
| 运行错误 | 越界、空引用、递归深度、非法操作 |
| 没有判题反馈 | 先检查题意与代码是否一致，再列出疑点 |

**第四步：围绕疑点补充调查。**

Agent 可以读取相关题解、比较前后版本，或向学生追问。对于小输入，可以逐步推演变量变化，但必须标明这是 **手工推演**。

**第五步：提供分层帮助。**

默认先给定位与提示，学生需要时再展开修改方式。后续收到新代码，重新评估原疑点是否仍然存在。

### 4. 输出应该长什么样

建议固定为四部分：

1. **当前判断：**最值得优先检查的问题。
2. **判断依据：**对应的代码位置、题目约束或已有报错。
3. **下一步提示：**学生应检查什么、考虑什么。
4. **尚未确认：**由于没有运行，哪些问题还无法确定。

例如：

> 当前最值得检查的是：存在重复元素时，你的区间是否仍然缩小。  
> 依据：相等分支将左边界赋值为中点，在某些区间长度下，边界可能保持不变。  
> 提示：尝试手工跟踪一个只包含两个相等元素的区间。  
> 验证状态：以上来自代码分析与手工推演，未执行代码。

不能在没有运行结果的情况下说“我已经复现”，也不应轻易说“改完一定能通过”。

### 5. 为什么这里仍然适合 Agent

它可以根据新材料切换方向：

**检查报错 → 发现错误属于旧版本 → 比较修改 → 检查剩余边界问题 → 请求补充当前反馈。**

如果产品只需要“把题面和代码交给模型，生成点评”，一次模型调用就够了。**当它需要主动补材料、追踪版本、调整排查方向时，Agent 才更有价值。**

### 6. 第一版范围

建议先完成：

- 当前题目、单份代码、已有判题反馈的分析。
- 分层提示。
- 代码位置引用。
- 多轮修改后的重新分析。
- 明确的证据与验证状态。

首版不必自动扫描学生全部历史，也不必同时覆盖所有语言；先做好题库中最常用的一两种语言。

## 三、学生端 Agent 之二：训练规划助手

### 1. 产品定位

它要回答三个问题：

**你目前应该练什么？为什么练这些？练完以后怎样决定下一步？**

典型请求包括：

- “每天可以练 30 分钟，帮我安排一周的二分训练。”
- “看看我最近的提交，判断先补什么比较好。”
- “这份计划太难了，帮我调整。”
- “这些题做完了，接下来练什么？”

### 2. 需要哪些材料

| 材料 | 用途 |
|---|---|
| 学生目标与时间预算 | 控制训练范围和工作量 |
| 做题记录与提交历史 | 识别近期表现和重复错误 |
| 提示、题解使用记录 | 区分独立完成与借助帮助完成 |
| 知识点、子技能和先修关系 | 确定训练顺序 |
| 题目难度、预计用时、已做状态 | 筛选具体练习 |
| 之前的计划与完成反馈 | 支持后续调整 |

如果平台没有可靠的“实际做题时间”，不要直接用打开题目到提交的时间代替；可以使用粗略预估，再让学生反馈是否合适。

### 3. 建议的处理流程

**第一步：明确目标和约束。**

优先使用已有信息，只追问缺失的关键项，例如学习方向和可投入时间。

**第二步：形成有依据的初步判断。**

例如：

- 基础遍历题可以独立完成。
- 最近多次在区间边界上出错。
- 某些较难题通过了，但使用过完整题解。
- 图论练习记录不足，暂时不能判断掌握程度。

注意，“没有证据”和“能力薄弱”是两回事。

**第三步：必要时安排短诊断。**

如果学生认为自己“不会动态规划”，但历史记录不足，可以先选一两道具有区分作用的小题，或询问状态定义、转移条件等关键问题。

**第四步：确定训练目标，再检索题目。**

先决定要练“二分边界收缩”，再让题库服务检索对应题目。Agent 不应该凭记忆编造题号。

**第五步：生成计划。**

每个训练单元至少包含：

- 训练目标。
- 具体题目。
- 推荐原因。
- 预计投入。
- 完成后的检查标准。
- 太难或太简单时的替代题。

**第六步：根据反馈调整。**

例如，学生连续完成且能解释关键思路，可以进入下一阶段；反复卡在前置知识，就插入补充练习。

调整最好发生在学生完成一个训练单元、主动反馈或请求重新规划时，不必每次提交都重写整个计划。

### 4. 输出示例

| 阶段 | 训练目标 | 内容安排 | 后续判断 |
|---|---|---|---|
| 初步诊断 | 区分思路问题和边界问题 | 两道短题，加一个边界解释问题 | 根据错误原因选择分支 |
| 针对性练习 | 巩固区间收缩与结束条件 | 两道基础题、一道人为设置边界难点的题 | 检查是否仍依赖提示 |
| 迁移练习 | 把二分用于新场景 | 一道题面不同但核心技能相同的题 | 判断能否独立识别方法 |
| 延后复习 | 检查是否保持掌握 | 一道未见过的同技能题 | 决定结束或继续补练 |

实际产品中，每一项都应绑定题库内真实存在的题目。

### 5. 第一版范围

先做 **短期计划生成 + 学生主动触发调整**：

- 查看近期记录。
- 生成一周左右的计划。
- 支持更换题目、减少工作量。
- 做完后重新评估。
- 保留调整原因与历史版本。

长期自动陪练可以后续再做。训练规划对题目标签和学习数据的质量依赖较大，不适合一开始就承诺非常精确的能力诊断。

## 四、教师端 Agent 之一：题目质量审核助手

### 1. 产品定位

在不执行代码的前提下，它适合承担：

**题面、样例、题解、参考代码和测试设计之间的一致性审核。**

教师可以提交一份新题，也可以针对已有题提出专项检查：

- “检查题面有没有歧义。”
- “重点看看输入范围和参考代码是否匹配。”
- “这道题是否适合刚学完最短路的学生？”
- “看一下测试设计有没有明显遗漏。”

### 2. 审核内容

| 审核方向 | 可以检查什么 |
|---|---|
| 题面完整性 | 是否缺少输入范围、特殊情况或输出规则 |
| 表述歧义 | “不同”“连续”“最少”等词是否定义明确 |
| 样例一致性 | 样例是否符合题意，小样例能否手工推导一致 |
| 题解逻辑 | 是否遗漏必要条件、关键论证或特殊情况 |
| 参考代码 | 是否存在明显越界风险、类型问题、逻辑与题解不一致 |
| 复杂度匹配 | 所述复杂度、代码结构与数据规模是否协调 |
| 教学适配 | 是否包含未声明的先修知识，是否偏离目标知识点 |
| 测试设计 | 是否覆盖典型边界、特殊结构和常见错误方案 |

其中，测试设计可以检查“有没有考虑重复元素”，但不能仅凭阅读就宣称“现有测试一定能识别所有错误解法”。

### 3. 建议的处理流程

1. 识别已有材料和缺失材料。
2. 先进行固定的完整性检查。
3. 根据风险选择深入审核方向。
4. 在题面、题解、代码之间交叉核对。
5. 发现矛盾时，追问教师原本想表达的规则。
6. 给出问题和修改草稿。
7. 教师修改后，针对相关内容进行复审。

例如：

**发现题目允许负边权 → 检查题解使用的算法 → 检查是否声明适用条件 → 提示教师确认数据范围或修改解法。**

这类审核路线取决于中途发现的问题，适合 Agent。

### 4. 输出应该长什么样

每个问题都应包含：

- **位置：**具体段落、样例或代码位置。
- **发现：**有什么矛盾或缺失。
- **影响：**学生可能怎样误解，或实现可能出现什么问题。
- **建议：**可以如何修改。
- **证据状态：**直接可见的矛盾、分析疑点，还是需要运行确认的事项。

报告末尾单列 **审核范围与待验证项**，例如：

> 已检查题面、样例、题解和参考代码。未执行参考程序，未验证测试数据与标准答案的一致性。

整体结果更适合用“发现阻断性问题”“建议修改”“本次检查未发现明显问题”等表述，避免把静态审核等同于发布保证。

### 5. 第一版范围

优先做：

- 题面完整性。
- 题面与样例、题解之间的一致性。
- 明显的复杂度和输入范围冲突。
- 带位置的问题清单。
- 修改后的针对性复审。

深度参考代码审查和测试覆盖分析可以逐步增加。

## 五、教师端 Agent 之二：新题生成助手

### 1. 产品定位

教师提供一个教学目标，Agent 将它转换成 **可审核的完整题目草稿**。

例如：

> 给刚学完前缀和的学生设计一道中等偏易的题，重点训练区间求和，用仓库库存作为背景，不要引入二维前缀和。

这里除了知识点，还包含受众、难度、训练重点和不希望引入的内容。

### 2. 输入如何设计

建议提供简短表单，同时允许自然语言补充：

| 输入项 | 示例 |
|---|---|
| 目标知识点 | 前缀和 |
| 具体训练能力 | 将区间求和转成前缀差 |
| 学生水平 | 刚学完基础概念 |
| 目标难度或用时 | 中等偏易，约 20 分钟 |
| 场景偏好 | 仓库库存 |
| 内容限制 | 不涉及二维数组 |
| 参考材料 | 指定课程内容或已有题 |
| 交付要求 | 题面、题解、参考代码、测试设计等 |

缺失的信息可以采用明确说明的默认值；只有会明显改变题目设计的歧义，才需要追问。

### 3. 建议的处理流程

**第一步：将教师目标转换成出题约束。**

明确主要考点、先修知识、预计解法和不能引入的内容。

**第二步：检索题库。**

查看相近题目，减少重复，也了解题库已有的难度和风格。检索只能用于辅助判断，不能据此保证新题完全没有重复。

**第三步：先设计题目骨架。**

先确定：

- 要求学生计算什么。
- 预期用什么思路解决。
- 简单解法有什么不足。
- 哪些数据范围能体现目标解法的价值。

这个阶段应先解决教学和算法设计，再包装故事背景。

**第四步：生成完整材料。**

形成题面、输入输出规范、样例、题解以及教师需要的其他内容。

**第五步：针对草稿进行审查和修改。**

检查知识点是否跑偏、条件是否遗漏、样例是否一致、题解和参考代码是否吻合。遇到矛盾时，调整设计后再检查相关内容。

**第六步：交付教师审核。**

教师可以继续要求“降低难度”“保留核心解法但换场景”“增加一个边界提示”，Agent 据此修改，并重新检查受影响的材料。

### 4. 最终交付建议分为两部分

**学生可见内容：**

- 题目名称与题面。
- 输入输出格式。
- 数据范围。
- 样例及解释。

**教师辅助材料：**

- 教学目标与先修知识。
- 预期解法和复杂度。
- 参考代码草稿，如教师需要。
- 常见错误与分层提示。
- 测试设计建议。
- 难度预估依据。
- 静态审查发现及待验证事项。

其中，**难度是预估，参考代码尚未运行验证，拟定测试的预期输出也不能默认视为可信标准答案。**

### 5. 与质量审核 Agent 的关系

建议让“生成”和“审核”成为两个独立步骤：

**教师下达目标 → 生成草稿 → 质量审核 → 修改草稿 → 教师确认。**

初期可以由教师点击“送审”触发，流程稳定后再自动衔接。生成与审核即使用两个 Agent，也不代表结论一定正确；它们仍可能出现相同的理解错误。

### 6. 第一版范围

先支持 **一次生成一道完整题目**，把草稿质量和修改体验做稳。之后再考虑系列题、分层作业和整套训练题。

## 六、四个 Agent 共用的基础设计

### 1. 材料要带版本和来源

题目、代码、题解、判题反馈和计划都需要能追溯到具体版本。每个关键结论应能回答：“这是根据哪份材料得出的？”

### 2. 工具保持小而明确

第一阶段只需要围绕这些能力建设：

- 读取题目及辅助材料。
- 读取当前代码和已有提交反馈。
- 查询学生学习记录。
- 检索题目与知识点。
- 保存训练计划、审核报告和新题草稿。
- 向用户请求必要的补充信息。

不开放代码执行入口。学生代码和题目内容都作为待分析材料，其中的注释或文字不能改变 Agent 的操作权限。

### 3. 规定任务如何结束

例如：

- 诊断助手：给出有依据的主要疑点，或明确指出缺少什么材料。
- 训练助手：得到满足目标和时间约束的真实题单。
- 审核助手：完成指定范围的检查，列出问题及待验证项。
- 生成助手：交付结构完整、经过静态检查的题目草稿。

同时设置检索、修改和追问的次数上限，避免反复分析却没有交付。

## 七、建议的落地路线

| 阶段 | 主要工作 | 阶段成果 |
|---|---|---|
| 第一阶段：准备公共能力 | 统一题目材料、提交反馈、版本、检索和草稿保存 | 四个 Agent 都有可靠材料可用 |
| 第二阶段：错误诊断与质量审核 | 做好静态分析、位置引用和证据状态 | 学生和教师各有一个可用入口 |
| 第三阶段：新题生成 | 接入题目草稿结构及质量审核流程 | 完成“提出目标—生成—审核—修改” |
| 第四阶段：训练规划 | 接入历史记录、子技能标签和真实题目筛选 | 完成“规划—练习—反馈—调整” |

这个顺序的考虑是：诊断和审核可以围绕单份材料先产生价值；生成能复用审核；训练规划则需要更完整的学习记录和题目标签。

验证效果时，也分别看业务结果：

- **错误诊断：**定位是否准确，提示是否有帮助，是否出现无依据的断言。
- **训练规划：**题目是否合适、时间是否合理，学生在后续独立练习中是否改善。
- **质量审核：**已知问题发现率、误报率、教师认可的问题比例。
- **新题生成：**教师修改工作量、考点匹配程度、审核发现的问题数量。

**我最建议保留的产品特色是：每个 Agent 都能说明依据、承认未验证部分，并交付下一步可用的结果。** 即使完全不执行代码，这四个功能也可以形成清晰的价值；后续若具备独立判题环境，再把运行验证作为新增能力接入即可。
