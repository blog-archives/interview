底层是 `hmap`，核心是哈希 + 桶数组，数组元素是 `bmap`（桶）。
key经过哈希运算，哈希值的**高几位用来选桶**，落到对应的 bmap；每个桶最多存 8 组 k‑v。
桶内部存哈希值的**top hash（哈希的高8位）**，查找时先对比 top‑hash，匹配上才完整比较 key，减少完整key对比开销，这点你理解正确。

> 小纠正：**bmap不是链表**。原生桶内部没有链表指针；溢出时，是桶尾部存一个 `overflow` 指针指向额外新建的溢出桶，形成桶链，不是k‑v连成链表。一个主桶可以挂多个溢出桶。

扩容两类：

1. **增量扩容（翻倍扩容）**：负载因子达到 **6.5**（元素数量 / 桶数量）触发，桶数量翻倍，把数据迁移到新桶。
2. **等量扩容**：总元素不多，但溢出桶太多（桶链过长），桶总数不变，只是把松散的数据重新整理，减少溢出桶，不扩大容量。

**渐进式扩容**：触发扩容不会一次性搬完所有桶。hmap同时保存新旧两套桶数组。后续**每次写操作会迁移1‑2个桶**；读操作也会协助访问迁移，不会阻塞一次性全量迁移。直到全部桶迁移完毕，旧桶才丢弃。

额外两个你没提到的重要点：

1. map 不是并发安全，读写并发直接panic；
2. 遍历map是随机顺序，不是插入顺序；遍历期间删除key是允许的，新增key不一定会被本次遍历看到。

## 迁移过程

hmap 内部会维护两套桶数组：**oldbuckets（旧桶数组）**、**newbuckets（新桶数组）**。
没扩容时，`oldbuckets` 为 nil，全部数据存在 `buckets`。一旦触发扩容，就分配 `newbuckets`，同时把原来的 `buckets` 赋值给 `oldbuckets`，当前工作桶切换为 `newbuckets`，此时数据还绝大部分留在 oldbuckets，没有立刻迁移。

hmap 有个 `nevacuate` 字段，标记**下一个待迁移的旧桶下标**，用来渐进迁移。
迁移（evacuate）只在**写操作（增、改、删）**发生：每次写，检查是否还处在扩容阶段，如果是，就根据 `nevacuate`，迁移 1‑2 个旧桶，把里面 kv 分流拷贝到 newbuckets 对应桶，迁移完成后标记这个旧桶已经搬迁完毕，`nevacuate` 向后推进。

> 读操作不会做迁移；读的时候要同时查 oldbuckets + newbuckets，防止读到还没搬走的旧数据。

分两种扩容：

1. **翻倍扩容**：newbuckets 桶数量是 old 的2倍。每个旧桶里的 key，依据哈希值的高位，分流到 newbuckets 的两个目标桶之一。
2. **等量扩容**：newbuckets 和 oldbuckets 桶数量一样。不改变 key 的目标桶，只是把旧桶以及溢出桶里的 kv，重新整理到新桶，削减溢出桶，桶编号不变。

等到 `nevacuate` 走完全部旧桶，代表所有桶迁移完成，`oldbuckets` 置为 nil，扩容结束。

## 删除重点

底层：`delete()` 不是直接把 k‑v 内存清零。
bmap 桶内有**tophash 数组**，删除时把对应槽位的 tophash 标记为**empty（空状态）**，key/value 不会立刻清零，槽位变为可复用。

桶有几种状态标记：正常、empty、evacuated（已经迁移走）。

> 扩容期间删除：如果要删的 key 还在 oldbuckets，会先触发迁移这个桶，再执行删除。

重点要点：

1. delete 一个不存在的 key，不会 panic，什么都不做。
2. **delete 不会缩小 map 容量、不会触发缩容**。就算把所有 key 全部删光，桶的数量不会回落，旧桶数组占用内存不会归还；只会把槽位标记空，后续新增 key 可以复用这些槽。
3. 大量删除元素之后，map 负载因子变低，但桶数组不会收缩；想释放内存只能重建新 map 拷贝数据。
4. 遍历过程中删除 key 是安全允许的，被删的槽标记 empty，本次遍历不会再输出该 key。
5. 扩容阶段删除，会协助 evacuate 迁移对应旧桶；读不会迁移，删除属于写操作

## 问答

3. 问：map桶里面是链表结构吗？
   答：不是，单个桶内部最多8个kv，溢出靠overflow指针串联额外桶，形成桶链，不是kv互相串链表。

4. 问：触发翻倍扩容的负载因子阈值是多少？含义是什么？
   答：6.5，元素个数除以桶的个数，超过该阈值触发翻倍扩容。

5. 问：等量扩容会增加桶的总数量吗，解决什么问题？
   答：桶总数不变，主要解决溢出桶过多、桶链太长的问题，整理数据减少溢出桶。

6. 问：渐进式扩容，读操作会帮忙迁移桶吗？
   答：不会，只有写操作才执行桶迁移；读只会同时查新旧两个桶。

7. 问：为什么map遍历输出顺序不是插入顺序？
   答：遍历从随机起始桶开始遍历，而且扩容后key位置发生变化，所以顺序随机。

8. 问：并发读写map会发生什么？
   答：直接触发运行时panic，map本身无并发安全保护。

9. 问：扩容过程中，读 map 需要访问哪两套桶？
   答：oldbuckets 和 newbuckets 都要查。

10. 问：哪个字段记录下一个要迁移的旧桶？
    答：nevacuate。

11. 问：等量扩容，key会换到别的桶编号吗？
    答：不会，仅整理溢出桶，桶编号不变。

12. 问：读操作会执行桶迁移工作吗？
    答：不会，只有写操作才执行迁移。

13. 问：扩容没完成，旧桶什么时候释放？
    答：全部桶迁移完毕，oldbuckets置nil之后才会交由GC回收。

14. 问：delete 不存在的 key 会 panic 吗？
    答：不会，无操作。
15. 问：大量 delete 之后 map 会自动缩容吗？
    答：不会，Go map 没有缩容机制，桶数组大小不会变小。
16. 问：全部 key 都 delete 掉，原来的桶内存会释放吗？
    答：不会，桶数组保留，只是槽位标记为空，内存不会还给堆；想要释放只能新建 map 复制元素。
17. 问：删除的时候底层怎么标记这个槽位失效？
    答：修改桶内 tophash 的值标记为 empty，key value 不会马上清零。
18. 问：扩容进行中，delete 一个还在 oldbuckets 的 key 会发生什么？
    答：delete 属于写操作，会先迁移该旧桶到 newbuckets，再执行删除逻辑。

19. 问：nil map 执行读取 m [k] 会 panic 吗？
    答：不会，返回对应 value 类型零值。
20. 问：nil map 执行赋值 m [k]=v 会发生什么？
    答：运行时 panic。
21. 问：nil map 调用 delete 会 panic 吗？
    答：会，delete 属于写操作，nil map 直接 panic。
22. 问：nil map 可以直接 range 遍历吗？
    答：可以，遍历直接结束，不会循环、不会 panic。
23. 问：nil map 和空 map `make(map[..])` 的区别？
    答：nil map 底层指针 nil，不能写；空 map 底层已经分配结构，可以增删元素。
