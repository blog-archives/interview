## 面试口述回答

微服务 RPC 的超时时间不能直接拍一个固定值，我一般会从调用本身、整条链路和重试策略三个层面考虑。

首先，看这个 RPC 在正常生产业务高峰下的 P99 延迟，并在 P99 基础上为网络抖动、GC 和瞬时负载等情况留出合理余量，以此得到初始 timeout。这里的 P99 应优先来自线上正常高峰负载；如果服务尚未上线，再用尽量接近真实流量的压测数据估算，而不是拿极限压测下的 P99 作为日常超时基准。

其次，单次 RPC timeout 必须受上游请求整体 deadline，也就是剩余时间预算的约束，不能把剩余时间全部占满，还要给当前服务的本地处理和后续调用留时间。如果存在重试，也要在整体预算内给重试和退避预留时间，避免第一次调用就耗尽全部时间。

工程上通常提供服务级默认 timeout，让大多数普通 RPC 复用；少数延迟特征或业务要求明显不同的 RPC，再配置个性化 timeout。个性化配置可以覆盖默认值，但最终实际生效的时间仍不能超过上游 `context` 的剩余 deadline。

在 Go gRPC 中，可以使用 `context.WithTimeout` 为调用设置超时，并通过 `context` 将 deadline 和取消信号沿调用链向下传播。

## 思路是怎样一步一步收敛的

### 1. 为什么 RPC 必须有超时

假设服务 A 调用服务 B，而 B 因数据库、网络或自身故障长期没有响应。如果 A 没有设置超时，请求就会持续等待，占用 goroutine、连接和内存等资源。随着请求堆积，A 也可能被拖慢，故障进一步向上游扩散。

因此，RPC timeout 不只是为了控制响应时间，也是故障隔离手段：下游在合理时间内无法响应时，上游应及时结束等待并释放资源。

接下来真正需要回答的问题是：这个“合理时间”怎样确定？

### 2. 先用正常高峰下的 P99 加余量得到初始值

timeout 首先要建立在 RPC 的真实延迟分布上，而不是参考一次开发环境请求，也不适合只看平均响应时间。平均值容易掩盖少量但正常存在的慢请求，P99 更能反映尾部延迟。

例如，某个 RPC 在正常生产高峰下的延迟为：

```text
P50 = 60 ms
P95 = 120 ms
P99 = 180 ms
```

P99 为 180 ms，表示约 99% 的请求能在 180 ms 内完成。但 timeout 不应直接等于 180 ms，因为正常运行中仍会出现网络抖动、GC、CPU 瞬时繁忙或连接池短暂竞争。

所以，更完整的判断应当合并为一点：

> 以正常生产业务高峰下的 P99 为基线，再增加合理余量，得到初始 timeout。

例如，可以先将 180 ms 的 P99 上浮到 250～300 ms，再根据超时率、成功率和业务体验持续调整。余量没有适用于所有系统的固定比例，关键是由实际监控数据验证，而不是一次设定后不再变化。

### 3. P99 应该从哪里获得

已经上线的服务，应优先使用真实生产环境、正常业务高峰负载下的数据。它最接近日常要承载的请求特征，也包含线上真实的网络和资源竞争情况。

如果服务还没有上线，则可以通过接近真实流量模型的压测进行估算，包括相似的并发量、请求比例和数据规模。

需要注意，不应把系统接近容量极限时测得的 P99 直接作为常规 timeout 基准。例如，正常高峰 P99 为 180 ms，而极限压测 P99 已经达到 800 ms，这通常说明系统在极端压力下发生了排队或性能退化。此时简单地把常规 timeout 提高到 1 秒，只会让请求等待更久，甚至加剧资源堆积；更应该分析容量、限流或性能瓶颈。

### 4. 初始 timeout 还要服从整条链路的时间预算

只看下游 RPC 自身的 P99 仍然不够，因为一次调用通常只是整个请求链路中的一环。

假设一个 HTTP 接口的整体 deadline 是 1 秒，当前服务收到请求时只剩 600 ms，后面还要进行本地计算并调用其他服务。那么，即使当前 RPC 根据 P99 加余量算出的 timeout 是 700 ms，也不能真的等待 700 ms。

可以把最终有效时间理解为：

```text
有效 RPC deadline
= min（配置的 RPC timeout，上游 context 剩余时间预算）
```

实际分配时，还应从上游剩余预算中扣除本地处理、后续步骤以及必要的安全余量。也就是说，timeout 既要适应下游的正常延迟，又不能破坏上游接口的整体时限。

### 5. 如果存在重试，要提前划分预算

重试不能被当作独立于 timeout 的附加动作。假设整段下游调用总共只有 500 ms 的预算，如果第一次调用的 timeout 就是 500 ms，那么第一次超时后已经没有时间再次尝试。

因此，需要综合考虑：

```text
总调用预算 ≈ 各次尝试时间 + 重试退避时间 + 必要安全余量
```

具体怎样切分取决于业务和故障特征。通常只对幂等、可安全重试的操作启用有限次数的重试，并避免多层服务同时重试造成流量放大。越接近上游 deadline，越不应该发起一个大概率来不及完成的新尝试。

### 6. 默认 timeout 与个性化 timeout 怎样配合

如果每个 RPC 都单独配置，维护成本会很高。因此工程上更常见的做法是设置一个服务级默认 timeout，覆盖大多数延迟特征相近的普通调用；只有少数慢查询、批量操作或业务时限特殊的 RPC，才使用个性化配置。

两者的关系分为两层：

- 在配置层面，RPC 的个性化 timeout 覆盖服务级默认 timeout。
- 在运行时层面，无论最终选中哪个配置值，都不能突破上游 `context` 的剩余 deadline。

因此，某个 RPC 配置了 800 ms，并不代表它一定能执行 800 ms。如果上游 `context` 只剩 300 ms，它最多只能使用这 300 ms；实际工程中通常还要主动少用一点，为后续逻辑留下空间。

### 7. Go gRPC 中如何实现

Go gRPC 通常通过 `context` 设置并传递 deadline：

```go
ctx, cancel := context.WithTimeout(parentCtx, rpcTimeout)
defer cancel()

resp, err := client.GetUser(ctx, req)
```

如果 `parentCtx` 已经有一个更早的 deadline，新创建的 `ctx` 不会把它延长。调用超时或上游取消请求后，取消信号会通过 `context` 传给下游。下游处理代码也应正确监听 `ctx.Done()`，并继续把同一个调用链上的 `context` 传递给数据库或更下游的 RPC，而不是重新创建一个与上游无关的后台 `context`。

## 最终结论

RPC timeout 的设置可以收敛为以下逻辑：先根据正常生产业务高峰下的 P99 加合理余量，确定单次调用的初始配置；再结合上游请求的剩余 deadline、本地与后续处理时间进行收缩；如果有重试，还要把多次尝试和退避放进同一份总预算中。

工程实现上，使用服务级默认 timeout 降低配置成本，用个性化 timeout 处理少数特殊 RPC；但无论配置如何覆盖，最终有效时间都不能超过上游 `context` 的剩余 deadline。上线后再根据延迟分布、超时率、错误率和业务体验持续校准。

## 延伸问题

### 整体 HTTP 接口的 1 秒 deadline 是怎么来的？

通常由用户体验目标、上游网关限制、接口 SLO 以及整条调用链的历史延迟共同决定，再将整体预算分配给各个处理阶段。1 秒只是示例，不是通用标准。

### timeout 与 retry 应该怎样配合？

先确定整段调用的总预算，再划分单次尝试、退避和安全余量。只重试幂等且可能恢复的错误，并限制次数，避免重试风暴。

### deadline 如何沿 gRPC 调用链传播？

上游把带 deadline 的 `context` 传给 gRPC 调用，gRPC 会将 deadline 传递给下游。下游继续复用该调用链的 `context`，就能让超时和取消信号逐层生效。

### 为什么不统一把 timeout 设置得长一些？

过长的 timeout 会让失败请求占用资源更久，延迟故障发现并加剧堆积。timeout 的目标不是尽量等待成功，而是在成功率、响应时间和故障隔离之间取得平衡。

### timeout 设置后还需要继续调整吗？

需要。流量、数据规模、依赖性能和调用链都会变化，应结合线上 P99、超时率和容量情况定期复核。
