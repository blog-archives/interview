## Kafka 是怎么保证消息消费的有序性的？

Kafka **只保证单分区内有序**，不保证跨分区全局有序。

怎么做：

1. **生产端**：同一业务键（如 orderId）发到同一分区——自定义 `Partitioner`，或对 key 做 hash 分区
2. **分区内**：Broker 按追加顺序写入 log，offset 递增
3. **消费端**：单分区对应一个消费者线程（同 Consumer Group 内一个分区只被一个消费者消费），按 offset 顺序拉取处理

要全局有序：只能 **单分区**，吞吐会降。常见折中是「局部有序」（同一用户/订单有序即可）。

口述：有序靠「同 key 进同分区 + 分区内单线程消费」；全局有序就单分区。

## 幂等机制怎么做，避免重复消费？

Kafka at-least-once 下，重试 / rebalance 可能导致重复投递，所以消费侧要幂等。

常见做法：

1. **唯一业务 ID 去重**：消息带 `bizId`，落库前查「是否已处理」；用 DB 唯一索引 / Redis `SETNX` 记录已消费 ID
2. **状态机 / 版本号**：只允许合法状态流转（如「未支付 → 已支付」），重复请求直接忽略
3. **天然幂等写**：`UPDATE ... SET`、按主键覆盖写，重复执行结果一样
4. **Kafka 自身**：生产端开 `enable.idempotence=true` 防 Producer 重试导致重复写入；Exactly-once 还要事务 + 消费侧配合，业务上仍常做幂等兜底

口述：以业务唯一键做去重表或唯一约束，处理前判断「做过就跳过」；别只靠 Kafka 配置。
