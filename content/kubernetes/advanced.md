## 什么时候选择 Kubernetes，什么时候不值得引入？

当系统需要在多节点上统一管理较多工作负载，并持续获得自动调度、故障恢复、服务发现、滚动发布、弹性、资源隔离和标准化交付能力时，Kubernetes 的收益会逐渐显现。

如果服务少、流量稳定、部署简单，Docker Compose、虚拟机脚本或托管应用平台已经足够，引入 Kubernetes 可能只是把业务复杂度换成集群、网络、存储、权限、可观测性和升级复杂度。

决策时评估：业务规模和增长、发布频率、SLO、隔离与合规、现有平台痛点、团队能力、托管服务可用性，以及迁移和长期运维成本。托管 Kubernetes 主要降低控制面维护成本，不会消除应用改造和数据面问题。

### 延伸问题

1. 微服务多就一定需要 Kubernetes 吗？

> 不一定。服务数只是信号，还要看部署频率、故障恢复、弹性和组织协作需求。复杂度没有达到阈值时，更简单的平台可能有更低总成本。

2. 单节点可以运行 Kubernetes 吗？

> 可以用于学习、边缘或特定统一交付场景，但单节点无法提供真正的节点级高可用，生产收益要单独论证。

3. 最容易低估的成本是什么？

> 平台升级、CNI / CSI、证书与权限、监控告警、容量、灾备和跨团队故障排查，往往比“把 YAML 跑起来”更难。

## 如何设计一个适合运行在 Kubernetes 的 Go HTTP 服务？

核心目标是让实例可替换、可观察、可安全终止：

1. **无状态**：会话和持久数据放到外部系统，本地缓存可丢失并能重建；
2. **配置外置**：从环境或文件读取 ConfigMap / Secret，不把环境差异写入镜像；
3. **健康语义清晰**：Startup、Readiness、Liveness 分工明确，接口低成本；
4. **优雅终止**：处理 SIGTERM，停止接流、完成在途请求和消费确认；
5. **超时与韧性**：所有外部调用有超时，重试有上限、退避和幂等，并提供限流与降级；
6. **可观测**：结构化日志输出到 stdout / stderr，暴露指标，传播 trace ID；
7. **资源可预测**：经过压测设置 requests / limits，控制 goroutine、连接池和内存峰值；
8. **安全**：非 root、只读根文件系统、最小 Linux capabilities 与最小 ServiceAccount 权限，镜像保持精简并扫描漏洞。

### 延伸问题

1. 登录状态放 Pod 内存有什么问题？

> Pod 可随时替换且请求会到不同副本，内存会话导致扩缩容和故障切换不可靠。可使用外部会话存储，或在适用时采用可验证 Token。

2. 为什么日志输出到标准输出？

> 便于容器运行时接管并由节点级采集器统一收集；若只写容器可写层，本地日志会随 Pod 替换丢失并可能占满节点磁盘。

3. 无状态是否意味着没有任何本地数据？

> 不是。允许临时缓存和工作文件，但它们必须可丢失、可重建，不能成为正确性或故障恢复的唯一依据。

## 如何部署“API + Redis + MySQL”？

一种合理的对象划分是：

- API：Deployment + ClusterIP Service；外部 HTTP 流量通过 Gateway / Ingress；
- Redis / MySQL：若必须自建，使用 StatefulSet、用于访问或成员发现的 Service、每副本 PVC，并配合成熟 Operator；
- 普通配置放 ConfigMap，凭证放 Secret 或外部密钥系统；
- API 使用 Service DNS 访问依赖，并通过超时、退避重试和 Readiness 处理依赖暂不可用。

生产中通常优先评估托管 MySQL / Redis。简单 StatefulSet 只解决 Pod 身份和挂载，不提供数据库复制、选主、备份、恢复、升级和一致性。Redis / MySQL 也不能像无状态 API 一样仅靠增加 `replicas` 完成安全扩容。

### 延伸问题

1. API 是否要等数据库启动后再创建？

> Kubernetes 不应被当成跨服务严格启动顺序编排器。API 要能容忍依赖暂时不可用，通过连接重试、超时和 readiness 控制接流。

2. 删除数据库 Pod 后数据一定安全吗？

> PVC 能让替代 Pod 重新挂载卷，但不等于数据一致、没有双写或已有备份。仍需数据库恢复机制、fencing、快照 / 备份和演练。

3. 有状态服务什么时候适合自建？

> 团队具备相应数据库和 Kubernetes 运维能力、托管服务不满足成本或合规要求，并且有成熟 Operator、备份恢复和故障演练体系时才更合理。

## 如何防止服务访问不该访问的目标？

使用 NetworkPolicy 在 L3 / L4 层限制选中 Pod 的 Ingress 和 Egress。策略是**可叠加的允许列表**：某方向一旦被策略选中而隔离，只有任一适用策略允许的流量才放行；它不是按规则顺序执行的防火墙。

生产实践通常先为 Namespace 建立默认拒绝，再按最小权限放行 DNS、必需服务、监控和外部出口。NetworkPolicy 是否真正生效取决于 CNI / 网络实现支持；它不能替代应用层认证、TLS、授权和 RBAC。

### 延伸问题

1. NetworkPolicy 控制 Service 还是 Pod？

> 它通过 Pod / Namespace selector 和 IP / 端口描述允许的 Pod 网络流量，不是直接给 Service 名称配置权限。Service 转换前后的地址语义还可能受实现影响。

2. Ingress 和 Egress 分别是什么？

> Ingress 是进入被选中 Pod 的流量，Egress 是从被选中 Pod 发出的流量。要建立双向通信，源端 Egress 和目标端 Ingress 都必须允许。

3. 默认拒绝 Egress 后最常漏掉什么？

> DNS。应用可能表现为所有域名访问失败，因此要显式允许到集群 DNS 的必要 UDP / TCP 端口，并结合实际 DNS 部署选择目标。

4. NetworkPolicy 与 RBAC 有什么区别？

> NetworkPolicy 控制网络连通性；RBAC 控制主体对 Kubernetes API 资源可执行的动作。能连上 API Server 不代表有权限，反之有 API 权限也不代表业务网络一定可达。

## 如何实现灰度或金丝雀发布？

先让稳定版和新版本同时存在，再用网关、Ingress Controller、Service Mesh 或发布平台按权重或规则分流：

- 金丝雀通常按 1%、5%、20% 等流量比例逐步扩大；
- 灰度可按用户、租户、地区、Cookie 或请求头选择人群；
- 新旧版本通常各有独立 Deployment 和 Service，流量层把它们当成两个后端；
- 每一步都设置观察窗口和自动 / 人工判定门槛，异常时把新版本权重降为 0。

发布期间不仅看 Pod Ready，还要比较新旧版本的错误率、延迟、饱和度、资源使用和核心业务指标，并考虑数据库 schema、消息格式和缓存数据的前后兼容。

### 延伸问题

1. 调整新旧 Pod 数量能精确控制流量比例吗？

> 不能。即使共用一个 Service，也只可能得到受连接和实现影响的大致比例；不同 Service 之间更不会因副本数自动分流。精确权重应由支持该能力的流量层完成。

2. 如何保证同一用户稳定进入同一版本？

> 使用用户 ID、Cookie、Header 等一致路由键；同时考虑未登录用户、缓存键、后台任务和跨服务调用是否仍会混用版本。

3. 回滚只是把镜像改回去吗？

> 不一定。若新版本已写入不兼容数据或执行破坏性 schema 变更，代码回滚也可能失败。发布设计应采用向前 / 向后兼容的数据变更并准备恢复方案。

## 如何建立日志、指标和链路追踪？

三类信号回答不同问题：日志记录离散事件，指标描述可聚合趋势和告警，Trace 展示一次请求跨服务的路径与耗时。三者应通过 service、namespace、pod、version、request ID / trace ID 等上下文关联。

典型链路：

- 日志：应用输出结构化日志到 stdout / stderr，Fluent Bit 等 DaemonSet 采集，发送到 Loki 或 Elasticsearch，再由 Grafana / Kibana 查询；
- 指标：应用暴露 Prometheus 指标，监控系统采集并围绕延迟、流量、错误、饱和度和业务指标告警；
- Trace：使用 OpenTelemetry SDK / Collector 采样和导出，串联入口、服务调用、数据库和消息队列。

还要监控观测系统本身：日志丢弃、采集延迟、指标基数、Trace 采样、存储容量和告警投递。高基数标签、敏感信息和无限日志量都是常见事故源。

### 延伸问题

1. 为什么日志采集器常用 DaemonSet？

> 每个节点运行一个 Agent，读取本节点容器日志并补充 Kubernetes 元数据，避免每个业务 Pod 都部署一套独立采集器。

2. Prometheus 和 Loki 有什么区别？

> Prometheus 主要处理数值时间序列指标；Loki 主要存储和查询日志。Grafana 可以同时展示两者并关联 Trace。

3. 所有请求都应该全量 Trace 吗？

> 不一定。高流量系统通常采用头部或尾部采样，并对错误、慢请求和关键业务提高采样率，在排障价值、成本和隐私之间权衡。

## 生产环境哪些配置最容易引发事故？

高风险点通常集中在以下几类：

| 类别 | 典型风险 | 防护思路 |
|---|---|---|
| 资源 | request 过大导致 Pending，limit 过小导致节流或 OOM | 压测、监控、配额和分阶段调整 |
| 探针 | 过严造成重启风暴，过松让坏实例接流 | 语义分离、合理阈值、故障演练 |
| 发布 | `maxUnavailable` 过大、不可变性差、缺少回滚门槛 | 灰度、digest、发布检查和兼容变更 |
| 网络 | selector / 端口错误、默认全通、策略误封 DNS | EndpointSlice 检查、最小权限和预发布验证 |
| 存储 | `Delete` 回收策略、误删 PVC、无备份 | Retain 评审、备份恢复演练、删除保护 |
| 可用性 | 副本集中、没有备用容量、误解 PDB | 跨拓扑分布、容量冗余和灾难演练 |
| 权限与密钥 | 过宽 RBAC、Secret 入库、特权容器 | 最小权限、加密、审计和 Pod 安全策略 |

关键配置应通过代码评审、策略即代码、预发布验证和渐进式发布控制风险。最重要的不是“从不出错”，而是能尽早发现、限制爆炸半径并快速恢复。
