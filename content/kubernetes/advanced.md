## 什么时候你会选择 K8s，什么时候认为它不值得引入？

当服务数量、实例数量和节点规模增加，并且需要自动调度、扩缩容、故障恢复、滚动发布和统一管理时，可以考虑使用 K8s。
如果系统规模较小、部署简单、流量稳定，单机或少量服务器配合 Docker Compose 就能满足需求，那么引入 K8s 反而会增加学习和运维成本，不一定值得。
本质上不是看有没有多台机器，而是看现有部署方式是否已经难以控制，以及团队有没有维护 K8s 的能力。

### 延伸问题

1. 服务数量多，就一定需要 K8s 吗？

> 不一定。服务数量只是参考，还要看部署频率、扩缩容、故障恢复需求，以及现有运维方式是否已经难以管理。

2. 只有一台服务器，可以使用 K8s 吗？

> 技术上可以，但通常收益有限。除非用于学习、测试或统一环境，否则 Docker Compose 往往更简单。

3. 引入 K8s 的主要成本是什么？

> 主要包括学习成本、集群维护、监控告警、网络与存储管理，以及故障排查复杂度。

4. Docker Compose 和 K8s 应该怎么选择？

> Compose 更适合规模较小、部署简单的系统；K8s 更适合多节点、需要自动扩缩容和故障恢复的复杂系统。

5. 使用云厂商托管 K8s，就一定值得引入吗？

> 不一定。托管服务降低了控制面的维护成本，但应用改造、资源配置、网络、存储和故障排查仍然存在复杂度。

## 你如何设计一个 Go HTTP 服务，使它更适合运行在 K8s？

我会尽量把 Go HTTP 服务设计成无状态服务，把配置和敏感信息放到 ConfigMap、Secret 或外部配置中心，状态数据放到数据库或缓存中。
服务需要提供 Startup、Readiness 和 Liveness 健康检查接口，并正确处理 SIGTERM，实现优雅退出。
同时输出结构化日志和监控指标，合理设置超时、资源 requests 和 limits，使它能够被安全扩缩容和排查故障。

> 无状态、配置外置、健康检查、优雅退出、可观测性。

### 延伸问题

1. 为什么 Go 服务最好设计成无状态？

> 无状态服务可以任意扩容、缩容或替换 Pod，请求转发到任何一个实例都能正常处理。

2. 用户登录状态应该保存在哪里？

> 不要只保存在 Pod 内存中，通常放在 Redis、数据库中，或者使用可验证的 Token。

3. Readiness 和 Liveness 接口有什么区别？

> Readiness 判断是否可以接收流量，Liveness 判断进程是否需要重启，两者不能简单混用。

4. Go 服务收到 SIGTERM 后应该怎么处理？

> 停止接收新请求，等待正在处理的请求完成，关闭数据库连接等资源，然后主动退出。

5. 为什么不能只依赖本地日志文件？

> Pod 随时可能被替换，本地日志可能丢失，因此通常输出到标准输出，再由日志系统统一采集。

## 如果要在 K8s 中部署一个“API 服务 + Redis + MySQL”的系统，你会如何划分资源对象？

API 服务是无状态的，我会使用 Deployment 管理多个副本，通过 ClusterIP Service 提供集群内访问；如果需要对外暴露，再配置 Ingress。

Redis 和 MySQL 是有状态服务，通常使用 StatefulSet、Service 和 PVC，分别保证稳定身份、网络访问和数据持久化。

普通配置放 ConfigMap，密码等敏感信息放 Secret。生产环境中，我会优先考虑云数据库或成熟的 Operator，而不是自己用简单的 StatefulSet 搭建高可用 Redis 和 MySQL。

### 延伸问题

1. Redis 和 MySQL 为什么更适合使用 StatefulSet？

> 因为它们需要稳定的实例身份和持久化存储，而 StatefulSet 能为每个 Pod 提供稳定名称并绑定独立 PVC。

2. API 服务如何访问 Redis 和 MySQL？

> 分别通过 Redis 和 MySQL 的 Service DNS 名称访问，不应该直接依赖 Pod IP。

3. API 是否应该等待 Redis 和 MySQL 启动后再创建？

> K8s 通常不保证严格启动顺序。API 应该通过连接重试、超时和 Readiness Probe 处理依赖暂时不可用。

4. 删除 Redis 或 MySQL 的 Pod，数据会丢失吗？

> 如果数据保存在 PVC 中，Pod 被替换后通常可以重新挂载原来的存储；如果只写在容器文件系统中，数据就可能丢失。

5. Redis 和 MySQL 可以像 API 一样直接增加副本吗？

> 不可以简单扩容。它们涉及数据复制、一致性和主从选举，通常需要数据库自身的集群方案、成熟的 Operator 或托管服务。

## 如何防止某个服务访问它本不该访问的其他服务？

可以使用 NetworkPolicy 限制服务之间的网络访问。它类似于 Pod 之间的防火墙，通过标签选择需要保护的 Pod，然后规定哪些 Pod 或命名空间可以通过哪些端口访问它。实际使用时通常先默认拒绝，再按照最小权限原则放行必要流量。

### 延伸问题

1. NetworkPolicy 控制的是 Service 还是 Pod？

> 它通过标签选择并控制 Pod 的网络流量，不是直接给 Service 设置访问权限。

2. Ingress 和 Egress 分别控制什么？

> Ingress 控制进入 Pod 的流量，Egress 控制 Pod 主动访问外部目标的流量。

3. 创建一条允许规则后，其他流量会自动被拒绝吗？

> 对被策略选中的 Pod 和对应流量方向来说，未被允许的流量会被拒绝；实践中通常显式配置默认拒绝规则，避免遗漏。

4. 配置了 NetworkPolicy 为什么可能没有效果？

> 可能是集群使用的 CNI 网络插件不支持 NetworkPolicy，或者标签、命名空间和端口选择错误。

5. NetworkPolicy 和 RBAC 有什么区别？

> NetworkPolicy 控制 Pod 之间的网络连通性；RBAC 控制用户或服务账号对 Kubernetes API 资源的操作权限。

## 你会怎样给线上服务建立可观测性：日志、指标、链路追踪？

Go 服务负责生成结构化日志，并输出到 stdout 和 stderr，不直接写容器内的日志文件。容器运行时会捕获这些输出，为每个容器写入工作节点上独立的日志文件，kubelet 负责日志轮转和清理。
Fluent Bit 等日志采集器通常以 DaemonSet 运行在每个节点上，读取本节点的容器日志，并补充 Pod、命名空间等信息，然后发送到 Loki 或 Elasticsearch 集中存储。最后通过 Grafana 或 Kibana 进行查询、展示和告警。
为了避免节点磁盘被写满，还需要控制业务日志量、配置日志轮转，并监控日志采集和节点磁盘状态。

可以把它们分成三类：采集、存储查询、展示。

- Fluent Bit：日志采集器。它通常运行在每个工作节点上，读取所有容器的日志，补充 Pod、Namespace 等信息，再转发到后端日志系统。它比较轻量，主要负责“收集和运输”。

- Loki：日志存储和查询系统。它接收 Fluent Bit 发送的日志，按照 Pod、服务名、Namespace 等标签组织数据。通常和 Grafana 配合，特点是比较轻量，适合 Kubernetes 日志。

- Elasticsearch：通用的分布式搜索和数据存储系统。它能够对日志内容建立索引，全文搜索能力很强，但资源消耗和维护复杂度通常比 Loki 高。

- Grafana：可视化和告警平台。它可以连接 Loki、Prometheus、Elasticsearch 等多个数据源，用来查询日志、展示指标图表和配置告警。

- Kibana：主要面向 Elasticsearch 的日志查询和可视化界面。可以搜索日志、查看字段、制作图表和仪表盘。

两套常见组合：

> Fluent Bit → Loki → Grafana：相对轻量，适合 Kubernetes 日志。

> Fluent Bit → Elasticsearch → Kibana：搜索能力较强，但系统相对更重。

最简单的记忆方式：

> Fluent Bit 负责采集，Loki 或 Elasticsearch 负责存储和查询，Grafana 或 Kibana 负责展示。

### 延伸问题

1. 日志、指标和链路追踪有什么区别？

> 日志记录具体事件，指标反映系统整体状态，链路追踪展示一次请求经过了哪些服务以及每一步的耗时。

2. 为什么容器日志通常输出到 stdout？

> 这样容器运行时可以统一接管日志，节点级采集器也能集中收集，不需要业务服务自行管理日志文件。

3. 为什么日志采集器通常使用 DaemonSet？

> 因为 DaemonSet 可以在每个工作节点运行一个采集器，统一读取该节点上所有容器的日志。

4. Prometheus 和 Loki 分别负责什么？

> Prometheus 主要采集和存储数值指标，Loki 主要存储和查询日志，两者都可以通过 Grafana 展示。

5. 如何把一次请求的日志和调用链关联起来？

> 为请求生成统一的 request ID 或 trace ID，并让它在服务之间传递，同时记录到日志和链路数据中。

## 生产环境中，哪些 K8s 配置最容易引发事故？

生产环境最容易引发事故的配置，主要包括资源限制、健康检查、服务路由、发布策略和存储配置。

比如 requests 设置过大可能导致 Pod 无法调度，内存 limit 过小会导致 OOM；探针配置错误可能造成流量过早进入或容器反复重启；Service selector、端口配置错误会直接导致服务不可访问。
此外，滚动更新参数不合理可能造成容量不足，PVC 回收策略配置错误可能导致数据丢失。因此关键配置应该经过评审，并通过灰度发布和监控验证。

### 延伸问题

1. requests 设置得过大会有什么影响？

> Pod 可能找不到满足资源要求的节点，长期处于 Pending 状态。

2. 内存 limit 设置得过小会发生什么？

> 容器超过限制后可能被 OOM Kill，如果持续发生，就可能进入 CrashLoopBackOff。

3. Readiness Probe 配置错误有什么影响？

> Pod 可能一直无法加入 Service 后端，或者尚未准备好就开始接收流量。

4. Service selector 配置错误会发生什么？

> Service 无法匹配正确的 Pod，EndpointSlice 中没有可用后端，最终导致访问失败。

5. 滚动更新中的 `maxUnavailable` 设置过大有什么风险？

> 更新过程中可能同时停止过多旧 Pod，导致可用容量不足，严重时会造成服务中断。
