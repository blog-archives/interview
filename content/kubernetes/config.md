## ConfigMap 和 Secret 有什么区别？Pod 如何使用它们？

ConfigMap 保存非敏感配置，Secret 保存密码、Token、证书等敏感数据。两者都能把配置与镜像解耦，常见注入方式是：

- 作为单个环境变量或 `envFrom` 注入；
- 以 Volume 文件挂载；
- 由程序通过 Kubernetes API 读取，但这会增加权限和耦合，通常不是首选。

Secret 在 API 清单中的 `data` 字段使用 Base64 表示，这只是编码，不是加密。Secret 与 ConfigMap 都属于 Namespace，Pod 通常只能直接引用同 Namespace 的对象。

### 延伸问题

1. 为什么不把配置写入镜像？

> 配置与镜像分离后，同一镜像可用于不同环境，修改配置也不必重建镜像，更便于职责分离和发布审计。

2. 环境变量和文件挂载怎么选？

> 少量、启动时读取且无需热更新的配置适合环境变量；需要保持文件格式、证书轮换或支持重载的配置适合 Volume。敏感信息无论使用哪种方式都有泄露面，需要最小权限和日志脱敏。

3. ConfigMap / Secret 不存在时 Pod 会怎样？

> 非 optional 的引用缺失时，容器通常无法正常创建或启动，Events 会显示配置相关错误；设置为 optional 后，应用必须能处理缺省值。

## 修改 ConfigMap 或 Secret 后，运行中的 Pod 会自动生效吗？

要区分“容器内数据是否更新”和“应用是否使用新值”：

- **环境变量**：运行中进程的环境不会改变，需要替换 Pod；
- **Volume 挂载**：kubelet 会以最终一致的方式逐步更新投射文件，但不是瞬时更新；
- **`subPath` 挂载**：不会收到 ConfigMap / Secret 的自动文件更新；
- **应用层**：即使文件已更新，程序仍需监听、定期重读或收到重载信号，否则业务配置不生效。

生产中常把配置内容的哈希写入 Pod 模板注解，让配置变化触发 Deployment 滚动更新；也可以使用专门的 reloader，但要控制发布节奏和错误配置的影响面。

### 延伸问题

1. 修改 ConfigMap 会自动重启 Deployment 吗？

> 默认不会。Deployment 的 Pod 模板没有变化时，不会仅因它引用的 ConfigMap 改变就自动滚动重启。

2. 为什么文件挂载更新不是立即发生？

> kubelet 按同步周期和缓存策略更新投射卷，因此存在传播延迟。强实时配置更适合专门的配置分发机制，应用也要定义一致性和失败策略。

3. 不可变 ConfigMap / Secret 有什么作用？

> 设置 `immutable: true` 可以防止误改，也能减少 kubelet watch 压力；要变更时创建新对象并更新引用。不可变字段不能再改回可变，只能删除重建对象。

## Secret 天然安全吗？生产环境如何保护？

Secret 只是把敏感数据与普通配置区分管理，并不等于端到端安全。默认的 Base64 表示可直接还原；若集群未配置静态加密，Secret 在 etcd 中也可能以未加密形式保存。

生产环境至少应做到：

1. 使用 RBAC 最小化用户和 ServiceAccount 的 `get`、`list`、`watch` 权限；
2. 为 Secret 配置 etcd 静态加密，并保护 etcd 备份和加密密钥；
3. 不把明文或仅 Base64 编码的 Secret 提交到 Git；使用外部密钥管理、加密清单或安全注入流程；
4. 限制容器权限，避免不必要地挂载 Secret，禁止在日志、错误信息和诊断包中输出；
5. 建立轮换、吊销、审计和泄露响应流程。

### 延伸问题

1. RBAC 能解决 Secret 的所有安全问题吗？

> 不能。RBAC 保护 Kubernetes API 访问，但拿到节点、容器、etcd 备份或应用日志的攻击者仍可能接触 Secret，需要分层防护。

2. 用文件挂载一定比环境变量安全吗？

> 不能绝对化。环境变量可能进入进程诊断或错误日志，文件也可能被容器内进程读取。文件挂载便于轮换和权限控制，但最终要看威胁模型、容器权限与应用实现。

3. Base64 的目的是什么？

> 主要是让二进制数据能安全地放入 JSON / YAML 字段中，不提供保密性。
