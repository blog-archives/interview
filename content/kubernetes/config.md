
## ConfigMap 和 Secret 有什么区别？

ConfigMap 和 Secret 都是用来保存配置、把配置和镜像分离的资源对象。ConfigMap 保存服务地址、功能开关等普通配置；Secret 保存密码、Token、证书等敏感数据。Secret 中的数据通常使用 Base64 编码，但这不是加密，它的安全性主要依赖 RBAC 权限控制、etcd 加密等额外措施。

### 延伸问题

1. 为什么不把配置直接写进镜像？

> 如果配置写进镜像，每次修改配置都要重新构建和发布镜像。使用 ConfigMap 或 Secret，可以让同一个镜像适应不同环境，也能实现配置与应用代码分离。

2. Pod 如何使用 ConfigMap 和 Secret？

> 常见方式有两种：作为环境变量注入容器，或者作为文件挂载到容器中。应用再通过读取环境变量或配置文件获取数据。

3. 修改 ConfigMap 或 Secret 后，Pod 会自动重启吗？

> 默认不会。以环境变量注入的配置不会自动更新；以文件挂载时，文件内容通常可以逐渐更新，但应用是否重新加载，还要看应用本身。因此生产中经常通过滚动重启让新配置生效。

4. Secret 使用 Base64 编码，能防止数据泄露吗？

> 不能。Base64 只是编码，不是加密，可以轻易还原。Secret 的安全性需要依赖 RBAC 权限控制、etcd 静态加密以及避免日志泄露等措施。

5. ConfigMap 和 Secret 可以跨命名空间使用吗？

> 通常不可以。Pod 只能直接引用同一命名空间中的 ConfigMap 和 Secret；不同命名空间需要分别创建和管理。

## Go 服务如何从 ConfigMap / Secret 读取配置？

Go 服务读取 ConfigMap 和 Secret，常见有两种方式。第一种是把配置注入为环境变量，Go 程序通过读取环境变量获取；第二种是把配置挂载成文件，Go 程序读取对应的配置文件。普通且简单的配置适合环境变量，配置项较多、需要保持文件格式或者希望支持动态加载时，更适合文件挂载。

需要注意配置更新的区别：
- 环境变量：Pod 运行后不会自动变化，一般需要重新创建或滚动重启 Pod。
- 文件挂载：挂载内容通常会逐渐更新，但 Go 服务是否采用新配置，取决于它有没有监听或定期重新读取文件。
所以，不是 ConfigMap 和 Secret 主动把配置发送给 Go 服务，而是它们被注入容器后，由 Go 服务读取。

## Secret 是否天然安全？还需要注意哪些问题？

Secret 并不天然安全。它的数据默认通常只是 Base64 编码，并不是加密，拿到数据后可以轻易还原成明文。它的安全性主要依赖 RBAC 权限控制、etcd 静态加密以及规范的使用方式。使用时应该遵循最小权限原则，限制能够读取 Secret 的用户和服务账号，同时避免把 Secret 写进代码仓库、配置清单或应用日志。

### 延伸问题

1. 为什么 Secret 使用 Base64 编码，而不直接保存明文？

> Base64 主要是为了让文本和证书等二进制数据能够使用统一格式传输，并不是为了安全。任何拿到数据的人都可以轻易解码。

2. RBAC 如何保护 Secret？

> RBAC 可以限制哪些用户和 ServiceAccount 能读取、修改 Secret。生产环境应该遵循最小权限原则，只允许真正需要的应用访问指定 Secret。

3. 为什么还要开启 etcd 静态加密？

> K8s 的资源最终会保存到 etcd。如果没有开启静态加密，攻击者拿到 etcd 数据或备份后，可能直接读取 Secret；开启后可以降低底层数据泄露的风险。

4. Secret 使用环境变量和文件挂载，哪种更安全？

> 两种方式都有泄露风险。环境变量可能被调试工具或错误日志暴露；文件挂载可以控制文件权限，也更容易更新。实际选择要结合应用方式，但都必须限制容器和 Pod 的访问权限。

5. Secret 可以直接提交到 Git 仓库吗？

> 不应该。即使 YAML 中保存的是 Base64 内容，也可以轻易还原。通常应该使用外部密钥管理系统、密封 Secret，或者在部署过程中安全地注入。

## 配置更新后，运行中的 Pod 会自动感知吗？

通过环境变量注入的配置不会自动更新；通过 Volume 挂载的配置文件通常会被同步更新，但最终能否生效，还取决于应用是否支持动态加载。
