磁盘问题通常分为三类：文件系统容量耗尽、inode 耗尽，以及磁盘 I/O 变慢。本篇重点整理容量和文件占用排查中最常用的 `df`、`du`、`lsof` 和 `lsblk`。

## df：查看文件系统使用情况

| 命令 | 作用 |
|---|---|
| `df -h` | 以易读单位查看各文件系统容量 |
| `df -i` | 查看 inode 使用情况 |
| `df -h /var/log` | 查看指定路径所在的文件系统 |
| `df -T` | 同时显示文件系统类型 |

典型输出：

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/vda1        50G   46G  1.5G  97% /
```

| 字段 | 含义 |
|---|---|
| `Filesystem` | 文件系统或设备 |
| `Size` | 总容量 |
| `Used` | 已使用容量 |
| `Avail` | 普通用户通常还可使用的容量 |
| `Use%` | 使用比例 |
| `Mounted on` | 挂载点 |

排查具体路径时，最好直接运行 `df -h <路径>`，因为 `/var`、`/data` 等目录可能位于不同挂载点。

### 容量还有剩余，为什么仍然无法创建文件？

可能是 inode 已经耗尽。文件内容占用数据块，每个文件和目录还需要 inode 保存元数据。大量小文件可能在磁盘容量尚未耗尽时先用完 inode。

```shell
df -i
```

如果 `IUse%` 达到 100%，应定位产生海量小文件的目录和程序，而不是只清理少量大文件。

## du：定位大目录和大文件

| 命令 | 作用 |
|---|---|
| `du -sh /var/log` | 查看一个目录的总占用 |
| `du -h --max-depth=1 /var` | 查看 `/var` 下一级目录的占用 |
| `du -xhd 1 /var` | 限制在同一文件系统并查看一级目录 |
| `du -ah /var/log` | 同时统计文件与目录 |

从挂载点开始逐层缩小范围：

```shell
du -xhd 1 /var | sort -h
du -xhd 1 /var/log | sort -h
find /var/log -xdev -type f -size +500M -ls
```

在超大目录上执行 `du` 会遍历大量目录项，本身可能造成明显 I/O。生产环境应先从最可能的目录开始，并避开业务高峰。

### `df` 和 `du` 有什么区别？

`df` 从文件系统角度统计整个挂载点的数据块；`du` 遍历当前可见的目录树，累计文件占用。磁盘满时先用 `df` 找到具体文件系统，再用 `du` 定位其中的大目录。

## lsof：查看进程打开的文件

`lsof` 的含义是 list open files。Linux 将普通文件、目录、设备、管道和网络 Socket 等都抽象成文件，因此它也可以用来排查端口和网络连接。

| 命令 | 作用 |
|---|---|
| `lsof /var/log/app.log` | 查看哪些进程打开了指定文件 |
| `lsof +L1` | 查看链接数小于 1、已删除但仍被打开的文件 |
| `lsof -p 1234` | 查看指定进程打开的文件 |
| `lsof -i :8080` | 查看使用 8080 端口的进程 |

### 为什么删除文件后空间没有释放？

`rm` 删除的是文件名与 inode 的关联。如果进程仍持有打开的文件描述符，数据块要等最后一个描述符关闭后才会释放。此时 `du` 已经看不到文件，`df` 却仍把空间计为已使用。

```shell
lsof +L1
```

输出中如果文件名带有 `(deleted)`，并且 `SIZE/OFF` 很大，就要确认对应进程是否仍在写入。处理方式通常是让程序重新打开日志，或者在确认业务影响后安全重启服务。不要只为了释放空间就直接 `kill -9`。

## lsblk：查看块设备和挂载关系

| 命令 | 作用 |
|---|---|
| `lsblk` | 查看磁盘、分区和挂载点 |
| `lsblk -f` | 同时查看文件系统类型、UUID 和挂载点 |
| `lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINTS` | 只显示关注的字段 |

`lsblk` 适合确认系统有哪些磁盘、分区和挂载点，但它不负责统计目录占用了多少空间。

## 磁盘满的排查顺序

1. 用 `df -h` 确认哪个文件系统容量不足；
2. 用 `df -i` 判断是否为 inode 耗尽；
3. 从对应挂载点开始，用 `du -xhd 1` 逐层定位；
4. 用 `find` 找异常大文件或异常多的小文件；
5. 如果 `df` 与 `du` 差异很大，用 `lsof +L1` 检查已删除文件；
6. 确认文件用途和业务影响后再清理、轮转、归档或扩容；
7. 处理后重新执行 `df`，并观察文件是否继续快速增长。

## 常见场景

> 日志文件非常大，可以直接 `rm` 吗？

先确认日志是否仍被服务写入、是否有审计和保留要求，以及是否配置了轮转。直接删除正在写入的日志可能无法释放空间，还会让服务继续写入不可见文件。更稳妥的做法是使用正确的日志轮转机制，并通知服务重新打开日志文件。

> `du` 找不到大文件，但 `df` 显示磁盘已满，除了已删除文件还有什么原因？

还可能是权限不足导致 `du` 无法读取部分目录、挂载点下面的原有文件被新挂载覆盖、文件系统保留块和元数据占用，或者存储快照保留了数据。应结合挂载关系、权限和具体存储系统继续排查。

> 为什么不建议直接从 `/` 执行一次完整的 `du`？

它可能跨越多个挂载点，扫描伪文件系统、网络盘和大量业务文件，产生较重 I/O。先通过 `df` 找到目标挂载点，再使用 `du -x` 限制范围更安全。
