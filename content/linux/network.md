网络排查要把问题拆成几层：域名是否解析、目标 IP 是否可达、端口是否监听、TCP 是否能够建立连接，以及 HTTP/TLS/业务响应是否正常。单个命令通常只能验证其中一层。

## ip：查看地址和路由

| 命令 | 作用 |
|---|---|
| `ip addr` | 查看网卡和 IP 地址 |
| `ip -br addr` | 用简洁格式显示网卡和地址 |
| `ip link` | 查看网卡链路状态 |
| `ip route` | 查看路由表 |
| `ip route get 10.0.0.8` | 查看访问目标 IP 会选择的路由和源地址 |

当机器有多块网卡、多个 IP 或复杂路由时，`ip route get` 比只看完整路由表更容易确认一次访问实际会从哪里发出。

## ss：查看端口和连接

`ss` 是排查 Linux Socket 的常用工具，通常比旧的 `netstat` 更适合现代 Linux 系统。

| 命令 | 作用 |
|---|---|
| `ss -lntp` | 查看正在监听的 TCP 端口及进程 |
| `ss -lnup` | 查看正在监听的 UDP 端口及进程 |
| `ss -ant` | 查看全部 TCP 连接并禁用名称解析 |
| `ss -antp` | 查看 TCP 连接及进程信息 |
| `ss -s` | 查看 Socket 汇总统计 |
| `ss -lntp '( sport = :8080 )'` | 查看 8080 端口的 TCP 监听 |

选项可以这样记：`l` 是 listening，`n` 表示显示数字地址和端口，`t` 是 TCP，`u` 是 UDP，`p` 显示进程。查看其他用户的进程信息可能需要更高权限。

### 如何判断服务监听在哪里？

```text
LISTEN 0 4096 127.0.0.1:8080 0.0.0.0:* users:(("app",pid=1234,fd=8))
```

这里表示服务只绑定在本机回环地址 `127.0.0.1`，其他机器不能通过服务器网卡 IP 访问它。如果监听地址是 `0.0.0.0:8080`，通常表示监听所有本机 IPv4 地址，但外部能否访问还取决于防火墙、安全组、端口映射和网络策略。

### 常见 TCP 状态

| 状态 | 含义 |
|---|---|
| `LISTEN` | 服务正在等待新连接 |
| `ESTABLISHED` | TCP 连接已经建立 |
| `TIME-WAIT` | 主动关闭方等待延迟报文失效 |
| `CLOSE-WAIT` | 本机收到对端关闭，但应用还没有关闭 Socket |
| `SYN-SENT` | 已发出连接请求，正在等待响应 |
| `SYN-RECV` | 已收到连接请求，等待握手完成 |

一定数量的 `TIME-WAIT` 很正常；异常多时应检查短连接和连接池。大量 `CLOSE-WAIT` 长时间不消失，通常要检查应用是否遗漏了连接关闭逻辑或缺少超时。

查看指定状态可以使用：

```shell
ss -ant state time-wait
ss -ant state close-wait
```

## ping：验证 IP 层基本连通性

```shell
ping -c 4 10.0.0.8
```

`ping` 可以观察 ICMP 是否能往返以及大致延迟，但不能证明 TCP 端口或应用正常。很多服务器、防火墙和云网络会禁用 ICMP，所以 `ping` 不通也不能直接断定目标不可达。

## dig：检查 DNS

| 命令 | 作用 |
|---|---|
| `dig example.com` | 查询域名解析的完整信息 |
| `dig +short example.com` | 只显示简洁结果 |
| `dig @8.8.8.8 example.com` | 指定 DNS 服务器查询 |
| `dig example.com CNAME` | 查询指定记录类型 |

排查域名问题时，应注意解析出的 IP、记录类型、TTL 和使用的 DNS 服务器。DNS 成功只说明获得了解析结果，不代表目标端口和应用可用。

## nc：测试 TCP 或 UDP 端口

```shell
nc -vz 10.0.0.8 8080
```

`-v` 显示详细信息，`-z` 只扫描监听状态而不发送业务数据。`nc` 成功说明 TCP 建连基本正常，但不能证明 HTTP 路径、TLS、鉴权和业务逻辑正常。

不同发行版提供的 `nc` 实现和参数可能略有差异，可以先查看 `nc -h` 或 `man nc`。

## curl：验证 HTTP、HTTPS 和应用响应

| 命令 | 作用 |
|---|---|
| `curl -v URL` | 显示连接、请求和响应过程 |
| `curl -I URL` | 只请求响应头 |
| `curl -i URL` | 同时输出响应头和响应体 |
| `curl -sS URL` | 安静输出，但仍显示错误 |
| `curl --connect-timeout 3 URL` | 限制建立连接的等待时间 |
| `curl --max-time 10 URL` | 限制整个请求的最长时间 |

本机排查服务时，可以逐层测试：

```shell
curl -v http://127.0.0.1:8080/health
curl -v http://10.0.0.8:8080/health
curl -v https://service.example.com/health
```

第一步验证应用和回环监听，第二步验证网卡地址与主机网络，第三步验证 DNS、TLS、负载均衡或反向代理。请求时应保持协议、路径、Host 和鉴权条件一致，否则结果不能直接对比。

### 查看一次请求的分阶段耗时

```shell
curl -sS -o /dev/null \
  -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first_byte=%{time_starttransfer} total=%{time_total}\n' \
  https://example.com/health
```

这些时间是从请求开始累计的，可以用来判断延迟主要出现在 DNS、TCP 建连、TLS 握手、等待首字节还是响应传输阶段。

## 服务无法访问时的排查顺序

1. 用 `dig` 确认域名是否解析到预期地址；
2. 用 `ip route get <目标IP>` 确认本机路由和源地址；
3. 在服务端用 `ss -lntp` 确认端口、进程和绑定地址；
4. 用 `nc -vz` 验证 TCP 端口能否建立连接；
5. 用 `curl -v` 验证 HTTP、TLS 和应用返回；
6. 分别从服务本机、同网段客户端和外部入口测试，缩小故障范围；
7. 根据结果检查防火墙、安全组、代理、容器端口映射或网络策略。

## 常见现象

> `Connection refused` 通常说明什么？

通常表示请求已经到达目标主机，但对应端口没有服务监听，或者中间设备主动拒绝并立即返回。优先检查 IP、端口、服务状态和监听地址。

> 连接超时通常说明什么？

数据包或响应可能被防火墙静默丢弃、路由不可达、目标严重拥塞，或者服务虽然接收了连接却长时间不响应。应结合 `nc`、`curl -v` 的阶段和服务端连接状态继续判断。

> 本机访问成功，其他机器访问失败怎么办？

先检查服务是否只绑定 `127.0.0.1`，再检查主机防火墙、安全组、容器端口映射、Kubernetes Service、代理和跨主机路由。本机成功只能证明部分应用链路正常。

> 端口处于 `LISTEN`，为什么接口仍然失败？

监听只说明内核可以接受新连接。应用还可能卡死、健康检查失败、TLS 或请求路径错误、鉴权失败，或者数据库等下游依赖不可用，需要继续使用真实请求和日志验证。
