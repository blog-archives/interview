title: top 命令详解

`top` 用来实时观察系统负载、CPU、内存和进程资源占用。它适合快速发现异常进程，但一次刷新只是一张快照，判断问题时还要连续观察并结合日志和监控。

## 常用启动方式

| 命令 | 作用 |
|---|---|
| `top` | 查看整机和全部进程 |
| `top -p 1234` | 只观察指定进程 |
| `top -H -p 1234` | 展示指定进程中的线程 |
| `top -d 2` | 每 2 秒刷新一次 |
| `top -b -n 1` | 批处理模式输出一次，适合保存或脚本采集 |

## 一份典型输出

```text
top - 23:10:18 up 12 days, 4:32, 2 users, load average: 2.18, 3.14, 3.07
Tasks: 257 total, 3 running, 253 sleeping, 0 stopped, 1 zombie
%Cpu(s): 7.2 us, 7.5 sy, 0.0 ni, 84.6 id, 0.5 wa, 0.1 hi, 0.1 si, 0.0 st
MiB Mem : 15946.0 total, 86.0 free, 8410.0 used, 7450.0 buff/cache
MiB Swap: 2048.0 total, 1980.0 free, 68.0 used. 6740.0 avail Mem

    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
   1234 app       20   0    6.3g   1.8g  28000 S  85.3  11.6   125:33 java
```

## 第一行：运行时间和负载

| 字段 | 含义 |
|---|---|
| `23:10:18` | 当前系统时间 |
| `up 12 days, 4:32` | 系统已经连续运行的时间 |
| `2 users` | 当前登录会话数，不一定是不同用户数 |
| `2.18, 3.14, 3.07` | 最近 1、5、15 分钟的平均负载 |

Linux 的 load average 主要统计正在使用或等待 CPU 的可运行任务，以及处于不可中断睡眠状态的任务。它不是 CPU 使用率，需要结合逻辑 CPU 数量判断。

- 8 核机器持续 load 约为 3，通常仍有 CPU 余量；
- 2 核机器持续 load 约为 6，通常说明任务明显排队；
- load 很高但 CPU 很空闲，可能有大量任务卡在磁盘或网络存储 I/O。

1 分钟负载高于 5、15 分钟，说明压力可能刚刚上升；1 分钟负载低于后两者，说明压力可能正在回落。

查看逻辑 CPU 数量可以使用：

```shell
nproc
lscpu
```

## 第二行：任务状态

| 字段 | 含义 |
|---|---|
| `total` | 当前任务总数 |
| `running` | 正在运行或等待 CPU 的任务数 |
| `sleeping` | 等待事件、定时器、锁或 I/O 的任务数 |
| `stopped` | 被暂停的任务数 |
| `zombie` | 已退出但没有被父进程回收的子进程数 |

大量 `sleeping` 通常是正常现象。持续出现大量 `zombie` 时，应找到其父进程并检查子进程回收逻辑，直接对僵尸进程执行 `kill -9` 没有作用。

## 第三行：CPU 状态

| 字段 | 含义 | 数值较高时的排查方向 |
|---|---|---|
| `us` | 用户态程序使用的 CPU 时间 | 业务计算、死循环、序列化、GC |
| `sy` | 内核态使用的 CPU 时间 | 系统调用、网络处理、上下文切换 |
| `ni` | 调整过 nice 值的任务使用时间 | 低或高优先级任务占用 |
| `id` | CPU 空闲时间 | 越低说明 CPU 越忙 |
| `wa` | 等待 I/O 完成的时间 | 磁盘延迟、网络存储、I/O 堵塞 |
| `hi` | 处理硬中断的时间 | 硬件或网卡中断 |
| `si` | 处理软中断的时间 | 网络包处理等软中断工作 |
| `st` | 虚拟机被宿主机抢走的 CPU 时间 | 宿主机资源竞争 |

`wa` 高只能说明采样期间 CPU 经常因 I/O 无事可做，不能仅凭这一项认定磁盘故障，还要结合磁盘延迟、吞吐和 `D` 状态进程验证。

按 `1` 可以展开每个逻辑 CPU 的使用率。如果整机 CPU 不高但某个单线程应用很慢，应检查是否只有一个核心被打满。

## 第四、五行：内存和 Swap

| 字段 | 含义 |
|---|---|
| `total` | 物理内存或 Swap 总量 |
| `free` | 完全没有被使用的内存 |
| `used` | 已使用内存，计算口径可能随工具版本变化 |
| `buff/cache` | 缓冲区和文件页缓存等占用 |
| `avail Mem` | 估算可以提供给新应用且通常不需要明显换页的内存 |

Linux 会主动把暂时空闲的内存用于文件缓存，所以 `free` 很少不等于内存不足。通常更应该关注 `avail Mem`、Swap 换入换出、应用延迟和是否发生 OOM。

少量 Swap 已使用也不一定表示当前内存紧张：被换出的冷页面可能没有必要立即读回。如果系统持续换入换出且延迟明显升高，才说明可能发生内存抖动。可以结合下面的命令连续观察：

```shell
free -h
vmstat 1 5
```

## 进程列表

| 字段 | 含义 |
|---|---|
| `PID` | 进程编号 |
| `USER` | 进程所属用户 |
| `PR` | 调度优先级 |
| `NI` | nice 值 |
| `VIRT` | 进程可见的虚拟地址空间 |
| `RES` | 当前驻留在物理内存中的大小 |
| `SHR` | RES 中可能共享的部分 |
| `S` | 进程状态 |
| `%CPU` | 进程 CPU 使用率 |
| `%MEM` | 进程占物理内存的比例 |
| `TIME+` | 进程累计消耗的 CPU 时间 |
| `COMMAND` | 进程或命令名称 |

`VIRT` 很大不代表实际用了同样多的物理内存，判断物理内存占用时通常先看 `RES`。不过共享页面可能在多个进程中重复计算，需要精确归因时还应进一步查看 PSS。

常见进程状态包括：

| 状态 | 含义 |
|---|---|
| `R` | 正在运行或等待 CPU |
| `S` | 可中断睡眠，通常在等待事件 |
| `D` | 不可中断睡眠，常见于等待 I/O |
| `T` | 已停止或被调试器跟踪 |
| `Z` | 僵尸进程 |

进程显示为 `S`，并不代表它在采样周期内没有使用 CPU；它可能刚完成计算，此刻恰好在等待事件。

## 常用交互按键

| 按键 | 作用 |
|---|---|
| `P` | 按 CPU 使用率排序 |
| `M` | 按内存使用率排序 |
| `T` | 按累计 CPU 时间排序 |
| `1` | 展开或合并每个逻辑 CPU |
| `H` | 显示或隐藏线程 |
| `c` | 显示或隐藏完整命令行 |
| `k` | 向进程发送信号，应谨慎使用 |
| `q` | 退出 |

## CPU 高时的排查顺序

1. 观察 load、`us`、`sy`、`wa` 和每个 CPU 核心，确认异常类型；
2. 按 `P` 找到持续占用 CPU 的进程，不要只看一次刷新；
3. 按 `H` 或运行 `top -H -p <PID>` 找到高 CPU 线程；
4. 使用对应语言或运行时工具分析线程栈、GC 和热点代码；
5. 对照流量、发布、定时任务和错误日志确认原因；
6. 根据业务影响选择限流、降级、摘除实例或回滚，并在处理后持续观察。

## 内存高时的排查顺序

1. 先看 `avail Mem`、Swap 和变化趋势，判断是否真的存在内存压力；
2. 按 `M` 找到 RES 较大的进程；
3. 区分运行时堆、堆外内存、线程栈、文件映射和页缓存；
4. 通过内核日志确认是否发生过系统或 cgroup OOM；
5. 结合应用堆分析和多次快照判断是正常增长、缓存还是泄漏。

检查 OOM 记录可以使用：

```shell
journalctl -k | grep -i -E 'out of memory|oom|killed process'
dmesg | grep -i -E 'out of memory|oom|killed process'
```

## 常见误区

> `%CPU` 为什么可能超过 100%？

部分 `top` 配置以单个逻辑 CPU 为 100%，多线程进程同时使用多个核心时就可能超过 100%。按 `I` 可以切换某些版本的 Irix/Solaris CPU 统计模式。

> load 很高是否一定要增加 CPU？

不一定。先检查 CPU 是否真的繁忙，以及是否有大量 `D` 状态任务。如果根因是存储 I/O，单纯增加 CPU 通常没有帮助。

> 排在第一的进程就是故障根因吗？

不一定。它可能只是正常承载了最多流量，或者只在一次采样中短暂升高。需要观察趋势并结合业务指标、日志和变更记录验证。

> 可以直接在 `top` 中按 `k` 杀掉高占用进程吗？

不应直接操作。先核对 PID、用户、完整命令行、服务冗余和业务影响，优先使用服务管理器或向进程发送 `SIGTERM` 完成优雅退出，`SIGKILL` 只作为最后手段。
