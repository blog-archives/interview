## 第一行：系统基本状态

```text
top - 23:10:18 up 12 days, 4:32, 2 users, load average: 2.18, 3.14, 3.07
```

| 数字 | 含义 |
|---|---|
| `23:10:18` | 当前系统时间 |
| `up 12 days, 4:32` | 系统已经连续运行 12 天 4 小时 32 分钟 |
| `2 users` | 当前有两个登录会话，不一定是两个不同用户 |
| `2.18` | 最近 1 分钟平均负载 |
| `3.14` | 最近 5 分钟平均负载 |
| `3.07` | 最近 15 分钟平均负载 |

这里 1 分钟负载低于 5 分钟和 15 分钟负载，说明系统压力可能正在下降。

负载要结合 CPU 核数看。例如：

- 1 核机器持续 load 3：压力较大。
- 8 核机器 load 3：通常还有余量。

## 第二行：任务状态

```text
Tasks: 257 total, 3 running, 253 sleeping, 0 stopped, 1 zombie
```

| 数字 | 含义 |
|---|---|
| `257 total` | 当前共 257 个任务或进程 |
| `3 running` | 3 个正在运行或等待 CPU |
| `253 sleeping` | 253 个正在等待事件，例如请求、锁或 I/O |
| `0 stopped` | 没有被暂停的进程 |
| `1 zombie` | 有一个已退出但未被父进程回收的僵尸进程 |

大量 sleeping 通常很正常。这里需要关注的是那一个 zombie，找到它的父进程并检查回收逻辑。

## 第三行：CPU

```text
%Cpu(s): 7.2 us, 7.5 sy, 0.0 ni, 84.6 id, 0.5 wa, 0.1 hi, 0.1 si, 0.0 st
```

| 字段 | 数字含义 |
|---|---|
| `7.2 us` | 7.2% CPU 时间用于运行用户态程序 |
| `7.5 sy` | 7.5% 用于运行内核代码 |
| `0.0 ni` | 调整过 nice 优先级的进程占用 0% |
| `84.6 id` | CPU 有 84.6% 的时间处于空闲 |
| `0.5 wa` | 0.5% 的时间在等待 I/O |
| `0.1 hi` | 0.1% 用于处理硬中断 |
| `0.1 si` | 0.1% 用于处理软中断 |
| `0.0 st` | 虚拟机没有明显被宿主机抢走 CPU 时间 |

这组数据说明整机 CPU 很空闲，暂时不像 CPU 瓶颈。

## 第四行：物理内存

```text
MiB Mem : 15946 total, 86 free, 8410 used, 7450 buff/cache
```

| 数字 | 含义 |
|---|---|
| `15946 total` | 物理内存总量约 15.6 GiB |
| `86 free` | 完全没有被使用的内存只有 86 MiB |
| `8410 used` | 当前被进程和系统实际使用的内存 |
| `7450 buff/cache` | 用作磁盘缓冲和文件页缓存的内存 |

`free` 很少不代表内存一定不够。Linux 会主动用空闲内存做缓存，需要时可以回收，所以还要看后面的 `avail Mem`。

## 第五行：Swap 和可用内存

```text
MiB Swap: 2048 total, 1980 free, 68 used. 6740 avail Mem
```

| 数字 | 含义 |
|---|---|
| `2048 total` | Swap 总量为 2 GiB |
| `1980 free` | 还有 1980 MiB Swap 未使用 |
| `68 used` | 已使用 68 MiB Swap |
| `6740 avail Mem` | 估算还有约 6.6 GiB 内存可供新程序使用 |

虽然 `free` 只有 86 MiB，但 `available` 还有约 6.6 GiB，所以当前不能判断为内存不足。少量 Swap 被使用过，也不代表现在正在频繁换页。

## 进程列表

```text
PID USER PR NI VIRT RES SHR S %CPU %MEM TIME+ COMMAND
```

| 字段 | 含义 |
|---|---|
| `PID` | 进程编号 |
| `USER` | 启动进程的用户 |
| `PR` | 调度优先级 |
| `NI` | nice 值，影响普通进程的调度倾向 |
| `VIRT` | 进程拥有的虚拟地址空间 |
| `RES` | 当前实际驻留在物理内存中的大小 |
| `SHR` | RES 中可能与其他进程共享的部分 |
| `S` | 进程状态，如 `R`、`S`、`D`、`Z` |
| `%CPU` | 进程的 CPU 使用率 |
| `%MEM` | 进程占物理内存的比例 |
| `TIME+` | 进程累计消耗的 CPU 时间 |
| `COMMAND` | 进程或命令名称 |

以 Java 进程为例：

```text
1234 app 20 0 6.3g 1.8g 28000 S 85.3 11.6 125:33 java
```

表示它：

- PID 是 `1234`，由 `app` 用户运行。
- 虚拟地址空间是 `6.3 GiB`，不等于实际占用。
- 实际驻留物理内存约 `1.8 GiB`，约占整机内存 `11.6%`。
- 当前是睡眠状态，但采样周期内使用了 `85.3%` CPU。
- 已累计消耗约 125 分钟 CPU 时间。

对这份输出的整体判断是：**整机 CPU 和可用内存都还有余量，系统压力可能正在下降；Java 进程是当前最主要的 CPU 消耗者，同时存在一个需要检查父进程的僵尸进程。** 不过这只是一次快照，还要连续观察才能确认趋势。
