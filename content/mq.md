## kafka

### kafka 为什么性能高

Kafka 高吞吐主要来自三点核心：
第一，采用 append‑only 顺序追加写日志，避开昂贵的磁盘随机 IO；
第二，通过 Partition 分区实现读写并行，支持集群水平扩容；
第三，消费端使用 sendfile 零拷贝，减少 CPU 的数据拷贝开销。

在此基础上，依靠操作系统 PageCache 页缓存、全链路批量处理、极简服务端模型进一步放大性能。

### 为什么放弃 zookeeper

1. **运维负担**：需要维护 ZK 独立集群，多一套分布式系统，额外故障点。
2. **元数据性能瓶颈**：ZK 的 ZAB 写能力有限，大规模分区场景，Controller 故障切换时需要全量拉取 ZK 元数据，切换慢，集群分区数量受限。
3. **多副本状态不一致**：元数据分散 ZK、Controller、Broker 多处，网络抖动容易出现状态错位。
4. 元数据传播链路长，watch 机制在大规模集群压力大。

KRaft 将元数据交给 Kafka 内部 Raft 仲裁组，元数据保存在内部`__cluster_metadata`主题；follower 持续同步日志，controller 故障切换速度大幅提升，可以支持百万级分区，架构运维简化。Kafka4.0 彻底移除 ZK 支持。

### 索引

Kafka 索引的整套设计，核心是牺牲微小的扫描开销，换取极致的内存利用率和超高吞吐：
Kafka 采用分段日志 + 双稀疏索引 + mmap内存映射架构。每个日志段配有 offset 偏移量索引和 time 时间索引，采用稀疏索引策略，不每条消息建索引，仅间隔固定字节保存索引锚点，极大压缩索引体积、常驻页缓存。同时通过相对偏移量压缩进一步节省空间。查询时通过二分定位锚点 + 小范围顺序扫描，利用磁盘顺序读高性能，在极低内存开销下保证查询效率。索引采用mmap映射不占堆内存、无GC压力，且索引可重建、不影响数据可靠性，完美适配 Kafka 高吞吐、大数据量、顺序读写的核心场景。

### 时间轮

时间轮是一种高性能定时任务调度算法，底层是环形数组，数组每个槽挂载双向链表保存定时任务。时钟指针按固定 tick 间隔前进，指针走到槽位就执行槽内到期任务，新增删除任务接近 O (1)，性能优于最小堆 DelayQueue。

单层时间轮能管理的时间范围有限，Kafka 实现**多级层级时间轮**，内层粒度细、外层粒度粗。长延时任务存放在外层，当外层槽到期，任务会降级重新插入内层细粒度时间轮，临近到期再执行。Kafka 依靠 DelayQueue 驱动时钟推进，避免空转消耗 CPU。

该时间轮仅用于 Broker 内部超时等待，任务放在内存，没有持久化，**不对外提供业务延时消息能力**，业务层想要延时消息必须自己实现。

## rabbit mq

### 事务

RabbitMQ 事务是生产者侧的原子发送机制，基于 Channel 实现，用来保证一批消息要么全部投递成功，要么全部不投递。
开启事务后发送的消息先暂存内存，commit 才真正路由到队列，rollback 就全部丢弃。
但是它性能差，消费端不支持事务，也无法和数据库事务实现原子性，生产环境很少使用，一般选用 Publisher Confirms。

### 消息什么时候会进入死信交换机

1. 消息 TTL 超时过期；
2. 消费者调用 NACK/REJECT，并且 requeue=false，不重新放回原队列；
3. 队列消息数达到最大长度，队头消息被溢出丢弃。

注意死信判断发生在队列，交换机不会产生死信；TTL 不会实时扫描消息，要等到消息走到队头才判断；死信交换机就是普通交换机，死信队列也是普通队列。

### 无法路由的消息会去到哪里

如果消息投递交换机后找不到匹配队列：
默认`mandatory=false`消息直接丢弃；设置`mandatory=true`，消息会 return 退回生产者客户端，通过回调通知业务。
注意这种路由失败发生在交换机层面，消息没有进入队列，**不会触发死信交换机 DLX**。
如果想统一收集这类消息，可以给交换机配置 Alternate Exchange 备用交换机，路由失败的消息转发到 AE，存入兜底队列用于排查。

### 推模式

RabbitMQ 是纯推模式，Broker 主动下发消息，主要依靠 QoS 的 prefetchCount 预取窗口来保护消费者。它限制 Channel 上最多有 N 条已投递但未 ACK 的消息，达到上限 Broker 就停止推送；消费者处理完发送 ACK 之后，Broker 才继续补发消息，把消息压力留在服务端，不会一股脑全部推到消费端内存。

注意该机制必须开启手动 ACK 才生效。但 prefetch 是固定配置值，需要人工调参，不像拉模式可以完全自适应消费速度。同时配合队列最大长度、死信、Broker 流控做辅助防护。

## rocket mq

### 混合推拉

RocketMQ 的混合推拉模式叫 “名推实拉”。底层网络全部是 Pull，由消费者客户端内部后台线程持续发起长轮询请求，Broker 不会主动推送消息。

Broker 没有消息就挂起请求，有消息立刻返回；客户端收到消息调用业务注册的监听器回调，业务感知上和推模式一样。消费完马上发起下一轮拉取，持续蹲消息。

这么设计是兼顾两者优势：底层拉模式让 Broker 压力小，客户端可以根据自身处理能力控制拉取速度，避免被流量打崩；上层 SDK 封装，把拉取、offset、重试全部隐藏，业务开发像推模式一样简单。同时它也开放原生 Pull API，允许业务完全自主控制消费逻辑。

## 通用问题

### 延迟消息怎么实现

- kafka 没有延迟消息
- rabbit 本身没有延迟消息，可以通过超时转移到死信队列来达到延时效果
- rocket 早期是简单的延时等级，后来改为时间轮实现

### 消息堆积怎么办

**短期应急：**

1. Broker：优先扩容消费者；积压过大可迁移历史堆积消息，优先处理新消息；尽量不临时改分区。
2. 消费端：扩容消费实例，排查慢逻辑、无效重试，失败消息进死信队列。
3. 生产端：限流熔断、业务降级，降低写入速度，保护 MQ 磁盘不打满。

**长期优化：**

1. MQ 层面：按业务、任务快慢拆分 topic / 队列，快慢业务隔离；提前规划分区数，压测预留容量。
2. 生产者：流量评估，非核心业务做好限流降级预案。
3. 消费者：优化消费逻辑，开启批量消费；规范重试机制；完善堆积、延迟监控告警。

### raft

Raft 每个节点有 Follower、Candidate、Leader 三种状态，依靠递增的 term 任期。

1. **Leader 选举**：Follower 超时收不到心跳变成 Candidate，term 加一发起投票；拿到过半选票成为 Leader；持续发心跳维持地位。投票限制：候选者日志必须至少和自己一样新。
2. **日志复制**：客户端写全部走 Leader，Leader 生成日志条目，推送给 Follower；过半节点落盘之后日志才算提交；Leader 通知 Follower 应用已提交日志。Follower 日志冲突时，Leader 强制覆盖对齐。
3. **安全约束**：只有拥有全部已提交日志的节点才能当选 Leader，保证已提交日志永不丢失。

### 推 or 拉模式

推模式是 Broker 主动把消息推送给消费者，优点实时性好，消费者编码简单。缺点是 Broker 不清楚消费者处理能力，消息突增容易压垮消费者；一般通过 prefetch 预取窗口限制未处理消息数量做流控；Broker 压力相对更大，RabbitMQ 就是推模式。

拉模式由消费者主动向 Broker 拉取消息，消费者完全掌控消费速度，不会被流量打垮，Broker 逻辑简单；缺点普通短轮询会产生大量无效请求，Kafka 用长轮询解决这个问题，阻塞等待消息到来，兼顾实时性。消费者需要自己管理 offset，业务代码复杂一点。

### 怎么保证顺序性

MQ 只能保证**单个分区 / 队列内部有序**，跨分区无法保证有序。

业务上的局部有序（同一个订单 / 用户有序）实现：

1. 发送端：将相同业务 key 做哈希路由，全部发送到同一个分区 / 队列。
2. 消费端：一个分区只能单线程消费，不能把消息丢入异步线程池处理。
3. 注意规避乱序坑：生产者自动重试会造成消息乱序，顺序场景要关闭自动重试；消费失败重试也可能打乱顺序。

如果要全局绝对有序，只能使用单个分区，单线程消费，但是吞吐量很低，一般不推荐。

### 处理重复消息

MQ 只能保证至少一次投递，无法避免消息重复，必须业务实现幂等。

消息重复产生的主要原因：生产者发送成功但响应丢失触发重试；消费处理完业务还没提交 offset/ack 就宕机重启，造成重复消费。

主流处理方案：

1. 数据库唯一索引：消息携带业务唯一 ID，通过唯一索引冲突过滤重复，最可靠，生产最常用，可以和业务操作放在同一个事务。
2. 业务状态机：利用业务本身状态流转，判断是否已经处理完成，适合订单这类业务。
3. Redis 缓存做去重，适合高吞吐场景，只能做加速，需要数据库兜底，不能单独依赖。

Kafka 幂等生产者、Kafka 事务只能保证 Kafka 内部读写精确一次；一旦操作数据库等外部系统，仍然要业务幂等。不要依靠关闭重试来规避重复，会带来消息丢失风险。

### 如何保证消息不丢失

消息丢失发生在生产者发送、Broker 存储、消费者消费三个阶段。

- 生产者端：关闭单向发送，开启确认回调；发送失败消息本地持久化补偿重试。Kafka 设置 acks=all、开启幂等生产者。
- Broker 端：开启消息持久化，配置多副本集群；RocketMQ 可以开启同步刷盘，Kafka 依靠操作系统 PageCache+ISR 多副本保证。
- 消费端是高频坑点：禁止提前提交 offset/ACK，关闭自动提交。**业务逻辑处理成功之后，再手动提交 offset 或者 ACK**；业务处理失败就不要确认，让消息重新投递。

最后配置死信队列兜底，处理持续失败的消息。同时注意，保证不丢失的方案会带来消息重复，消费端必须做幂等。

### 消费模型

1. **点对点（P2P）**：一条消息，**同一个消费组内只有一个消费者消费**，用于负载均衡处理任务。
2. **发布订阅（Pub/Sub）**：一条消息，**每个消费组都能收到完整消息**，各组独立消费。

一句话区分：P2P是组内抢；发布订阅是每组都一份。
