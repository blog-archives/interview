## 一、InnoDB 缓冲与日志

### Doublewrite Buffer

刷脏页之前先写一份到共享表空间。将单次高危写操作拆成两次，防止宕机产生半页写损坏，保证数据页完整。

### redo log buffer

log buffer 是 redo 日志内存缓冲区。事务修改生成 redo 先放这里，满足条件再刷到磁盘 redo 文件。目的是合并写、减少随机 IO。默认在事务提交时落盘

### write-ahead logging（wal）技术

WAL，全称Write‑Ahead Logging，预写日志，是InnoDB核心机制。

核心规则：**修改数据页之前，必须先把本次修改写到redo log日志，日志落盘成功，才允许更新内存里的数据页；数据页不需要立刻刷到磁盘**。

好处有两点： 第一，崩溃恢复。数据库宕机时，内存脏页还没刷盘，但是redo log已经持久化了，重启可以通过redo log重做已经提交的修改，保证数据不丢，保障事务的持久性。 第二，提升性能。不用每次修改都刷磁盘数据页，改成顺序写redo log，顺序写比随机写磁盘快很多。

区分两个容易混的点：

1. redo log属于WAL实现，服务崩溃恢复；binlog是MySQL层日志，用于主从复制、数据备份。
2. WAL只保证日志先写盘，不代表数据页马上落盘，脏页会后台慢慢刷盘。

简单一句话总结：**先记日志，再改内存数据；日志先落盘，事务才算完成，数据页延后刷盘**。

补充小坑：如果redo log写满，就会触发强制刷脏页，此时会出现性能抖动。

### redo log 记录的是什么

redo log 记录数据页上的物理改动，用来崩溃恢复；binlog 记录逻辑变更，用来复制备份。

### change buffer

Change Buffer 是 InnoDB Buffer Pool 的一块内存区域，**只对二级非唯一索引生效**，聚簇索引、二级唯一索引无法使用。

更新二级非唯一索引时，如果索引页不在内存，不会加载磁盘页，而是先把变更缓存在 Change Buffer；等后续该索引页读入内存时再做merge合并，减少磁盘随机读，提升写入性能。

二级唯一索引不能用它：写入时必须校验唯一性约束，一定要把索引页加载到内存，所以走不了Change Buffer。

merge触发时机：访问索引页、后台master线程定期执行、数据库正常关闭、表重建。 Change Buffer的操作也会写redo log，保证崩溃安全。

弊端：长期不访问的索引页会堆积待合并数据，异常重启会增加恢复耗时；写后立刻查询该索引时收益很低。 参数`innodb_change_buffer_max_size`控制它占Buffer Pool的最大百分比。

### buffer pool

Buffer Pool是InnoDB的核心内存缓冲区，用来缓存**磁盘的数据页和索引页**，目的减少磁盘IO，提升读写性能。

1. **读请求**：优先从Buffer Pool找页；命中直接返回；没命中就从磁盘加载页放入Buffer Pool。

2. **写请求**：不会直接写磁盘，修改内存里的页，页变成**脏页**；脏页由后台线程异步刷回磁盘。

3. 内部组成：

   - 缓存页：存放真实数据、索引；

   - Free链表：空闲可用页；

   - LRU链表：管理冷热页，淘汰很久没访问的数据；

   - Flush链表：存放脏页。

1. LRU优化：分冷热区，避免大量全表扫描直接把热数据淘汰出去。
2. 相关参数：`innodb_buffer_pool_size`，一般建议设置为物理内存的50%‑70%。

补充：Change Buffer属于Buffer Pool内部的一块子区域。

## 二、索引与查询优化

### B+树索引原理

B+树是MySQL索引的底层数据结构，特点：

- 非叶子节点只存索引键和指针，不存数据，单个节点能容纳更多键，树更矮；
- 叶子节点包含全部索引键和对应数据（或主键），叶子之间用双向链表连接，范围查询效率高；
- 所有查询都要走到叶子节点，查询路径长度稳定。

对比B树：B树非叶子节点也存数据，单个节点容纳键少，树更高；范围查询需要中序遍历整棵树，效率低。

### 聚簇索引与二级索引

- **聚簇索引**：叶子节点存储完整行数据，一张表只能有一个。InnoDB中主键就是聚簇索引；没有主键时选第一个唯一非空索引；都没有则自动生成隐藏rowid。
- **二级索引（非聚簇索引）**：叶子节点存储索引列值 + 主键值，不存完整行数据。一张表可以有多个二级索引。

通过二级索引查询时，如果需要的列不在索引中，就需要拿主键再去聚簇索引查一次完整行，这就是**回表**。

### 回表与覆盖索引

**回表**：通过二级索引找到主键后，再用主键到聚簇索引查询完整行数据的过程。回表需要额外一次B+树查找，性能有开销。

**覆盖索引**：查询需要的所有列都包含在索引中，不需要回表，直接从索引叶子节点返回数据。Explain中Extra显示`Using index`。

业务场景：高频查询的列尽量建联合索引覆盖，避免回表。例如`SELECT name, age FROM user WHERE name = ?`，建`(name, age)`联合索引即可覆盖。

### 最左匹配与联合索引

联合索引遵循**最左匹配原则**：查询从索引最左列开始匹配，遇到范围查询（>、<、between、like左模糊）就停止匹配后面的列。

联合索引字段顺序选择原则：

1. **等值查询优先**：经常用于`WHERE`等值条件的列放前面；
2. **高频查询列优先**：区分度高、查询频率高的列放前面；
3. **范围查询列放后面**：范围查询会中断后续列的索引匹配，所以范围列放后面；
4. **覆盖查询需求**：如果需要覆盖索引，把查询要返回的列也纳入索引。

例如`WHERE a = ? AND b > ? AND c = ?`，联合索引`(a, b, c)`中c不会走索引，因为b是范围查询中断了匹配。

### 索引失效场景

常见导致索引失效的SQL写法：

1. **隐式类型转换**：字段是字符串但查询用数字，如`WHERE phone = 13800000000`（phone是varchar），MySQL会对字段做函数转换导致失效；
2. **like 左模糊**：`WHERE name LIKE '%张三'`或`'%张三%'`无法走B+树索引，右模糊`'张三%'`可以；
3. **or 条件**：`WHERE a = 1 OR b = 2`，如果a和b没有分别建索引，整个查询不走索引；需要两个列都有索引才可能走index merge；
4. **索引列参与运算/函数**：`WHERE YEAR(create_time) = 2024`或`WHERE id + 1 = 10`，对索引列使用函数或运算导致失效；
5. **不符合最左匹配**：联合索引`(a, b)`，查询`WHERE b = ?`跳过了最左列a，不走索引；
6. **MySQL优化器判断全表扫描更快**：数据量小或区分度低时，优化器可能选择全表扫描。

### 数据排序时怎么实现的

1. **索引有序扫描**：order by 字段能命中索引，直接顺着索引有序读取数据，无额外排序操作，Explain 无 Using filesort。
2. **filesort排序**：无法用索引时触发。优先在sort_buffer内存排序；内存不足，落地磁盘做归并排序。分单路、双路排序模式。

注意：filesort不代表一定磁盘排序。业务要稳定顺序必须显式写order by。

### 为什么不推荐使用多表 join

MySQL不是禁用join，两表join合理使用没问题，**不建议三张及以上多表join**，主要四点原因：

第一，优化器风险。多表join的连接组合数量阶乘上涨，优化器只能贪心估算，容易选错驱动表，导致扫描行数暴增，性能劣化。

第二，消耗数据库资源。过滤条件不好时会生成很大的中间结果集，占用大量内存，甚至落盘磁盘临时表，挤压buffer pool热点缓存，拖累库上其他SQL。

第三，不利于分库分表扩展。ShardingSphere虽支持跨库join，但需要把各分片数据拉到中间件内存做关联，网络、内存开销大，性能差。

第四，维护麻烦。on、where条件容易写错，复杂SQL排查和调优难度高。

所以互联网业务通常拆成多次单表查询，关联逻辑放应用层组装，应用层可以水平扩容；也可以适当冗余字段减少关联。小数据量、索引完善的场景，少量多表join是可以用的。

### Explain Extra 重点标记

✅ 正常：

- `Using index`：**覆盖索引**，不需要回表，高性能，理想状态

⚠️ 需要优化：

1. `Using filesort`：文件排序，**没有用到索引排序，需要额外排序**，order by 没走索引
2. `Using temporary`：使用临时表，常见 group by、distinct，性能差
3. `Using where`：存储引擎返回数据后，mysql 服务层再过滤，不一定坏，要看 type

### 千万级大表分页优化

`limit offset, size` 在 offset 很大时性能差，因为MySQL需要先扫描 offset + size 行再丢弃前 offset 行。优化方案：

1. **子查询延迟关联**：先用覆盖索引查到主键id，再用id关联回表查询完整行。`SELECT * FROM table WHERE id IN (SELECT id FROM table WHERE condition LIMIT 100000, 10)`；
2. **游标分页（seek pagination）**：用上一页最后一条记录的id作为条件，`WHERE id > last_id LIMIT 10`，避免大offset，适合无限滚动场景；
3. **业务限制深度**：产品层面限制最大翻页页数（如最多100页），超过后用搜索或筛选缩小范围；
4. **冷热数据归档**：历史数据归档到单独表或ES，主表只保留近期数据，减少单表行数。

## 三、事务、隔离级别与锁

### 二阶段提交

MySQL InnoDB 二阶段提交是用来保证 redo log 与 binlog 两份日志一致性。

第一阶段 Prepare：写 redo log 并刷盘，事务状态置为 PREPARED，不写 binlog。

第二阶段 Commit：刷写 binlog，再把 redo log 标记为 COMMITTED，事务结束。

如果宕机重启，读到 redo log 为 PREPARED 状态时，会核对对应 binlog 是否完整：binlog 完整就提交事务，binlog 缺失则回滚事务，避免主从数据不一致。

### 四种隔离级别

SQL标准定义了4种事务隔离级别：

1. **读未提交（Read Uncommitted）**：能读到其他事务未提交的数据，存在脏读，基本不用；
2. **读已提交（Read Committed, RC）**：只能读到其他事务已提交的数据，解决脏读，但存在不可重复读（同一事务内两次读同一行结果不同）；
3. **可重复读（Repeatable Read, RR）**：同一事务内多次读同一行结果一致，解决不可重复读，InnoDB默认级别；
4. **串行化（Serializable）**：事务完全串行执行，解决所有并发问题，但性能最差。

**RC vs RR 业务选型：**

- RR：MVCC基于事务启动时的read view，同一事务内数据视图稳定，适合需要一致性读的业务（如金融转账）；但间隙锁更多，死锁概率更高；
- RC：每次select都生成新的read view，能读到其他事务已提交的最新数据；间隙锁更少（只有外键检查和唯一键检查会加间隙锁），并发性能更好；适合互联网高并发业务，大部分互联网公司默认用RC。

### MVCC 原理

MVCC（多版本并发控制）是InnoDB实现隔离级别的核心机制，通过保存数据行的多个历史版本，让读写互不阻塞。

核心组成：

- **undo log**：保存数据行的历史版本，通过roll_pointer指针形成版本链。每次修改都会把旧值写入undo log；
- **read view**：事务执行快照读时生成的一致性视图，记录当前活跃事务列表，用于判断版本链中哪个版本对当前事务可见；
- **trx_id**：每行数据隐藏的事务ID字段，标记最后修改这行的事务。

可见性判断规则：

- 版本trx_id < read_view.min_trx_id：该版本在read view生成前已提交，可见；
- 版本trx_id >= read_view.max_trx_id：该版本在read view生成后才开始，不可见；
- 版本trx_id在活跃事务列表中：该版本事务还未提交，不可见；
- 否则可见。

**undo log 清理时机**：purge线程定期清理不再需要的undo log。当没有任何事务的read view还引用某个undo版本时，该版本就可以被清理。长事务会持有旧read view，导致undo log无法清理，磁盘占用上涨。

### RR 级别幻读解决

**幻读**：同一事务内两次执行范围查询，第二次查询出现了第一次没有的行（其他事务插入了新行并提交）。

InnoDB在RR级别下通过**Next-Key Lock（临键锁）**解决当前读的幻读问题：

- 对范围查询加临键锁（记录锁 + 间隙锁），锁住查询范围和范围之间的间隙，其他事务无法在这个范围内插入新行；
- 例如`SELECT * FROM user WHERE age > 20 FOR UPDATE`，会锁住所有age > 20的记录和对应的间隙，阻止新插入age > 20的行。

**快照读 vs 当前读：**

- **快照读（一致性非锁定读）**：普通SELECT，基于MVCC读取数据行的历史版本，不加锁，不会阻塞其他事务。RR级别下同一事务内快照读基于同一个read view，不会出现幻读；
- **当前读（锁定读）**：`SELECT ... FOR UPDATE`、`SELECT ... LOCK IN SHARE MODE`、INSERT、UPDATE、DELETE，读取最新已提交版本并加锁。RR级别下通过临键锁防止幻读。

注意：MVCC只能解决快照读的幻读，当前读的幻读需要靠临键锁解决。

### 事务回滚场景

不同异常场景下事务回滚的表现不同：

- **普通SQL报错**：只撤销失败的那条语句，事务继续存活，需要手动rollback。例如唯一键冲突、字段超长等；
- **死锁**：InnoDB自动选择回滚代价最小的事务，整体回滚该事务；
- **连接断开**：MySQL服务端检测到连接关闭，自动回滚该连接上所有未提交事务；
- **数据库宕机**：重启后通过redo log重做已提交事务，未提交事务自动回滚；
- **程序panic / crash**：如果进程还活着、连接还在，MySQL完全不知道程序出错，事务不会自动回滚，业务代码必须在defer/recover中手动rollback；如果进程崩溃导致连接断开，MySQL会自动回滚。

关键原则：**只有数据库连接被MySQL服务端判定关闭时，未提交事务才自动全部回滚。**

### InnoDB 锁机制

**锁的粒度：**

- **行锁**：锁定具体行，并发度高。InnoDB行锁是通过索引实现的，没命中索引时会升级为表锁（实际是锁住所有扫描到的行，效果近似表锁）；
- **表锁**：锁定整表，并发度低。一般是DDL操作或没命中索引的DML导致；
- **意向锁**：表级锁，事务打算加行锁前先加意向锁，让其他事务快速判断表上是否有行锁，避免逐行检查。意向锁之间互相兼容，意向锁和表锁互斥。

**锁的模式：**

- **共享锁（S锁）**：读锁，多个事务可以同时持有S锁，互斥X锁。`SELECT ... LOCK IN SHARE MODE`；
- **排他锁（X锁）**：写锁，一个事务持有X锁后，其他事务不能加任何锁。INSERT/UPDATE/DELETE/`SELECT ... FOR UPDATE`自动加X锁。

**行锁的三种类型（RR级别）：**

1. **记录锁（Record Lock）**：锁定具体索引记录，精确到一行；
2. **间隙锁（Gap Lock）**：锁定索引记录之间的间隙（不包含记录本身），防止其他事务在间隙中插入新行，解决幻读。间隙锁之间不互斥（多个事务可以同时锁同一个间隙），只和插入操作互斥；
3. **临键锁（Next-Key Lock）**：记录锁 + 间隙锁，锁定记录本身和之前的间隙，左开右闭区间。InnoDB默认的行锁算法。

**RR下什么时候产生间隙锁：**

- 使用当前读（FOR UPDATE / LOCK IN SHARE MODE / UPDATE / DELETE）且走索引范围查询时；
- 唯一索引等值查询命中记录时，退化为记录锁（不加间隙锁）；
- 唯一索引等值查询未命中时，会加间隙锁锁住查找范围；
- 非唯一索引等值查询，无论是否命中，都会加临键锁（包含间隙）。

**update没命中索引的后果：**

UPDATE语句如果没命中索引，InnoDB会扫描全表并对每一行都加行锁（实际效果等同于表锁），然后在server层过滤不满足条件的行并释放锁。这会导致：

- 锁定大量无关行，并发性能急剧下降；
- 死锁概率大幅增加；
- 长事务持有大量锁，阻塞其他操作。

### 死锁排查与解决方案

排查死锁，首先执行`show engine innodb status`，查看`LATEST DETECTED DEADLOCK`最近一次死锁日志，可以看到双方 SQL、持有锁和等待锁信息，以及两个事务的id。

线上建议开启`innodb_print_all_deadlocks`，把死锁持久化到错误日志，防止日志被覆盖。

通过日志梳理两个事务加锁顺序，绝大多数死锁是更新行顺序不一致导致。然后到项目代码中找到对应的业务逻辑。

**解决方案：**

1. **统一事务执行顺序**：多个事务更新相同资源时，按固定顺序（如按id从小到大）加锁，避免循环等待；
2. **减少事务中执行其他业务逻辑**：缩小事务范围，事务内只做数据库操作，不做RPC调用、复杂计算等耗时操作，减少锁持有时间；
3. **降低锁粒度**：检查SQL是否正确走索引，避免全表锁；合理使用覆盖索引减少回表加锁；
4. **设置锁超时时间兜底**：`innodb_lock_wait_timeout`控制锁等待超时，超时后自动放弃并回滚语句；
5. **隔离级别改为RC**：RC级别下间隙锁更少，死锁概率降低（允许的话）；
6. **业务代码捕获死锁异常做有限重试**：死锁是可重试错误，捕获后重新执行事务。

### select for update 与 skip locked

**select for update**：对查询结果行加排他锁（X锁），其他事务不能修改这些行，也不能再加排他锁，直到当前事务提交或回滚。

业务使用场景：

- 需要先查询再修改，且要保证查询到的数据不被其他事务修改（如库存扣减前先查库存）；
- 任务分配场景：查询待处理任务并锁定，防止多个worker同时抢到同一个任务。

**for update skip locked**：在select for update基础上，跳过已经被其他事务锁定的行，不等待锁释放，直接返回未被锁定的行。

解决的业务场景（库存抢扣 / 任务抢单）：

- 高并发抢库存时，多个请求同时select for update会导致锁等待，skip locked可以让请求直接跳过已被锁定的库存行，拿到可用库存立即处理，提升并发吞吐；
- 任务队列中多个worker同时抢任务，skip locked保证每个worker拿到不同的任务，不会重复处理。

缺陷：

- 跳过的行不会被返回，可能导致某些行一直被跳过（如果总是被长事务锁住），造成"饥饿"；
- 不保证按顺序获取，可能跳过前面的行直接拿后面的；
- 需要业务层处理"本次没拿到任何行"的情况（重试或等待）。

### 长事务与大事务危害

长事务就是事务开启后长时间不提交或回滚。大事务是指操作大量数据、执行时间长的事务。

危害：

- **undo日志历史版本无法回收**：长事务持有旧read view，导致undo log无法清理，磁盘占用上涨，MVCC查询需要遍历更长的版本链，性能变差；
- **行锁持有时间久**：引发大量锁等待、死锁，并发度下降；
- **binlog刷盘与主从延迟**：大事务提交才写binlog（statement格式），产生大量binlog，从库回放慢，加剧主从复制延迟；
- **阻塞DDL**：长事务持有MDL锁，DDL需要等待MDL锁释放，期间新来的读写请求全部阻塞，可能引发雪崩；
- **回滚开销大**：大事务回滚需要执行大量反向操作，耗时久，占用资源；
- **宕机恢复耗时增加**：崩溃恢复时需要重做或回滚大事务，恢复时间长。

哪些业务会写出大事务：

- 循环中逐条更新大量数据（如批量更新10万行）；
- 事务内调用RPC接口或执行耗时操作，事务长时间不提交；
- 一次性删除/插入大量数据；
- 事务嵌套或多层级联操作。

拆分大事务的方法：

- 批量操作分批提交（如每1000条提交一次）；
- 事务内只做数据库操作，RPC等耗时逻辑移到事务外；
- 用异步消息队列解耦，事务内只发消息，消费者异步处理；
- 大删除用条件分批delete，避免一次性删太多。

## 四、主从复制与 binlog

### binlog 三种格式

binlog是MySQL Server层的逻辑日志，记录所有修改数据的SQL操作，用于主从复制和数据备份恢复。三种格式：

1. **statement**：记录执行的SQL语句原文。优点是日志量小；缺点是不确定性函数（如UUID()、NOW()、LAST_INSERT_ID()）在从库执行结果可能不一致，导致主从数据不一致；
2. **row**：记录每一行数据的变更（before image + after image）。优点是数据绝对一致，不依赖SQL执行环境；缺点是日志量大（批量更新会记录每一行变更），无法直接从日志看出执行的SQL；
3. **mixed**：混合模式，MySQL自动判断。一般语句用statement格式，遇到不确定性函数或可能导致不一致的操作时自动切换为row格式。

**业务什么场景必须用row格式：**

- 对数据一致性要求高的业务（金融、支付、订单）；
- 使用了不确定性函数的业务；
- 需要做增量数据订阅（CDC）的场景，row格式能精确拿到每行变更前后的值，方便下游消费；
- 互联网业务基本都用row格式，mixed也可以，但row最安全。

### 主从复制流程

MySQL主从复制基于binlog，流程：

1. **主库写入binlog**：主库事务提交时，将修改操作写入binlog文件；
2. **从库IO线程拉取binlog**：从库的IO线程连接主库，请求读取指定位置之后的binlog，写入从库本地的relay log（中继日志）；
3. **从库SQL线程回放**：从库的SQL线程读取relay log，在从库上执行相同的操作，保持数据一致。

复制模式：

- **异步复制**：主库写入binlog后立即返回客户端，不等待从库确认。性能高但主库宕机可能丢数据；
- **半同步复制**：主库写入binlog后，等待至少一个从库确认收到binlog（不需要回放完成）才返回客户端。降低丢数据概率；
- **全同步复制**：等待所有从库都确认收到并回放完成才返回。性能差，一般不用。

### 主从延迟原因与解决方案

主从延迟产生的原因主要在两侧：

**传输侧：**

- 网络问题导致binlog日志传输慢（网络抖动、带宽不足）。

**回放侧（线上最常见）：**

- 硬件性能差距：从库配置比主库差，CPU/磁盘IO跟不上；
- 从库读压力大：读写分离场景下从库承担大量读请求，挤占了SQL回放线程的资源；
- 表缺少主键索引：从库回放时如果表没有主键，UPDATE/DELETE需要全表扫描定位行，回放极慢；
- 主库大事务、批量操作、大DDL产生大量binlog，从库消费处理不过来。

**读写分离场景下解决主从延迟导致的数据不一致：**

1. **强制走主库**：对一致性要求高的读操作（如刚写完立即读），强制路由到主库；
2. **延迟判断**：业务层判断`Seconds_Behind_Master`，延迟超过阈值时读请求切到主库；
3. **半同步复制**：确保从库至少收到binlog后才返回，减少延迟窗口；
4. **并行复制**：MySQL 5.7+支持基于组提交的并行回放，提升从库回放速度；
5. **业务层容忍**：对非核心读（如列表页、统计）接受秒级延迟。

### 半同步复制

半同步复制原理：主库事务提交时，写入binlog后，等待至少一个从库确认收到binlog（写入relay log，不需要回放完成），才向客户端返回成功。如果等待超时（默认10秒），自动降级为异步复制。

**数据丢失风险点（半同步不能完全杜绝丢数据）：**

1. **等待从库ack超时自动降级异步**：超时后主库切回异步模式，后续提交的事务可能在主库宕机时丢失；
2. **唯一应答的从库故障**：只有一个从库确认收到binlog，如果这个从库还没来得及回放就故障了，且没有其他副本留存日志，数据可能丢失；
3. **主库`sync_binlog`非1**：事务binlog停留在OS缓存未刷盘，主库宕机（如断电）导致OS缓存中的binlog丢失；
4. **从库ack应答包网络丢包**：主库没收到ack，错误判定超时降级为异步，但实际上从库已经收到了binlog，主库可能在降级后宕机导致后续事务丢失。

## 五、外键

### 物理外键 & 逻辑外键

物理外键是数据库原生约束，数据库保障关联正确，适合单机低并发业务；缺点是性能差、不能用于分库分表。 逻辑外键只存关联 ID，约束交给业务代码，高并发、分库分表场景普遍使用，但要业务自行处理脏数据风险。

## 六、分库分表

### 分库分表的实施流程

1. 先评估是否真的需要拆分，选择垂直还是水平拆分，选定分片键，梳理改造不兼容 SQL，选择分片中间件和分布式 ID 方案；
2. 初始化分库分表新表，业务代码改造，物理外键改为逻辑外键；
3. 线上不停服就走迁移服务：全量同步存量数据，CDC 消费 binlog 做增量同步，再开启业务双写；
4. 持续做新旧库的数据校验修复；
5. 灰度切流量，先逐步切读请求，全部读切完再切写，关闭双写；
6. 旧库保留做回滚兜底，稳定后关停同步任务，下线旧库。 如果业务允许停机，可以省去双写、CDC，停写直接导数据切换。

是否分库：看**单机实例资源**。单实例磁盘过大、写入 QPS 打满 CPU、单机锁 / 连接瓶颈。读高优先读写分离，写扛不住才分库。分库分垂直（按业务域）、水平（打散同一张表到多实例）。

是否分表：看**单表行数**，InnoDB 单表建议千万以内，超过后索引、DDL 性能变差。单表行数大但实例资源充足，只分表不用分库。 分表分水平分表（哈希 / 范围拆分数据行）、垂直分表（冷热列拆分）。

注意：垂直拆分不能解决单表行数过大；读写分离解决读压力，解决不了写压力。评估完之后还要选定合适分片键。

### 什么时候必须分库分表

当SQL优化、索引优化、读写分离、硬件升级、冷热归档这些手段全部做完之后，出现下面两类硬性瓶颈，就必须做分库分表：

1. **存储维度**：单表行数持续增长到千万级别，索引、查询、DDL、备份恢复压力恶化；或者单库整体数据量过大，磁盘空间不足；
2. **写入并发维度**：单机MySQL的写TPS打满硬件上限，读写分离只能分担读请求，无法解决写瓶颈。

### 分片路由策略

水平分表常见的路由策略：

- **Hash取模**：按分片键hash后对分片数取模，数据打散均匀，查询定位快；缺点是扩容时需要迁移大量数据（如从4扩到8，约75%数据需要迁移）；
- **Range范围分片**：按分片键的范围（如id区间、时间区间）分配到不同分片；扩容简单（新增分片即可），但容易出现热点分片（最新数据集中在一个分片）；
- **时间分片**：Range的特例，按时间（如按月/按年）分片，适合流水日志类业务，历史数据可以归档或删除；缺点是跨时间范围查询需要查多个分片。

分片键选择原则：尽量选业务高频查询条件，减少跨分片查询；分片键一旦选定很难修改，需要谨慎评估。

### 分库分表以后引入的问题

分库分表解决单库单表瓶颈，但会引入很多新问题：

1. **跨分片查询问题** 不带分片键查询，需要遍历多个分片；跨分片`join`、`group by`、`order by`、分页，无法数据库直接完成，需要业务层聚合，性能变差。
2. **分布式ID问题** 不能再用单库自增主键，需要额外实现雪花算法等分布式ID，要保证全局唯一。
3. **分布式事务** 跨库修改数据，本地事务失效。无法用数据库原生事务，只能用柔性事务（TCC、本地消息表、SAGA），开发复杂度上升，会有短暂不一致。
4. **外键失效** 物理外键无法跨库生效，只能改用逻辑外键，需要业务代码维护引用关系，还要做数据巡检兜底。
5. **分片键相关痛点** 分片键一旦选定很难修改；更新分片键的操作很难做；分片键选择不当会出现热点分片，部分库压力远高于其他分片。
6. **扩容迁移麻烦** 后期分片数量不够，重新分片需要数据迁移、双写、灰度切流，工程工作量大。
7. **运维复杂度增加** 实例、表数量变多；备份、DDL、监控、故障处理成本上升；主从延迟、数据校验难度变大。
8. **排序分页坑**`limit offset`分页跨分片会有深度分页性能问题，不能直接简单复用原来SQL。

总结：能通过索引优化、读写分离、归档解决，就不要分库分表，它会大幅增加业务和运维成本。

## 七、大表 DDL

### 大表加字段/索引4种方式

1. COPY：老版本算法，全程锁表阻塞读写，生产禁用。
2. INPLACE Online DDL：直接alter，可并发读写，警惕长事务导致MDL锁雪崩，IO无法限流。
3. INSTANT(8.0+)：仅支持末尾增删列等，毫秒执行，**不能建索引，仍怕长事务**。
4. gh‑ost/pt‑osc影子表迁移：空影子表执行变更后迁移数据，支持限流，需要双倍磁盘，rename瞬间短暂锁表。

**核心注意事项** 避开业务高峰期执行；先杀掉大长事务；评估磁盘剩余空间；8.0优先用INSTANT能做的操作；加索引不能用INSTANT，大表优先gh‑ost；主从环境关注主从延迟。

### COPY 算法流程

1. 获取原表**MDL写锁**，阻塞所有读写DML。
2. 创建一张**用户层可见的临时表**，复制原表结构，同时执行目标DDL（加索引、增删改字段）。
3. 将原表全部数据拷贝到这个临时表里。
4. 删除原表，把临时表rename成原表名字。
5. 释放锁，DDL结束。

关键点：

- **全程持有MDL写锁**，整个过程业务不能读写；
- 需要双倍磁盘空间；
- 不管什么DDL，都要全量拷贝整表数据。

一句话速记：拿写锁，建新临时表，拷全部数据，替换原表，全程锁业务。

### INPLACE 算法完整流程

分两种模式：

1. no‑rebuild：仅新增二级索引，**不重建聚簇索引**
2. rebuild：增删列等，重建聚簇索引+全部二级索引，生成InnoDB内部临时ibd文件

1. **获取MDL读锁**

   - 校验表、读取元数据；阻止其他DDL（drop/alter/rename）执行；

   - MDL 读锁和业务 DML 的 MDL 读锁互相兼容，业务可以正常读写本表；

   - 初始化 online log(row_log)，用来记录DDL过程中业务产生的增量变更。

2. **执行构建（最耗时Execute阶段）** 扫描原表聚簇索引：

   - no‑rebuild（加二级索引）：只提取索引字段，构建新二级索引B+树，原聚簇索引不变。

   - rebuild（增删列等）：读取全部行，按新结构生成全新聚簇索引以及全部二级索引，写入InnoDB内部临时ibd文件。

      此阶段业务持续读写原表，所有新增/修改/删除操作不写入正在构建的新索引/临时文件，全部写入online log。

3. **回放online log，追平增量** 历史数据构建完毕，反复回放online log里面积攒的业务变更，把增量应用到新索引/临时ibd文件，尽量缩小剩余未同步的数据量。

4. **短暂升级为MDL写锁**

   - 阻塞新的DML请求；

   - 把最后残余少量online log全部回放完成。

5. **提交元数据，替换文件**

   - no‑rebuild：更新元数据，标记新二级索引生效。

   - rebuild：原子替换内部临时ibd文件覆盖原表的数据文件。

   - 释放MDL锁，DDL结束，业务恢复正常。

1. INPLACE的rebuild虽然叫原地，但会生成**InnoDB层内部临时ibd**，不是MySQL层COPY算法那种用户可见临时表。
2. 整个DDL全程持有MDL读锁，直到最后瞬间升级写锁；**长事务持有MDL读锁，会卡在升级写锁这一步，引发业务堵塞**。
3. 如果指定LOCK=SHARED，则这期间只允许读、阻塞写，此时虽然算法是INPLACE，但不属于Online DDL。

### INSTANT算法流程

1. **准备阶段** 拿可升级MDL读锁，校验DDL操作是否支持INSTANT；**不扫描磁盘数据、不拷贝任何行**。业务DML正常读写本表。
2. **提交阶段（核心）** 短暂升级为**MDL排他写锁**，只更新系统数据字典：修改列定义、默认值，递增表元数据版本号。**完全不动`.ibd`磁盘数据文件**。更新完立刻释放MDL锁，DDL执行结束。

没有构建索引、没有重建表、没有online log、没有回放增量。

1. **后续读旧行（懒生效）** 读到DDL之前的老行：磁盘行本身没变，引擎**内存里动态补齐新增列默认值 / 跳过已删除列**返回给客户端。
2. **后续写新行** 后续insert/update重写该行时，才按最新表结构写入磁盘；存量旧行不会主动改写。

关键要点

- 耗时和表大小无关，毫秒完成。
- 仅提交那一瞬间持有MDL写锁；**如果存在长事务持有MDL读锁，依然会卡住等待**。
- 能力有限：不能用来建索引、不能修改字段类型。

一句话速记：校验支持INSTANT，瞬间拿MDL写锁改元数据就结束；旧行读的时候内存动态补字段，新写入才落地新结构。

### 第三方工具流程

gh‑ost（主流，binlog模式）完整流程

1. 通过`SHOW CREATE TABLE`拿到原表结构，创建**空影子表**（`_xxx_gho`），仅复制结构，不拷贝数据。
2. 在空影子表执行目标DDL（加字段、索引等），空表变更速度极快；锁只作用影子表，原表不受影响。
3. 按主键分chunk，**分批拷贝原表存量数据写入影子表**，支持限流，每批读完就释放读锁，不长期锁原表。
4. 伪装MySQL从库，订阅binlog，把原表拷贝期间产生的新增/修改/删除，异步应用到影子表，持续追平数据。
5. 存量拷贝完成，持续回放binlog把两边数据对齐。
6. **cut‑over切换**：短暂获取原表MDL写锁，原子rename交换原表和影子表名字。
7. 旧表改名成备份表，后续可删除，任务结束。

pt‑osc（触发器模式），前面步骤大体相同，区别：

1. `CREATE TABLE ... LIKE`创建空影子表，空表执行DDL。
2. **在原表创建insert/update/delete触发器**（瞬间拿MDL写锁，创建完释放），原表每次写操作，触发器同步写影子表。
3. 分批chunk拷贝存量数据。
4. 靠触发器实时同步增量，不需要解析binlog。
5. 最后短暂锁表rename交换表名。
6. 删除触发器、旧表。

共同关键点

- **全程不会长期持有原表MDL锁**；仅创建触发器(pt‑osc)、最终rename这两个瞬间短暂拿锁。
- 变更全部先在空影子表做完，再迁移数据；原表持续对外提供读写服务。
- 需要双倍磁盘空间存放影子表。
- 风险点：cut‑over那一瞬间如果有长事务，会阻塞业务，gh‑ost可配置超时直接放弃，避免卡死。

一句话速记：建空影子表 → 空表执行DDL → 分批拷存量 → 同步增量(触发器/binlog) → 短暂锁表rename交换。

## 八、工程实现

### 自己做一个数据同步需要注意什么

我们做MySQL同步到数仓，首先可以简化理解为同步到一个目标仓。多线程有两种实现思路：第一种是单张大表内部，按照主键或者时间做分片，多线程并行拉同一张表的数据，读取速度快，但写入的时候会变成随机写入，会影响聚簇索引的性能；第二种是线程按表划分，每个线程处理不同的表，冲突少，单表内部数据有序写入，聚簇索引效率更高，小表优先用这种方式，超大表再做表内分片。

然后要处理异常，我们需要独立的元数据存储，持久保存同步进度：包括分片或者表的状态、任务一开始拿到的全局binlog起始位点，如果到了回放阶段，还要记录回放位点。如果某个线程挂掉，只重试失败的分片或者表，不重跑全量；进程整体宕机重启，所有标记处理中的任务全部置为失败重新处理。同时写入必须做幂等，防止重试带来重复数据，靠元数据记录避免漏数据。

再讲同步流程：任务启动第一时间记下全局binlog位点，多线程执行全量同步，每个连接各自做MVCC快照读，多线程情况下拿不到全局统一快照，全量只负责搬运存量。同时我们就开始拉取binlog做缓存，但注意**此时不能回放写入目标仓**，避免全量的旧数据覆盖binlog已经更新好的新数据。

等所有分片、所有表的全量全部跑完之后，才开始从最开始记录的binlog起始位点回放缓存的变更事件。回放的时候要保证同一行的变更有序，直到binlog位点追上源库最新位置，源和目标两边数据就对齐了，之后就进入实时增量同步。

### 数据库不停服迁移

不停机数据库迁移，核心目标是**全程不中断业务、数据最终一致、可灰度、可回滚**，整体分为 **全量同步、增量追平、双写平滑过渡、灰度切流、下线旧库** 五个阶段。

第一阶段，**全量数据迁移** 我会单独搭建一套迁移服务，先把旧库历史全量数据批量迁移到新库，同时做好断点续传，保证大批量数据迁移稳定不崩。

第二阶段，**开启CDC增量同步** 全量跑的同时，迁移服务监听旧库的binlog，持续增量同步新增、修改、删除数据。 这里有个关键：**只要旧库还在写，binlog永远源源不断，不存在绝对对齐的时间点**，所以不能直接一刀切切换读写，会丢瞬时数据。

第三阶段，**开启业务层双写，解决时间窗口缺口** 为了不停写、零停机，我会开启**旧库主写、新库辅写**的双写模式：

1. 业务主逻辑只认旧库成功，**新库写入失败绝不阻塞主业务**；
2. 新库写失败的请求，进入异步重试队列补偿；
3. 此时存在**两套写入链路**：CDC同步旧数据 + 业务双写新数据。

这里会出现你问的**最大坑：重复写入、异步乱序覆盖** 所以工程上必须做两件事：

1. 所有写入、重试全部基于**主键幂等**，避免重复数据；
2. 重试不能无脑覆盖，利用表自带的**update_time 时间戳做条件更新**，只有新库数据更旧才更新，防止老重试覆盖新业务数据。

即使这样，依然存在**跨库读写的极端并发竞态漏洞**，所以必须加兜底：**后台持续数据校验补偿任务**，实时比对新旧库差异，自动修复。

第四阶段，**灰度切流量** 等双写稳定、两边数据一致、延迟极低：

1. 先灰度切换**读流量**到新库，逐步放量，随时可回滚；
2. 观察监控无异常后，再把**写流量完全切到新库**；
3. 关闭业务双写。

第五阶段，**下线同步任务** 写流量切完后，旧库不再产生新数据，CDC彻底无延迟，最后关停增量同步，旧库保留一段时间做回滚兜底，确认稳定再下线。

简单说： **靠全量打底、CDC追增量解决数据同步；靠双写抹平瞬时延迟缺口；靠幂等+时间戳解决异步乱序覆盖；靠数据校验兜底极端并发问题；最后灰度切流实现全程不停服、可回滚、数据一致。**
