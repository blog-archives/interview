##  索引失效的场景

- 使用函数或表达式操作索引列，比如 `WHERE YEAR(create_time) = 2023`
- 隐式类型转换，比如索引列是 INT，查询用 `WHERE id = '123'`，会转成字符串比较导致失效
- 还有 LIKE 以通配符开头，比如 `WHERE name LIKE '%手机'`，索引无法使用
- OR 连接的条件中，如果有一个条件的列没有索引，可能导致所有相关索引失效。
- 另外，联合索引不满足最左前缀原则，比如索引是，查询只用到 b 或 c 列，索引也会失效。
- 还有查询条件用 NOT IN、<>、!= 时，部分情况下索引可能失效。
- 最后，如果 MySQL 评估全表扫描比走索引更快，也会放弃使用索引。

## binlog 和 redo log 区别

binlog 是二进制日志，记录所有数据变更操作，用于主从复制和数据备份，是逻辑日志，会记录 SQL 语句或行变更信息，属于 MySQL Server 层。

redo log 是重做日志，是 InnoDB 存储引擎的日志，记录数据页的物理修改，用于崩溃恢复，确保事务提交后数据能持久化到磁盘，是循环写入的物理日志。

简单说，binlog管“历史记录和复制”，redo log管“崩溃后数据恢复”。

## 索引底层原理

MySQL 最常用的索引是 B+ 树索引，底层基于 B+ 树数据结构。

B+ 树是一种多路平衡查找树，叶子节点按顺序存储所有数据的主键或键值，并且叶子节点之间通过双向链表连接，方便范围查询。非叶子节点只存索引键和指针，不存数据，这样能让更多索引键加载到内存，减少磁盘 IO。

比如 InnoDB 的聚簇索引，叶子节点直接存整行数据，辅助索引的叶子节点存主键，查询时通过辅助索引找到主键，再去聚簇索引取数据。除了 B+ 树，还有哈希索引，适合精确匹配但不支持范围查询，以及全文索引、空间索引等特殊类型。
