## offset 大偏移为什么慢

offset 是逻辑偏移量，不是物理存储位置偏移。

即使走索引，索引只能按字段值快速定位，**不能按行号直接跳转**。要拿到第 1000001 条，仍然需要顺序读取、计数前 100 万条并丢弃，才能拿到目标数据。



> 解决办法

1. 游标分页：利用索引按值定位起点，不用扫描前 M 行。高效，但不适合随机跳转页面。

```sql
-- last_val：上一页最后一条的排序字段值
SELECT * FROM t WHERE id > last_val ORDER BY id LIMIT 20;
```

2. 延迟关联：子查询仅扫描索引拿 id。防御性优化，可以规避意外大量回表；但是治标不治本，仍然需要扫描大量数据。

```sql
SELECT t.* FROM t 
JOIN (SELECT id FROM t ORDER BY id LIMIT 20 OFFSET 1000000) tmp 
ON t.id = tmp.id;
```

3. 其他：业务层面限制大偏移，覆盖索引减少回表缓解



## 分布式主键

核心诉求：**全局唯一、趋势有序、高性能、可解析、避免冲突**，用于分库分表、分布式系统，不能依赖数据库自增（多库会重复）。



1. **数据库步长自增**：简单、数据库原生，ID 严格递增；扩缩容痛苦，仅适用于 MySQL，实例迁移配置错误会 ID 冲突。
2. **UUID**：本地生成、全局唯一；占用存储空间大，**完全无序导致索引性能差**，不可解析。
3. **雪花算法**：基于时间戳 + workerId + 序列号生成，全局唯一、趋势递增，本地生成性能高；**存在时钟回拨导致 ID 重复风险，workerId 需要外部保证全局唯一**。
4. **号段模式（Leaf‑Segment）**：服务预先从数据库申请一批连续 ID；ID 严格递增、无时钟风险，运维可控；依赖数据库，DB 宕机无法申请新号段；**服务重启会浪费未使用的 ID，产生 ID 空洞**。
5. **Redis INCR**：实现简单，原子自增 ID 严格递增；存在 Redis 单点风险，必须开启持久化防止 ID 丢失，高并发下容易成为瓶颈。



> 什么是趋势有序？

整体随着时间推移 ID 越来越大；**不是每一个都连续，后生成的 ID 大概率比先生成的大**。

有序是对数据库友好，可以减轻索引的维护代价。



> 什么是时钟回拨？

机器系统时间往回跳。机器同步 NTP 时间、人为修改服务器系统时间、虚拟机休眠迁移等。



> 什么是雪花算法？

利用预先设置好的机器 id + 当前时间戳生成的 64 位长整型分布式 id。

```text
0 | 41bit 时间戳 | 10bit workerId机器ID | 12bit sequence序列号
```

1. 符号位固定为 0，保证 ID 为正数。
2. 时间戳：不同开源库的位分配可以不一样；**单台机器 ID 趋势递增，多台机器整体趋势有序，不是严格全局递增**。
3. workerId（机器 ID）：需要人为给每个实例分配，**必须全局唯一，否则会出现 ID 重复**。
4. sequence 序列号：同一毫秒内从 0 开始自增；`lastTimestamp`、sequence 属于进程共享变量，实现上必须处理并发安全（加锁），防止单机内生成重复序列号。

- `Using index`：**覆盖索引**，不需要回表，高性能，理想状态

⚠️ 需要优化：

## 锁



### 行锁、间隙锁、临键锁

- Record 行锁：管控已存在的索引记录，可以阻塞 `update`/`delete`
- Gap 间隙锁：管控两条索引记录之间的间隙，只阻塞在这个区间的 `insert`
- Next-Key 临键锁：`(left, right]` 左边的间隙锁+右边的行锁，构成一个原子锁单元



> InnoDB 的行锁是**索引记录锁**，没有独立的物理行锁。

1. **行锁依赖索引；如果无法通过索引定位记录，InnoDB 就无法使用行锁，会退化为对聚簇索引的大量行锁，效果近似表锁**。

​	InnoDB 只能给索引记录加行锁。当 SQL 执行时不走索引，存储引擎无法精准定位要修改的少数索引记录，只能扫描聚簇索引全部记录，给扫描到的每一条聚簇索引记录都加上行锁，最终表现出来就是几乎锁住整张表。注意这不是真正的表锁，是大量行锁的集合，但并发效果和表锁一样差。

2. **通过二级索引做当前读，除了锁住匹配的二级索引记录，还必须锁住对应聚簇索引记录**。

​	二级索引叶子只存索引键 + 主键，不存完整行数据。锁住二级索引记录，仅仅能够阻止其他事务**经由这个二级索引路径访问该行**；其他事务依旧可以拿着主键，直接访问聚簇索引修改这条完整数据。而聚簇索引记录直接对应完整数据行，锁住聚簇索引记录，才能从根源阻止所有访问路径对这条行做修改。所以流程是：先锁定命中的二级索引条目，再根据里面保存的主键，锁定对应的聚簇索引记录。



> 为什么没有索引时，会退化成近似表锁？难道不能只针对符合条件的记录进行上锁吗

没有索引时会走聚簇索引全表扫描。where 条件由 Server 层过滤，InnoDB 引擎事先不知道哪些行符合条件；当前读要求读记录就加锁。

RR 隔离级别下临键锁的记录锁和间隙锁绑定，扫描过的记录即便不匹配条件，锁也不能中途释放，否则间隙锁失效会出现幻读。

因为缺少条件字段对应的索引，间隙锁只能基于聚簇索引生效，粗暴锁住全部记录和间隙，所有写操作都会阻塞。底层是行锁 + 间隙锁集合，快照读不受影响，写效果等价表锁。

RC 隔离级别没有间隙锁，不匹配行会释放锁，不会出现这个现象，但 RC 不能防幻读。



### 为什么需要临键锁

- 目的：RR 隔离级别下，**针对当前读，解决幻读问题**。

- 幻读定义：同一个事务内，多次执行**相同的范围读**，返回结果集行数发生变化（主要是别的事务插入了新行）。

- 解决思路：

  - Record 行锁：锁住已经存在的匹配记录，防止别人修改 / 删除；

  - Gap 间隙锁：锁住记录之间的间隙，**阻止其他事务向该间隙插入新记录**；

    两者配合，让查询的整个区间 “写封闭”，避免幻读。



原生问题：如果分开实现，先拿 `Gap(left, right)`，再拿 `Record(right)`。

- Gap 保护 `(left,right)`，阻止往间隙插入；
- 但 **right 这条已经被选中的目标记录，此时还没有行锁**，其他事务可以 update /delete right；
- 这是严重并发 bug：**本应被保护的目标记录出现裸奔窗口**。
- 所以 InnoDB 将 `Gap(left, right)` 与 `Record(right)` 合并为**原子的临键锁 `(left, right]`**：二者要么同时拿到，要么都拿不到，消除单条记录的裸奔窗口。



范围查询 / 普通索引等值，需要游标迭代，**依次获取多把临键锁 `(L1,R1]`、`(L2,R2]` …**

- 多把临键锁之间并不是一次性原子全部获取，是迭代时序上先后拿到。
- ✅这不是 bug，和上面的裸奔漏洞本质不一样：
  - 每一把临键锁内部，`Gap+Record`是原子；已经处理完的记录，锁是完整的，不存在目标记录裸奔；
  - 还没有获取的下一段临键锁，对应的记录 / 间隙还没有被游标访问，还不是本次待保护对象；
  - 靠`index->next()`原语：**迭代下一条之前预先拿后方 Gap 锁**，并且单条 SQL 引擎内部连续执行，没有可被并发利用的调度窗口，规避幻读。



## 事务



### ACID 如何实现

> **A 原子性 Atomicity：要么全成要么全回滚**

靠 **undo log（回滚日志）**。失败时，通过 undo log 回滚已经做过的数据修改；提交就丢弃 undo。



> **C 一致性 Consistency：事务结束所有约束合法**

C 是最终目标，**不单独由某一个日志实现**。

由 A (undo) + I (锁 / MVCC) + D (redo) + 表约束（主键、外键、check）共同达成。业务规则需要代码 / 约束自己写。



> **I 隔离性 Isolation：并发事务互不干扰**

靠 **锁 + MVCC（read‑view + undo log）**。

- 写：行锁、gap 锁防止写冲突；
- 读：MVCC 多版本，读历史快照，避免脏读不可重复读；



> **D 持久性 Durability：提交后修改永久生效，宕机不丢**

靠 **redo log（重做日志）**。事务提交先写 redo log 落盘，再异步刷磁盘数据页；宕机重启用 redo log 重放已经提交的变更。



## InnoDB



### 四大特性



> Change Buffer 变更缓冲

针对非唯一二级索引，增删改操作会先缓存在内存 change buffer 区域，延迟合并磁盘写入，减少随机 IO。



> Double Write 双写

脏页刷回磁盘前，先将数据写到共享空间的 doublewrite buffer（磁盘）。将单次高危写操作拆成两次，防止宕机产生半页写损坏，保证数据页完整。



> 自适应哈希索引

自动对热点的索引等值查询构建内存 hash，加速等值查询。



> Read Ahead 预读

提前把可能要读的数据页加载到 buffer pool，减少等待磁盘 io
