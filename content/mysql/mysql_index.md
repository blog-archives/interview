## 索引是什么

索引类似书的目录，用来减少扫描的数据量，提高查询效率。

从实现上看，索引是额外维护的一种数据结构，常见如 B+ 树、哈希表等。它保存了关键字，以及定位数据所需的信息：在 InnoDB 里，聚簇索引叶子节点直接存整行数据，二级索引叶子节点通常存主键；在 MyISAM 里，索引更常指向数据文件中的位置。查询时先走索引定位，再读取目标数据，而不是全表扫描。本质上是用额外的存储和维护成本，换查询速度。

## 索引的分类

- 按「数据结构」：B 树索引、B+ 树索引、哈希索引、R 树索引
- 按「物理存储」：聚簇索引、非聚簇索引
- 按「功能用途」：普通索引、唯一索引、主键索引、全文索引、空间索引
- 按「字段个数」：单列索引、联合索引

## 哈希索引的使用场景

适合高频等值查询，条件主要是 `=` 或 `IN`，例如按用户 ID 查资料、按订单号查订单。

不适合范围查询、排序和模糊查询，因为哈希值本身无序。MySQL 的 Memory 引擎支持显式哈希索引；InnoDB 内部还有自适应哈希索引，由引擎自动维护，不能手动创建。

## 聚簇索引和非聚簇索引

从存储方式看：聚簇索引的叶子节点直接存放完整数据行，找到索引就基本拿到整行；非聚簇索引（二级索引）的叶子节点存放的是主键或数据地址，通常还要再回表才能拿完整行。一个表通常只有一个聚簇索引，非聚簇索引可以有多个。

**唯一性**：InnoDB 的聚簇索引一般由主键构成，数据只能按一种顺序组织，所以聚簇索引只有一份；二级索引不决定整表的物理排列，因此可以建多个。

**效率**：范围查询、排序时，聚簇索引通常更有优势，因为叶子节点本身就是有序数据。二级索引若能覆盖查询所需列，可以避免回表，效率也很好；一旦需要回表，额外开销就会上来。

### 什么是覆盖索引

覆盖索引指：查询需要的列都已包含在索引中，不必再回表取数据。例如 `SELECT id, name FROM t WHERE name = 'Tom'`，若存在 `(name, id)` 索引（InnoDB 二级索引本身也会带上主键），往往可以直接从索引返回结果。

### 什么是回表

回表指：命中二级索引后，叶子节点只有主键（或数据地址），还要再拿这个主键去聚簇索引（或数据文件）查找完整行。例如用 `name` 上的二级索引查出主键，再回主键索引取整行，这第二次查找就是回表。

## 更新数据时，聚簇索引的结构和存储是否变化？

取决于更新的是不是聚簇索引列（通常是主键）。

- 更新聚簇索引列：记录需要按新键值重新定位存放，索引结构和存储位置都会变化，开销很大，所以主键一般不要轻易改。
- 更新非聚簇索引列：聚簇索引的排序键没变，树的整体结构通常不变，但叶子节点里的行内容会更新；若该列也存在于某个二级索引中，对应二级索引同样要维护。

## 什么字段适合当主键

- 具备唯一性，且不能为空
- 最好具有递增趋势；随机无序插入更容易引发页分裂，影响写入性能
- 不建议直接拿业务字段当主键（如会员卡号、订单号），因为业务规则后续可能变化，出现重复、重用或变更，主键一旦变动成本很高

## 性别字段能加索引吗？

通常不建议。

核心原因是取值很少，且各值占比往往接近，区分度极低。例如男女大约各占一半时，整体区分度约为 `2 / 总行数`，查任一性别都可能扫到近一半数据，索引收益很小，却还要承担维护成本。只有某个取值极度稀有、查询又总命中这个稀有值时，才可能有一点索引价值，但性别字段很少出现这种分布。

### 如何判断一个字段是否值得建立索引

可以先看区分度，再看具体查询值的选择性：

1. 看字段整体区分度：

    ```sql
    SELECT COUNT(DISTINCT 字段名) / COUNT(*) AS selectivity
    FROM 表名;
    ```

    结果越接近 1，区分度通常越好；结果极低，说明重复值太多。

2. 看常用查询条件命中的行占比：

    ```sql
    SELECT
        SUM(字段名 = '常用查询值') / COUNT(*) AS value_ratio
    FROM 表名;
    ```

    占比越高，说明一次查询要扫的数据越多，索引越难带来明显加速。

## 主键用自增 ID 还是 UUID

多数单机或简单分表场景，更建议自增 ID。

- 自增 ID 是整数，比 UUID 更省空间，二级索引也会更瘦，缓存命中率通常更好。
- 自增插入基本追加到索引末尾，页分裂更少；UUID 随机写入容易打散页，带来更多页分裂和随机 IO。
- 自增 ID 在排序、分页上通常更友好。
- UUID 的优势主要在分布式下更易生成全局唯一 ID；若确有分布式需求，也可以考虑雪花算法、有序 UUID 等方案，而不是直接用完全随机的 UUID 当主键。

### 页分裂

InnoDB 以页（默认 16KB）为单位管理数据和索引。顺序插入时，新数据通常追加到末尾页；页满了就分配新页，对已有页影响小。

如果插入值随机，新记录可能落到中间某个已满页，这时要把该页拆成两页，并调整页与页之间的链表关系，这就是页分裂。随机 UUID 更容易触发页分裂；自增 ID 多数时候是追加写入，所以更稳。

### 随机 IO

随机 IO 指读写位置不连续，磁头或页缓存需要频繁跳转，吞吐较差。顺序 IO 则沿着连续位置读写，效率更高。

UUID 主键随机插入时，写入位置分散，更容易放大随机 IO；自增主键写入更接近顺序追加，通常更友好。

## 索引是怎么实现的

MySQL InnoDB 的索引主要基于 B+ 树。

B+ 树是多路平衡树：非叶子节点主要存索引键和指向子节点的指针，真正的数据在叶子节点。节点内部按索引键有序排列；对主键（聚簇）索引来说，叶子节点存的是完整行，对二级索引来说，叶子节点存的是二级键加上主键。叶子节点之间通过指针连成双向链表，方便范围扫描。

![](/assets/iShot_2026-08-04_20.25.10.png)

得益于较高的扇出，千万级数据通常只需 3 到 4 层就能放下，也就意味着定位一条数据往往只要几次磁盘 I/O。和二叉树、普通 B 树相比，B+ 树更适合磁盘存储，查询和范围遍历都更高效。

## 查询数据时，到了叶子节点后，怎么找到具体的数据？

进入叶子节点对应的数据页后，页内记录会按主键顺序串成单向链表。链表便于插入删除，但检索时最坏要遍历整页，所以 InnoDB 又在页内维护了「页目录」来加速定位。

![](/assets/iShot_2026-08-04_20.36.43.png)

1. 把页内记录分成若干组，包含最小记录、最大记录，但不包含已删除记录。
2. 每组最后一条记录是组内最大记录，其头信息里的 `n_owned` 记录该组有多少条记录。
3. 页目录保存每组最后一条记录的地址偏移量，这些偏移量按顺序排成若干槽（slot）；每个槽相当于指向一个分组尾记录的指针。

查找时，先对页目录做二分，快速定位目标大概在哪个槽（哪个分组），再在该组内沿着记录链表顺序查找。这样不必每次都从最小记录开始扫完整页。
