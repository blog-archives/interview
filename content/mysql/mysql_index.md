## 索引是什么

索引类似书的目录，可以减少扫描的数据量，提高查询效率。

从物理角度说，索引在计算机里通常是一种单独存储的数据结构，比如 B 树、哈希表等，它记录着数据的关键字和对应数据在内存或磁盘中的物理地址。当需要查询数据时，系统会先查索引，通过关键字快速找到物理地址，再直接读取对应的数据块，而不是遍历所有数据。简单讲，它就是用额外的存储空间换查询速度的一种技术实现。

## 索引的分类

- 按「数据结构」分类：B 树索引、B+ 树索引、哈希索引、R 树索引；
- 按「物理存储」分类：聚簇索引、非聚簇索引；
- 按「功能用途」分类：普通索引、唯一索引、主键索引、全文索引、空间索引。
- 按「字段个数」分类：单列索引、多列索引。

## 哈希索引的使用场景

适合高频等值查询的场景。比如根据用户ID查信息、订单号查订单，这些场景查询条件基本是 `=` 或 `IN`。

不适合范围查询、排序或模糊查询，因为哈希值无序。像 Redis 的哈希类型、MySQL 的 Memory 引擎表，在这类场景下会用到哈希索引。

## 聚簇索引和非聚簇索引

从物理存储看，聚簇索引的叶子节点直接存储数据行，查询时找到索引就能拿到完整数据；非聚簇索引的叶子节点存储的是数据行的地址或主键，需要再通过地址或主键回表查询完整数据。一个表通常只能有一个聚簇索引，而非聚簇索引可以有多个。

**唯一性**：聚簇索引通常是基于主键构成的，因此每个表只能有一个聚簇索引，因为数据只能有一种物理排序方式；一个表可以有多个非聚簇索引，因为他们不直接影响数据的物理存储位置。

**效率**：对于范围查询和排序查询，聚簇索引通常更有效率，因为它避免了额外的寻址开销。非聚簇索引在使用覆盖索引进行查询时效率更高，因为他不需要读取完整的数据行。但是需要进行回表的操作时，使用非聚簇索引效率比较低。

### 什么是覆盖索引

覆盖索引就是索引包含了查询语句中所有需要返回的列，不用再去数据行里找其他字段。比如查询 `SELECT id, name FROM table WHERE id=1`，如果有个索引包含 `id` 和 `name`，那查这个索引就够了，不用回表读数据行，这就是覆盖索引。

### 什么是回表

回表就是当查询命中非聚簇索引时，索引叶子节点只存了主键或数据地址，需要再根据这个主键或地址去聚簇索引或数据文件里查找完整数据行的过程。比如用非聚簇索引查 `name`，先找到索引里的 `name` 对应主键，再用主键去聚簇索引找整行数据，这个「再找一次」的步骤就是回表。

## 更新数据时，聚簇索引的结构和存储是否变化？

这取决于更新的列是否为聚簇索引列。

- 如果更新的是聚簇索引列，数据行需要按新索引值重新排序存储，所以结构和存储会变化；
- 如果更新的是非聚簇索引列，聚簇索引的排序依据没变，结构不变，但叶子节点存的完整数据行内容会更新。

## 什么字段适合当主键

- 字段具有唯一性，且不能为空的特性
- 字段最好是有递增趋势的。如果值是随机无序的，可能会引发页分裂的问题，造成性能影响。
- 不建议用业务数据作为主键（比如会员卡号、订单号等），因为无法预测未来会不会因为业务需要，而出现业务字段重复或者重用的情况。

## 性别字段能加索引吗？

性别字段通常不建议加索引。

核心原因是 **“值数量少”** 和 **“实际数据中各值占比均衡”** 共同导致区分度极低。比如男女各占 50% 时，区分度仅 `0.5 / (总记录数)`，查询任一性别都会扫描近一半数据，索引无法有效加速，反而增加维护成本。只有当某一性别占比极低时，区分度才可能支持索引生效，但这种情况在性别字段上极少出现。

### 如何判断一个字段是否值得建立索引

可以分两步用 SQL 判断

1. 查字段整体区分度：

    ```sql
    SELECT COUNT(DISTINCT 字段名)/COUNT(*) AS selectivity FROM 表名;
    ```

    如果结果极低，说明值少，区分度基础差。

2. 查常用查询条件中具体值的占比：

    ```sql
    SELECT COUNT(*) FROM 表名 WHERE 字段名='常用查询值' / COUNT(*) AS value_ratio;
    ```

## 主键用自增 id 还是 uuid

建议用自增 ID。

- 自增 ID 是整数，存储空间比 UUID 小很多，索引效率更高。
- 自增 ID 插入时能保持主键有序，减少页分裂，提升写入性能；而 UUID 是随机字符串，插入时主键无序，会导致频繁的页分裂和磁盘随机 IO。
- 自增 ID 查询时排序、分页更高效，UUID 的随机性会让这些操作变慢。
- 虽然 UUID 能避免分布式 ID 冲突，但对大部分单表或简单分表场景，自增 ID 足够且优势更明显。

### 页分裂

数据库存数据和索引时，会把数据分成一块一块的“小本子”，每本有固定页数，每页写满了就不能再写。如果插入的数据是按顺序来的，就一直往最后一页写，等最后一页写满了，再新开一本小本子，原来的小本子不用动。

但如果插入的数据是随机的，可能插到中间某本的某一页，这页要是满了，就得把这页撕开，一半数据放新页，还得调整前后页的关系，这就是页分裂。随机的 UUID 插入时经常要撕页，而自增 ID 基本不用撕，所以性能更好。

### 随机 IO

随机 IO 就像看书时，不按页码顺序，一会儿翻到第 5 页，一会儿翻到第 200 页，每次翻页都要找半天位置。

数据库里，随机 IO 指读取或写入数据时，数据在磁盘上的位置不连续，需要频繁移动磁头去定位，速度很慢。比如 UUID 是随机的，插入时数据可能分布在磁盘的不同位置，就会产生很多随机 IO；而自增 ID 是顺序的，数据都存在连续的磁盘块，磁头不用来回动，就是顺序 IO，速度快很多。

## 索引是怎么实现的

MySQL InnoDB 引擎是用了 B+ 树作为索引的数据结构。

B+ 树是一种多叉树，叶子节点才存放数据，非叶子节点只存放索引，而且每个节点里的数据是按主键顺序存放的。每一层父节点的索引值都会出现在下层节点的索引值中，因此在叶子节点中，包括了所有的索引值信息，并且每一个叶子节点都有两个指针，分别指向上一个和下一个叶子节点，形成一个双向链表。

![](/assets/iShot_2026-08-04_20.25.10.png)

B+ 树存储千万级别的数据只需要 3-4 层高度就可以满足，这意味着从千万级别的表中查询目标数据最多需要 3-4 次磁盘 I/O，所以 B+ 树相比于 B 树和二叉树来说，最大的优势在于查询效率很高。

## 查询数据时，到了叶子节点后，怎么找到具体的数据？

数据页中的记录按照主键顺序组成单向链表，单向链表的特点就是插入、删除非常方便，但是检索效率不高，最差的情况下需要遍历链表上的所有节点菜呢完成检索。

因此，数据页中有一个页目录，起到记录的索引作用。

![](/assets/iShot_2026-08-04_20.36.43.png)

1. 将所有的记录分成几个组，这些记录包括最小记录和最大记录，但不包括标记为已删除的记录。
2. 每个记录组的最后一条记录就是组内最大的那条记录，并且最后一条的记录的头信息中会存储改组一共有多少条记录，作为 n_owned 字段
3. 页目录用来存储每组最后一条记录的地址偏移量，这些地址偏移量会按照先后顺序存储起来，每组的地址偏移量也被称之为槽（slot），每个槽相当于指针指向了不同组的最后一个记录。

页目录就是有多个槽组成的，槽相当于分组记录的索引。然后，因为记录是按照主键值从小到大排序的，所以我们通过槽查找记录时，可以使用二分法快速定位到要查询到记录在哪个槽（哪个记录分组），定位到槽后，再遍历槽内到所有记录，找到对应的记录，无需从最小记录开始遍历整个页中的记录链表。
