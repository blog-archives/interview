## 执行一条 SQL 请求的过程

当 MySQL 收到一条 SQL 请求时

1. 首先会经过 **连接池** 处理，验证连接合法性。
2. 然后进入 **解析器**，对 SQL 进行词法和语法分析，生成解析树。
3. 接着是 **预处理器**，检查表、字段是否存在，处理别名等，得到预处理后的解析树。
4. 之后 **优化器** 会根据索引、统计信息等选择最优执行计划，比如决定是否走索引、连接顺序等。
5. **执行器** 再根据执行计划，调用存储引擎的接口执行操作，比如 InnoDB 的读取或写入。
6. **存储引擎** 层会处理数据的存储和检索，包括缓存、锁、事务等，最后将结果返回给客户端。

> 这个过程中，查询缓存在 MySQL 8.0 已移除，所以主要是 **解析**、**优化**、**执行** 这几个核心步骤。

> 如果是问“一条SQL请求的过程”，通常默认是在已建立连接的前提下，所以重点讲解析、优化、执行等步骤。但如果问题涉及“从客户端发起请求到返回结果的完整流程”，就需要包括连接建立时的连接器验证步骤。具体看问题的上下文范围，日常开发中讨论单条SQL执行过程，一般可以不提重复的连接验证，只说连接复用后的处理阶段。

## 为什么 InnoDB 时默认引擎

因为 InnoDB 在功能和性能上更符合现代业务需求。

1. 事务支持：它支持 ACID 事务，能保证数据一致性，这是很多业务的基础
2. 并发性能：行级锁机制让并发读写效率更高，适合高并发场景
3. 崩溃恢复：通过 redolog 日志实现了崩溃恢复，可以在数据库发生异常情况（如断电、系统崩溃等）时通过日志文件进行恢复，保证数据的持久性和一致性

相比之下，早期默认的MyISAM不支持事务和行锁，在数据安全和并发处理上有明显短板。MySQL从5.5版本开始将InnoDB设为默认引擎，就是为了更好地满足企业级应用对事务、并发和可靠性的要求。

## InnoDB 和 MyISAM 的不同

||InnoDB|MyISAM|
|---|---|---|
|事务支持|支持|不支持|
|索引结构|聚簇索引。聚簇索引的文件存放在主键索引的叶子节点上，因此 InnoDB 必须要有主键，通过主键索引效率很高。但是辅助索引需要两次查询，先查到主键，然后在通过主键查询到数据。因此主键不应该过大。|非聚簇索引。数据文件是分离的，索引保存的是数据文件的指针。主键索引和辅助索引是独立的。|
|锁粒度|最小粒度是行锁|最小粒度是表锁。一个更新语句会锁住整张表，导致其他查询和更新都会被阻塞，因此并发访问受限|
|count 的效率|不保存具体行数，执行 count(*) 会全表扫描|保存了表的总行数，执行 count(*) 时直接返回结果|

## 数据文件大体分成哪几种

- `db.opt`：存储数据库的元数据信息，如字符集、排序规则等
- `*.frm`：存储每个表的元数据信息，主要包含表结构定义、存储引擎类型、表选项等
- `*.ibd`：是 InnoDB 存储引擎的表空间文件，存储对应表的数据和索引，包括聚簇索引和二级索引的数据，还包含 undo 日志、插入缓冲等 Inno DB的内部数据结构。如果启用了独立表空间，每个表会有单独的 .ibd 文件；如果是共享表空间，多个表的数据会存到 ibdata1 等文件中。
