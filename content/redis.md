### ziplist 和 listpack

都是连续内存的紧凑结构，用来优化少量数据，节约内存，查找时间复杂度 O (n)。

- ziplist 每个节点记录上一个元素的长度，修改数据可能发生连锁更新，一连串内存重分配，性能抖动；
- listpack 把字段改成记录自身长度，元素之间互不干扰，彻底解决连锁更新，Redis7.0 之后全面替换 ziplist。

redis 7.0 之后 ziplist 升级为 listpack

## 二、核心原理与线程模型

### redis 为什么这么快

Redis 快主要因为数据存内存；主线程单线程执行命令避免锁与上下文切换；IO 多路复用高效处理大量连接；搭配自研优化的数据结构、简单网络协议。

### Redis 为什么设计为单线程

Redis 核心操作是内存读写，CPU 不是主要瓶颈，单线程可以避免锁竞争与线程切换开销，天然保障命令、事务、Lua 脚本的原子性；结合 IO 多路复用，单线程就足以支撑高并发，实现简单。

### 6.0 为什么引入多线程

高并发、万兆网卡场景下，socket 读写和协议解析占用大量 CPU，成为网络瓶颈，多核资源浪费。6.0 新增 IO 多线程，仅将网络读写、协议解析交给线程池并行处理，命令执行仍保持主线程串行，不破坏原有语义，以此提升网络吞吐，该功能默认关闭。

## 三、持久化

### 持久化机制

RDB 定时快照备份，AOF 追加每条写操作

### 生成 RDB 文件时如何处理请求

bgsave 做 RDB，fork 瞬间短暂阻塞主线程；fork 完成后主进程正常处理客户端请求；依靠写时复制，子进程快照 fork 时刻的数据，后续新写入不会进入本次 RDB；`save`同步方式全程阻塞所有请求。

## 四、缓存

### 数据库与缓存一致性

- 旁路缓存：先更新数据库，再删缓存。存在极小的窗口可能读到久数据
- 先删缓存，再更新数据库：有脏数据的风险
- 延迟双删：删缓存 - 更新数据库 - 休眠一段时间再删一次缓存。休眠时间不好把控

要求强一致性时怎么半

- 放弃缓存
- 读写分布式锁、串行化访问
- 旁路缓存+版本号

### 缓存击穿

热点 key 在失效瞬间大量请求打到数据库

逻辑过期或永不过期避免物理失效（过期时间存在 value 里，后续异步更新），互斥锁控制只有一个线程加载数据

### 缓存穿透

查询根本不存在的数据导致每次请求都落库

布隆过滤器，缓存空值

### 缓存雪崩

大面积缓存同时失效，大量请求击穿到数据库

过期时间加随机值，避免集体同时过期

### 热点 key 问题的解决方案

本地缓存、主从读写分离、多副本 key（缓解集群模式下的读压力，但是加大写难度）、key 拆小、

## 五、事务、批处理与脚本

### 原生批处理命令和 pipeline 的区别

服务端原生批命令，具备原子性，一次网络往返，但 key 数量有限制。Pipeline 是客户端通信优化，合并多条命令一起收发减少往返时延，Redis 内部仍然逐条执行，**没有原子性，其他客户端命令可以穿插进来**。要原子批量选 MSET/MGET；不需要原子、追求吞吐选 Pipeline。

### redis 事务和关系型数据库事务的区别

Redis 事务仅保证 EXEC 执行阶段命令串行不被其他请求插入，**不支持错误回滚，本质是命令排队执行**。

### Lua 脚本

原子执行，减少网络开销，eval

### pipeline

批量打包命令，减少网络开销；无原子性

## 六、Big Key 与过期策略

### 数据过期后的删除策略

1. **惰性删除（被动删除）** key 过期不会立刻删，**等下次访问该 key 的时候**，才检查过期时间，如果已过期就删除并返回不存在。 优点：不耗 CPU；缺点：如果 key 再也不被访问，会一直占内存。
2. **定期删除** Redis 会**每隔一段时间随机抽取一批设置了过期的 key**，检查并删除其中过期的 key，循环执行。 不是扫描全库，避免长时间阻塞主线程；只能减少过期 key 堆积，不能保证全部清理干净。

### big key

BigKey 是指单个 key 对应的的 value 过大

危害：

- 内存分配与释放压力大
- 查询、遍历耗时久
- 影响迁移速度
- 网络传输占满带宽

方案：

- 拆分 key
- 分批遍历、删除

## 七、分布式锁

### redission 分布式锁原理

Redisson 用 Lua 脚本基于 Hash 实现可重入锁，记录客户端线程标识与重入计数；看门狗后台自动续期避免业务未完成锁过期；释放锁同样 Lua 原子校验归属、递减计数；抢锁失败订阅锁释放消息等待。

### red lock 红锁

Redlock 红锁，使用多套独立 Redis 主节点，必须半数以上节点加锁成功才算获取锁，解决单节点 / 主从切换锁丢失问题；但依赖系统时间，GC 停顿、时钟漂移会破坏锁安全，生产很少用。

### 分布式锁的主从切换导致锁失效问题

真要高可靠，建议直接上 ZooKeeper 或 etcd，它们基于一致性协议，天生能保证锁的安全性，就是性能低点。Redis 锁追求的是高性能，牺牲了一定安全性，得清楚这个权衡。

## 八、发布订阅

### 发布订阅功能

Redis 发布订阅是广播机制，publish 发送消息到频道，subscribe 订阅接收；消息不持久化，离线消息直接丢失，无 ack 确认，不适合做可靠 MQ，多用于简单实时通知场景；可靠消息优先使用 Redis Stream。

## 十、性能

### 性能瓶颈时如何处理

先用 `INFO stats`, `INFO memory`, `redis-cli --latency` 观察指标，看时 CPU、内存、网络、磁盘指标；同时配合 `SLOWLOG`, `INFO commandstats` 定位慢命令。

- CPU 没到顶但是 QPS 上不去，可能是大 key 或慢查询拖累；考虑将 keys 替换为 scan、拆分大 key
- 如果是整体读写压力大，做横向扩展，搭建集群（集群无法解决热点 key 问题）
- 如果存在热点 key，极端场景在应用层增加本地缓存，拦截最热流量
- 如果是持久化磁盘 IO 瓶颈，调整 RDB/AOF 策略，避免 fork 阻塞主线程

## 十一、集群

### 主从复制的拓扑结构

1. **一主一从**：最简单，用于备份和小规模读写分离。
2. **一主多从**：生产常用，多个从节点直接连主节点，分担读压力，但主节点复制带宽压力随从节点数量上升。
3. **树状级联复制**：从节点下面继续挂载从节点，减轻顶层主节点同步压力；代价是复制延迟随层级变大。

### 主从复制流程

Redis主从复制由**从节点主动发起**。从节点执行 replicaof 命令，与主节点建立TCP长连接后，发送携带主节点runid和自身复制偏移量offset的PSYNC同步请求，开启数据同步。

主节点收到请求后做双重校验：核对runid是否匹配、offset对应数据是否保存在复制积压缓冲区。校验通过则执行**部分重同步**，仅补发offset之后的增量命令，无需传输RDB，快速完成同步。

若runid变更，或offset数据已被缓冲区覆盖，会触发**全量同步**。主节点fork子进程生成RDB快照发送给从节点，从节点清空本地数据并加载快照。同时主节点将同步期间的新增写命令存入积压缓冲区，待快照加载完成后补发增量命令，保障数据完整。

初始化同步完成后，进入常态化增量复制阶段。主节点执行写命令后，会异步转发给从节点回放，双方实时更新offset偏移量。主从复制默认异步执行，主节点无需等待从节点完成，直接响应客户端，性能高效。

复制链路全程依靠**心跳机制**维持稳定：默认从节点每秒向主节点发送心跳包，上报自身offset和同步状态。若主节点超时未接收心跳，判定从节点失联；若从节点未收到主节点响应，会主动重连重试同步，确保链路持续可用。

### 主从复制延迟的常见原因

- 网络延迟、带宽跑满
- 主节点侧问题
    - 大内存实例执行 fork 生成 RDB 时，fork 调用阻塞主节点主线程，复制流推送暂停，同时生成、传输、加载更大的 RDB 文件耗时增加，共同导致主从复制延迟升高。
    - 缓冲区太小，断线重连经常出发全量同步
    - 主节点 CPU 打满，忙着处理业务请求，没空推送复制流
- 从节点侧问题：磁盘 IO 慢或 CPU 压力高，跟不上主节点的更新速度
- 架构原因：链式联级复制时，复制是一层一层往下传递的

### 集群模式和哨兵模式的区别

哨兵模式底层仍是一主多从，只负责自动故障切换，**不能分片扩容，写能力无法扩展**；Redis Cluster 通过 16384 哈希槽做数据分片，多主分担读写压力，同时自带故障转移能力，可以横向扩容存储与写性能。

### 集群的实现原理

Redis Cluster 使用 16384 个哈希槽分片数据，CRC16 算法计算 key 所属槽；节点之间依靠 Gossip 协议同步集群元数据；每个主节点分配部分槽，搭配从节点，通过集群投票完成故障转移；多 key 操作需要 hash tag 保证同槽，不支持跨节点事务。

### 集群模式下某个主节点宕机会怎么样

1. **该主配置了从节点（生产标准部署）** 集群节点间检测故障，投票完成故障转移，它的从节点晋升为新主，接管原有hash槽；集群继续正常对外服务。 ⚠️复制是异步，主还未同步到从的少量新写入数据有丢失风险。
2. **该主没有配置从节点** 它负责的hash槽无节点接管，标记为失败；**整个集群进入FAIL状态，全部槽拒绝读写**，该分片数据丢失。只能重启原节点恢复，或手动剔除节点放弃数据。

### 哨兵机制

哨兵集群监控 Redis 主从；单哨兵超时无响应为主观下线；达到指定数量哨兵一致判定故障，进入客观下线；自动选从升主，其他从切换复制新主，完成故障转移；哨兵不提供分片功能。

### 集群模式下的脑裂

网络分区后被隔离的旧主不会自己退位，与新主同时接收写入

`cluster‑require‑full‑coverage`可以拒绝不完整槽的写请求做缓解，但不能完全消除。

1. **确认真实集群状态** 逐个连接**所有集群节点**，执行 `cluster nodes`。 统计输出结果：大多数节点共识的主、槽分配，就是集群真实状态；少数被隔离节点的视图直接忽略。

   识别旧主：节点自身认为自己持有哈希槽，但其他多数节点标记它为fail，就是分裂的旧主。

2. **隔离旧主** 防火墙阻断业务访问该旧主，仅保留运维访问，阻止继续写入脏数据，不要直接重启。

3. **业务全部切到真实集群** 业务使用集群客户端，禁止硬编码节点IP；确认不再访问隔离旧主。

4. **处理旧主数据**

   - 允许丢失隔离期间写入的数据：执行`cluster reset hard`清空旧主数据，再让它重新加入集群同步。

   - 不能丢数据：先备份旧主RDB，业务脚本人工比对合并脏数据，完成后再reset加入集群。

1. **事后加固** 开启`cluster‑require‑full‑coverage yes`；节点跨机架部署；调优`cluster‑node‑timeout`。

### 哨兵模式下的脑裂

普通主从无脑裂：网络分区时旧主与哨兵、从节点断连但进程存活。哨兵判定旧主下线，选举出新主；被隔离的旧主不知道自己已被罢免，仍接受写请求，集群出现两个可写主，引发数据不一致。

配置`min‑replicas‑to‑write N`，主节点必须有至少 N 个正常同步的从节点才允许写。隔离后旧主连不上从节点，主动拒绝写入。

1. **确认集群真实状态** 逐个连接**所有哨兵节点**，执行 `sentinel master mymaster`。 统计返回结果：大部分哨兵报出的主IP就是**合法新主**；少数哨兵返回旧主IP，该结果直接忽略。仍可写入、但不是合法新主的那台Redis，就是脑裂旧主。

2. **隔离脑裂旧主** 防火墙/安全组阻断业务机器访问旧主Redis，只保留运维登录权限，**不要直接重启旧主**，停止继续写入脏数据。

3. **业务切换** 全部业务统一走哨兵获取主节点地址，移除所有硬编码Redis IP，确认业务已经全部访问合法新主。

4. **处理旧主数据**

   - 可接受脑裂期间数据丢失：旧主执行 `replicaof 新主IP 端口`，自动全量同步成为从节点。

   - 不能丢数据：先备份旧主RDB，业务脚本人工对比合并两份数据，合并完成后再把旧主设为从。

1. **事后加固** 配置`min‑replicas‑to‑write`；哨兵跨机架部署，核对quorum参数。
