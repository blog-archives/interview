## 一、常见的数据类型

### String 底层结构

动态数组 `len+free+buf[]`

**String 最大 value 与大 value 问题：**

Redis String 类型最大 value 为 512MB。但业务中存大 value 会带来严重问题：

- 内存分配与释放压力大，容易造成内存碎片；
- 查询、遍历耗时久，阻塞单线程主线程；
- 网络传输占满带宽，一次大 value 读取可能占用大量网络IO；
- 影响数据迁移速度（RDB/AOF重写、主从同步）；
- 集群模式下大 key 无法在节点间拆分，单个节点压力大。

业务方案：将大 value 拆分成多个小 key（如按字段拆分、按时间分片），或存到对象存储（OSS/S3）中，Redis 只存引用地址。

### Set 实现原理

压缩链表、跳表

### zset 与跳表

zset（有序集合）底层使用**跳表（Skip List）** + 哈希表实现。哈希表用于O(1)查找成员的score，跳表用于按score范围查找和排序。

**跳表对比平衡树（如红黑树）的优势：**

1. **实现简单**：跳表通过随机层级实现，代码比平衡树的旋转操作简单得多；
2. **范围查询高效**：跳表底层是有序链表，范围查询（zrangebyscore）只需找到起点后沿链表遍历，平衡树需要中序遍历，更复杂；
3. **插入删除更简单**：跳表插入删除只需要修改相邻节点指针，平衡树需要旋转维护平衡；
4. **并发友好**：跳表的修改局部性更好，加锁粒度更小。

**zrangebyscore 业务场景：** 按分数范围查询有序集合，常用于排行榜（如游戏积分榜、热度榜）、时间线（按时间戳范围查询消息）、延迟队列（按执行时间排序）。

**zset 百万数据性能：** 跳表查找时间复杂度O(log n)，百万级数据查找约20次比较，性能依然很好。但范围查询返回大量元素时，网络传输和序列化开销会成为瓶颈。

### Hash 与 String 序列化选型

**Hash 结构适用场景：** 对象的多个字段需要独立读写，如用户信息（name、age、email）。

**Hash vs String 序列化 JSON 对比：**

| 维度 | Hash | String + JSON |
|------|------|---------------|
| 字段读写 | 可以单独读写某个字段（HGET/HSET），不需要读取整个对象 | 读写任何字段都需要读取/写入整个JSON字符串 |
| 内存占用 | 小数据量时用ziplist/listpack紧凑存储，更省内存；字段多时编码转换后开销大 | JSON字符串有字段名重复开销，但整体可压缩 |
| 序列化 | 无序列化开销，直接存 | 需要JSON序列化/反序列化，有CPU开销 |
| 过期控制 | 只能对整个key设置TTL，不能对单个字段过期 | 整个key过期，同样不能字段级过期 |
| 嵌套结构 | 不支持嵌套（value只能是字符串） | 支持任意嵌套JSON结构 |
| 适用场景 | 对象字段需要独立更新、字段少且固定 | 对象整体读写、嵌套结构、需要压缩 |

**选型建议：** 字段少且需要独立更新用Hash；字段多、嵌套结构、整体读写用String+JSON。

### List 底层与消息队列缺陷

List 底层在数据量小时用 ziplist/listpack，数据量大时转换为 quicklist（双向链表 + 每个节点是一个ziplist）。

**List 为什么不适合做消息队列：**

1. **不支持多消费者组**：一个消息被一个消费者POP后就删除了，无法实现广播或多个消费者组独立消费；
2. **没有消息确认机制（ACK）**：消费者POP消息后如果处理失败，消息就丢失了，无法重试；
3. **没有消息持久化保障**：虽然Redis有RDB/AOF，但List中的消息在宕机时可能丢失（取决于持久化策略）；
4. **不支持消息回溯**：消费过的消息无法重新消费；
5. **没有死信队列**：处理失败的消息没有专门的队列存放。

**业务缺陷：** 简单的异步任务可以用List，但对可靠性要求高的场景（订单、支付）必须用专业MQ（Kafka/RocketMQ）或Redis Stream。

**List 充当消息队列时消息丢了怎么办：** 用 `RPOPLPUSH` 命令，原子地将消息从待处理队列移到"处理中"队列，处理完成后再从处理中队列删除；如果消费者宕机，处理中队列的消息可以被其他消费者重新处理。这是手动模拟ACK机制。更可靠的方案是直接用 Redis Stream。

### BitMap、HyperLogLog、Geo

**BitMap（位图）：**

- 本质是String类型，通过位操作存储0/1；
- 适用场景：用户签到、在线状态、布隆过滤器、日活统计；
- 优势：极度省内存，1亿用户签到一天只需要约12.5MB；
- 限制：只能存0/1，不能存其他值；offset是整数，需要业务映射。

**HyperLogLog（HLL）：**

- 用于基数统计（不重复元素计数），如UV统计；
- 适用场景：页面访问独立用户数、搜索关键词去重统计；
- 优势：内存极小，每个key固定约12KB，就能统计2^64个元素；
- 误差限制：标准误差约0.81%，不适合需要精确计数的场景（如财务统计）；
- 注意：HLL只存计数，不存原始元素，无法获取具体元素列表。

**Geo（地理位置）：**

- 底层用zset存储，将经纬度编码成52位整数（Geohash）作为score；
- 适用场景：附近的人、附近的店、距离计算、地理位置范围查询；
- 命令：GEOADD添加、GEOPOS获取位置、GEODIST计算距离、GEORADIUS按半径查询；
- 限制：精度约0.6米，足够大多数业务场景；不支持三维坐标（海拔）。

### 单个元素块的最大存储大小

单个元素块的最大存储大小是 512 MB

### ziplist 和 listpack

都是连续内存的紧凑结构，用来优化少量数据，节约内存，查找时间复杂度 O (n)。

- ziplist 每个节点记录上一个元素的长度，修改数据可能发生连锁更新，一连串内存重分配，性能抖动；
- listpack 把字段改成记录自身长度，元素之间互不干扰，彻底解决连锁更新，Redis7.0 之后全面替换 ziplist。

redis 7.0 之后 ziplist 升级为 listpack

## 二、核心原理与线程模型

### redis 为什么这么快

Redis 快主要因为数据存内存；主线程单线程执行命令避免锁与上下文切换；IO 多路复用高效处理大量连接；搭配自研优化的数据结构、简单网络协议。

### Redis 为什么设计为单线程

Redis 核心操作是内存读写，CPU 不是主要瓶颈，单线程可以避免锁竞争与线程切换开销，天然保障命令、事务、Lua 脚本的原子性；结合 IO 多路复用，单线程就足以支撑高并发，实现简单。

### 6.0 为什么引入多线程

高并发、万兆网卡场景下，socket 读写和协议解析占用大量 CPU，成为网络瓶颈，多核资源浪费。6.0 新增 IO 多线程，仅将网络读写、协议解析交给线程池并行处理，命令执行仍保持主线程串行，不破坏原有语义，以此提升网络吞吐，该功能默认关闭。

## 三、持久化

### 持久化机制

RDB 定时快照备份，AOF 追加每条写操作

**RDB vs AOF 对比：**

| 维度 | RDB | AOF |
|------|-----|-----|
| 持久化方式 | 定时生成全量快照 | 追加每条写命令 |
| 数据安全性 | 两次快照之间的数据可能丢失 | 根据刷盘策略，最多丢1秒数据 |
| 文件大小 | 紧凑的二进制文件，体积小 | 文本格式，体积大，需要定期重写 |
| 恢复速度 | 快（直接加载快照） | 慢（需要逐条回放命令） |
| 性能影响 | fork子进程生成快照，fork瞬间阻塞主线程；大数据量fork耗时 | 每条命令追加，性能影响小；AOF重写时fork子进程 |
| 适用场景 | 备份、容灾、全量恢复 | 数据安全性要求高的业务 |

### 生成 RDB 文件时如何处理请求

bgsave 做 RDB，fork 瞬间短暂阻塞主线程；fork 完成后主进程正常处理客户端请求；依靠写时复制，子进程快照 fork 时刻的数据，后续新写入不会进入本次 RDB；`save`同步方式全程阻塞所有请求。

### 混合持久化

Redis 4.0+ 支持混合持久化（AOF重写时开启），结合RDB和AOF的优点：

- AOF重写时，前半部分用RDB格式写入全量快照（快速、紧凑）；
- 后半部分用AOF格式追加重写期间的增量命令；
- 重启恢复时，先加载RDB部分（快速恢复全量数据），再回放AOF增量命令（恢复最新数据）。

混合持久化兼顾了恢复速度和数据安全性，是推荐的持久化方式。开启配置：`aof-use-rdb-preamble yes`。

### 宕机恢复数据丢失可能性

不同持久化策略下宕机的数据丢失情况：

1. **仅RDB**：取决于快照频率。如果每5分钟一次快照，宕机最多丢失近5分钟的数据；
2. **仅AOF + everysec**：最多丢失1秒数据（默认刷盘策略）；如果是always策略，基本不丢数据但性能差；
3. **AOF + no**：由OS决定刷盘时机，宕机可能丢失较多数据；
4. **混合持久化**：RDB部分是全量快照，AOF部分是增量，最多丢失AOF未刷盘的少量数据（通常1秒内）；
5. **无持久化**：宕机后所有数据全部丢失。

即使开启了持久化，以下情况仍可能丢数据：
- AOF文件损坏（磁盘故障、写入中断），需要redis-check-aof修复；
- RDB文件生成过程中宕机，本次快照不完整，只能用上一次完整快照恢复；
- 主从切换时，主库已写入但未同步到从库的数据会丢失。

## 四、缓存

### 数据库与缓存一致性

缓存与数据库双写一致性是缓存系统的核心问题。

**常见方案对比：**

1. **旁路缓存（Cache Aside）：先更新数据库，再删缓存**
   - 最常用的方案。更新数据库成功后删除缓存，下次读请求缓存未命中时回源数据库并回填缓存；
   - 存在极小的不一致窗口：更新数据库后、删缓存前，如果有读请求，会读到旧缓存数据；但这个窗口极短（删缓存是毫秒级），业务通常可接受；
   - 极端不一致场景：读请求缓存未命中 → 查询数据库（拿到旧值） → 写请求更新数据库并删缓存 → 读请求把旧值回填缓存。这个场景需要读数据库比写数据库还慢才会发生，概率极低。

2. **先删缓存，再更新数据库**
   - 有脏数据风险：删缓存后、更新数据库前，如果有读请求，会把旧数据从数据库读回缓存，导致缓存中是旧数据，且后续不会自动更新（直到缓存过期或被再次删除）；
   - 不一致窗口更长，不推荐单独使用。

3. **延迟双删：删缓存 → 更新数据库 → 休眠一段时间 → 再删一次缓存**
   - 解决"先删缓存再更新数据库"方案中旧数据回填的问题；
   - 延迟时间设置依据：必须大于一次读请求的耗时（读数据库 + 写缓存），确保在读请求回填旧缓存之后再删一次；通常设置为几百毫秒到1秒；
   - 缺陷：休眠时间不好把控，太短可能读请求还没回填，太长增加不一致窗口；增加了接口响应时间。

**更新数据库+删除缓存中途服务crash怎么办：**

- 如果更新数据库成功但删缓存前crash：缓存中还是旧数据，会一直不一致直到缓存过期。兜底方案：用消息队列异步重试删缓存，或用binlog订阅（CDC）监听数据库变更，异步删除缓存；
- 如果删缓存成功但更新数据库前crash：缓存已删，数据库还是旧值，下次读请求回源拿到旧值并回填，最终一致，没有问题；
- 通用兜底：设置缓存过期时间（TTL），即使出现不一致，最多TTL时间后缓存过期自动恢复一致。

**要求强一致性时的方案：**

- 放弃缓存，直接读数据库；
- 读写加分布式锁，串行化访问同一数据（性能差）；
- 旁路缓存 + 版本号：缓存value中带版本号，读取时校验版本，更新时基于版本号做乐观锁。

### 缓存击穿

热点 key 在失效瞬间大量请求打到数据库

逻辑过期或永不过期避免物理失效（过期时间存在 value 里，后续异步更新），互斥锁控制只有一个线程加载数据

### 缓存穿透

查询根本不存在的数据导致每次请求都落库

布隆过滤器，缓存空值

### 缓存雪崩

大面积缓存同时失效，大量请求击穿到数据库

过期时间加随机值，避免集体同时过期

**大量 key 同一时间过期的线上问题：**

- 大量key同时过期瞬间，请求全部回源数据库，数据库压力骤增，可能引发慢查询、连接占满，甚至数据库宕机；
- 这是缓存雪崩的导火索之一。

**避免方案：**

1. 过期时间加随机值：在基础TTL上加上随机偏移（如 `TTL = base_ttl + random(0, 300s)`），打散过期时间；
2. 缓存预热：系统启动或流量高峰前，提前把热点数据加载到缓存；
3. 多级缓存：本地缓存 + Redis缓存，Redis失效时本地缓存还能兜底；
4. 熔断降级：数据库压力过大时，部分接口降级返回默认值或缓存旧值。

### 热点 key 问题的解决方案

本地缓存、主从读写分离、多副本 key（缓解集群模式下的读压力，但是加大写难度）、key 拆小、

### 缓存预热与冷启动

**缓存预热**：系统启动、流量高峰前或缓存集群重启后，提前把热点数据加载到缓存中，避免流量到来时大量请求直接打到数据库。

预热方式：

1. 手动触发：运维脚本或管理后台手动加载指定热点数据；
2. 定时任务：低峰期定时刷新热点key的缓存；
3. 启动自动加载：应用启动时读取热点配置，自动加载到缓存；
4. 访问触发：允许少量请求回源并回填缓存，逐步建立缓存（适合非极端场景）。

**冷启动问题**：缓存集群重启或新系统上线后，缓存中没有任何数据，所有请求都穿透到数据库，可能导致数据库被打垮。

解决方案：

1. 缓存预热（如上）；
2. 限流降级：冷启动期间限制数据库访问QPS，超过阈值的请求降级；
3. 互斥锁重建：缓存未命中时加锁，只允许一个请求回源数据库，其他请求等待或返回默认值；
4. 缓存永不过期 + 异步更新：热点key不设物理过期，用逻辑过期，后台异步更新，避免冷启动。

## 五、事务、批处理与脚本

### 原生批处理命令和 pipeline 的区别

服务端原生批命令，具备原子性，一次网络往返，但 key 数量有限制。Pipeline 是客户端通信优化，合并多条命令一起收发减少往返时延，Redis 内部仍然逐条执行，**没有原子性，其他客户端命令可以穿插进来**。要原子批量选 MSET/MGET；不需要原子、追求吞吐选 Pipeline。

### redis 事务和关系型数据库事务的区别

Redis 事务仅保证 EXEC 执行阶段命令串行不被其他请求插入，**不支持错误回滚，本质是命令排队执行**。

**pipeline 和事务 multi 的区别：**

| 维度 | pipeline | multi（事务） |
|------|----------|---------------|
| 原子性 | 无原子性，命令逐条执行，其他客户端命令可穿插 | EXEC阶段原子执行，命令之间不被其他客户端插入 |
| 网络优化 | 合并多条命令一次发送，减少网络往返 | 每条命令单独发送（MULTI后命令入队，EXEC一次性执行），网络往返多 |
| 错误处理 | 命令之间独立，一条失败不影响其他 | 入队时语法错误整体不执行；执行时某条错误，其他命令继续执行，不回滚 |
| 适用场景 | 批量读写、追求吞吐 | 需要一组命令原子执行的场景 |

### Lua 脚本

原子执行，减少网络开销，eval

**Lua 脚本原子性：** Redis执行Lua脚本时，整个脚本作为一个整体在主线程执行，执行期间不会处理其他客户端请求，保证原子性。

**Lua 脚本业务风险：**

1. **阻塞主线程**：Lua脚本执行期间Redis无法处理其他请求，如果脚本中有耗时操作（大循环、大量数据遍历、慢命令），会导致整个Redis实例阻塞；
2. **内存风险**：脚本中创建大量临时变量或返回大结果，可能导致内存暴涨；
3. **调试困难**：Lua脚本在Redis中执行，调试和日志不如应用层方便；
4. **版本兼容**：不同Redis版本支持的Lua库可能不同，脚本迁移时需要注意；
5. **集群限制**：Redis Cluster中，Lua脚本操作的所有key必须在同一个slot（用hash tag保证），否则报错；
6. **不允许随机写**：Redis为了主从复制一致性，Lua脚本中不允许使用随机函数（如math.random）后执行写操作，会报错。

最佳实践：Lua脚本尽量短小精悍，只做必须原子的简单逻辑；复杂逻辑放应用层。

### pipeline

批量打包命令，减少网络开销；无原子性

## 六、过期策略、内存淘汰与 Big Key

### 数据过期后的删除策略

1. **惰性删除（被动删除）** key 过期不会立刻删，**等下次访问该 key 的时候**，才检查过期时间，如果已过期就删除并返回不存在。 优点：不耗 CPU；缺点：如果 key 再也不被访问，会一直占内存。
2. **定期删除** Redis 会**每隔一段时间随机抽取一批设置了过期的 key**，检查并删除其中过期的 key，循环执行。 不是扫描全库，避免长时间阻塞主线程；只能减少过期 key 堆积，不能保证全部清理干净。

### 内存淘汰策略

当Redis内存使用达到`maxmemory`上限时，触发内存淘汰机制，按策略删除部分key释放内存。

**8种内存淘汰策略：**

1. **noeviction**：不淘汰任何key，写请求直接返回错误（默认策略）；
2. **allkeys-lru**：从所有key中淘汰最近最少使用的key（最常用）；
3. **allkeys-lfu**：从所有key中淘汰使用频率最低的key（Redis 4.0+）；
4. **allkeys-random**：从所有key中随机淘汰；
5. **volatile-lru**：从设置了过期时间的key中淘汰最近最少使用的；
6. **volatile-lfu**：从设置了过期时间的key中淘汰使用频率最低的；
7. **volatile-random**：从设置了过期时间的key中随机淘汰；
8. **volatile-ttl**：从设置了过期时间的key中淘汰最早过期的（TTL最小的）。

**选型建议：**

- 缓存场景推荐`allkeys-lru`或`allkeys-lfu`，所有key都参与淘汰；
- 如果有持久化数据和缓存数据混合，用`volatile-*`系列，只淘汰设了过期时间的key，保护持久化数据；
- LRU适合访问模式相对均匀的场景；LFU适合有明显热点分层的场景（高频访问的key更可能持续高频）。

**maxmemory 设置为 0 代表什么：**

- 32位系统：maxmemory=0表示不限制内存使用（但32位系统最大寻址4GB）；
- 64位系统：maxmemory=0表示不限制内存使用，Redis会一直使用内存直到操作系统OOM killer杀掉进程。

**业务不配置 maxmemory 的后果：** Redis无限制使用内存，最终可能耗尽服务器内存，导致操作系统OOM killer杀掉Redis进程（或其他进程），服务不可用。生产环境必须配置maxmemory，并设置合理的淘汰策略。

### big key

BigKey 是指单个 key 对应的的 value 过大

危害：

- 内存分配与释放压力大
- 查询、遍历耗时久
- 影响迁移速度
- 网络传输占满带宽

方案：

- 拆分 key
- 分批遍历、删除

**bigkey 怎么发现：**

- `redis-cli --bigkeys`：扫描整个keyspace，找出每种数据类型最大的key（抽样扫描，不一定找出所有bigkey）；
- `MEMORY USAGE key`：查看指定key的内存占用；
- 慢查询日志：bigkey的操作通常耗时较长，会出现在SLOWLOG中；
- 监控命令：通过`MONITOR`或代理层监控，找出返回值大的命令；
- 业务代码审计：在写入时检查value大小，超过阈值告警。

**bigkey 删除为什么阻塞 Redis：** Redis是单线程，删除大key时需要一次性释放大量内存（如大Hash有百万字段、大List有百万元素），内存释放操作耗时较长，期间主线程无法处理其他请求。Redis 4.0+ 支持**异步删除**（`UNLINK`命令），将大key的内存释放交给后台线程处理，不阻塞主线程。生产环境删除大key用`UNLINK`代替`DEL`。

## 七、分布式锁

### Redis 分布式锁基础实现

最基础的分布式锁实现：`SET key value NX EX seconds`

- `NX`：key不存在时才设置成功（保证互斥，只有一个客户端能加锁成功）；
- `EX seconds`：设置过期时间，防止客户端宕机后锁永远不释放（死锁）；
- 一条命令原子执行，保证加锁和设置过期时间的原子性。

**为什么不能用 setnx + expire 两条命令：**

`SETNX key value` 加锁成功后，如果执行 `EXPIRE key seconds` 之前客户端崩溃或进程被杀，锁就没有设置过期时间，会永远存在，导致死锁。两条命令不是原子的，中间可能出问题。必须用 `SET key value NX EX` 一条命令保证原子性。

### 锁续期与看门狗

**问题：** 锁过期时间到了但业务还没执行完，锁自动释放，其他客户端拿到锁，导致并发问题。

**看门狗（Watchdog）原理：** 加锁成功后，后台启动一个定时任务（看门狗），每隔一段时间（通常是锁过期时间的1/3，如锁30秒则每10秒检查一次）检查锁是否还被当前客户端持有，如果是则自动续期（重置过期时间）。业务执行完成后释放锁，看门狗也停止。

**Go客户端实现：** go-redis库本身不内置看门狗，需要自己实现或使用第三方库（如`bsm/redislock`支持自动续期）。Redisson（Java客户端）内置了看门狗机制，是最成熟的实现。

### 锁误删与 value 唯一标识

**问题场景：** A客户端加锁，业务执行中锁过期自动释放，B客户端拿到同一把锁；此时A客户端业务执行完，执行`DEL key`释放锁，把B客户端的锁给释放了，导致C客户端也能拿到锁，并发安全被破坏。

**解决方案：value 存唯一标识**

- 加锁时，value存一个全局唯一标识（如UUID + 线程ID，或雪花算法ID）；
- 释放锁时，先检查锁的value是否等于自己的唯一标识，只有是自己的锁才释放；
- 检查和删除必须原子执行，用Lua脚本实现：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

### redission 分布式锁原理

Redisson 用 Lua 脚本基于 Hash 实现可重入锁，记录客户端线程标识与重入计数；看门狗后台自动续期避免业务未完成锁过期；释放锁同样 Lua 原子校验归属、递减计数；抢锁失败订阅锁释放消息等待。

### red lock 红锁

Redlock 红锁，使用多套独立 Redis 主节点，必须半数以上节点加锁成功才算获取锁，解决单节点 / 主从切换锁丢失问题；但依赖系统时间，GC 停顿、时钟漂移会破坏锁安全，生产很少用。

### 分布式锁的主从切换导致锁失效问题

真要高可靠，建议直接上 ZooKeeper 或 etcd，它们基于一致性协议，天生能保证锁的安全性，就是性能低点。Redis 锁追求的是高性能，牺牲了一定安全性，得清楚这个权衡。

### 分布式锁不适用场景与替代方案

**不适合 Redis 分布式锁的场景：**

1. **强一致性要求极高**：金融交易、资金扣减等，Redis锁存在主从切换丢锁风险，不能保证绝对安全；
2. **长时间持锁**：业务执行时间远大于锁过期时间，续期机制复杂且不可靠；
3. **需要可重入、公平锁、读写锁等高级特性**：Redis实现复杂，不如专业锁组件；
4. **需要锁的可观测性**：Redis锁难以监控谁持有锁、等待队列等。

**替代方案：**

1. **数据库乐观锁**：用版本号字段，`UPDATE table SET ... WHERE id = ? AND version = ?`，适合并发不高、冲突少的场景；
2. **数据库悲观锁**：`SELECT ... FOR UPDATE`，适合并发低但要求强一致的场景；
3. **ZooKeeper / etcd**：基于一致性协议的分布式锁，强一致，性能比Redis低；
4. **Redlock**：多Redis节点的红锁算法，提升安全性但实现复杂、有争议。

## 十、性能与线上故障

### 性能瓶颈时如何处理

先用 `INFO stats`, `INFO memory`, `redis-cli --latency` 观察指标，看时 CPU、内存、网络、磁盘指标；同时配合 `SLOWLOG`, `INFO commandstats` 定位慢命令。

- CPU 没到顶但是 QPS 上不去，可能是大 key 或慢查询拖累；考虑将 keys 替换为 scan、拆分大 key
- 如果是整体读写压力大，做横向扩展，搭建集群（集群无法解决热点 key 问题）
- 如果存在热点 key，极端场景在应用层增加本地缓存，拦截最热流量
- 如果是持久化磁盘 IO 瓶颈，调整 RDB/AOF 策略，避免 fork 阻塞主线程

### Redis 单线程 CPU 100% 原因与排查

Redis是单线程模型，CPU 100%意味着主线程被占满，所有请求都会变慢或超时。

**常见原因：**

1. **慢命令/大key操作**：对大key执行HGETALL、SMEMBERS、LRANGE、KEYS等全量遍历命令，耗时久阻塞主线程；
2. **大量key同时过期**：定期删除时一次删除大量过期key，CPU占用高；
3. **Lua脚本耗时过长**：Lua脚本中有大循环或复杂计算，长时间占用主线程；
4. **AOF重写/RDB fork**：虽然fork是子进程执行，但fork瞬间主线程阻塞，大内存实例fork耗时长；
5. **持久化刷盘**：AOF always策略每次写都刷盘，磁盘IO慢时阻塞主线程；
6. **网络IO瓶颈**：高并发下网络读写占满CPU（6.0前网络IO也在主线程）；
7. **频繁的内存淘汰**：maxmemory设置过小，大量写触发频繁淘汰，CPU占用高。

**排查思路：**

1. `SLOWLOG GET 10`：查看慢查询日志，找出耗时最长的命令；
2. `INFO commandstats`：查看各类命令的调用次数和总耗时，定位高频慢命令；
3. `redis-cli --bigkeys`：扫描找出大key；
4. `INFO stats`：查看总命令数、keyspace命中/未命中、过期key数等指标；
5. `CLIENT LIST`：查看客户端连接，是否有异常连接（如MONITOR客户端）；
6. 检查是否有`KEYS *`、`FLUSHALL`等危险命令被执行。

**紧急处理：** 如果CPU 100%且无法快速定位，可先通过`CLIENT KILL`断开异常连接，或重启实例（有持久化保障数据不丢）。

## 十一、集群

### 主从复制的拓扑结构

1. **一主一从**：最简单，用于备份和小规模读写分离。
2. **一主多从**：生产常用，多个从节点直接连主节点，分担读压力，但主节点复制带宽压力随从节点数量上升。
3. **树状级联复制**：从节点下面继续挂载从节点，减轻顶层主节点同步压力；代价是复制延迟随层级变大。

### 主从复制流程

Redis主从复制由**从节点主动发起**。从节点执行 replicaof 命令，与主节点建立TCP长连接后，发送携带主节点runid和自身复制偏移量offset的PSYNC同步请求，开启数据同步。

主节点收到请求后做双重校验：核对runid是否匹配、offset对应数据是否保存在复制积压缓冲区。校验通过则执行**部分重同步**，仅补发offset之后的增量命令，无需传输RDB，快速完成同步。

若runid变更，或offset数据已被缓冲区覆盖，会触发**全量同步**。主节点fork子进程生成RDB快照发送给从节点，从节点清空本地数据并加载快照。同时主节点将同步期间的新增写命令存入积压缓冲区，待快照加载完成后补发增量命令，保障数据完整。

初始化同步完成后，进入常态化增量复制阶段。主节点执行写命令后，会异步转发给从节点回放，双方实时更新offset偏移量。主从复制默认异步执行，主节点无需等待从节点完成，直接响应客户端，性能高效。

复制链路全程依靠**心跳机制**维持稳定：默认从节点每秒向主节点发送心跳包，上报自身offset和同步状态。若主节点超时未接收心跳，判定从节点失联；若从节点未收到主节点响应，会主动重连重试同步，确保链路持续可用。

### 主从复制延迟的常见原因

- 网络延迟、带宽跑满
- 主节点侧问题
    - 大内存实例执行 fork 生成 RDB 时，fork 调用阻塞主节点主线程，复制流推送暂停，同时生成、传输、加载更大的 RDB 文件耗时增加，共同导致主从复制延迟升高。
    - 缓冲区太小，断线重连经常出发全量同步
    - 主节点 CPU 打满，忙着处理业务请求，没空推送复制流
- 从节点侧问题：磁盘 IO 慢或 CPU 压力高，跟不上主节点的更新速度
- 架构原因：链式联级复制时，复制是一层一层往下传递的

### 集群模式和哨兵模式的区别

哨兵模式底层仍是一主多从，只负责自动故障切换，**不能分片扩容，写能力无法扩展**；Redis Cluster 通过 16384 哈希槽做数据分片，多主分担读写压力，同时自带故障转移能力，可以横向扩容存储与写性能。

### 集群的实现原理

Redis Cluster 使用 16384 个哈希槽分片数据，CRC16 算法计算 key 所属槽；节点之间依靠 Gossip 协议同步集群元数据；每个主节点分配部分槽，搭配从节点，通过集群投票完成故障转移；多 key 操作需要 hash tag 保证同槽，不支持跨节点事务。

**槽位为什么是 16384（2^14），不是更大数字：**

1. **心跳包大小**：Redis节点间心跳包中，节点信息包含自己负责的槽位信息，用bitmap表示。16384个槽位的bitmap大小为 16384/8 = 2KB；如果用65536个槽位，bitmap就是8KB。节点间每秒发送心跳，槽位越多心跳包越大，网络开销越高；
2. **集群规模限制**：Redis Cluster官方建议最大节点数约1000个。16384个槽分给1000个节点，平均每个节点约16个槽，足够分配且粒度合理；如果槽位太多，小规模集群时每个节点槽位过多，迁移和管理开销大；
3. **作者设计考量**：Redis作者antirez认为16384已经足够，更大的数字没有实际收益，反而增加心跳包体积和内存占用。

### 集群模式下某个主节点宕机会怎么样

1. **该主配置了从节点（生产标准部署）** 集群节点间检测故障，投票完成故障转移，它的从节点晋升为新主，接管原有hash槽；集群继续正常对外服务。 ⚠️复制是异步，主还未同步到从的少量新写入数据有丢失风险。
2. **该主没有配置从节点** 它负责的hash槽无节点接管，标记为失败；**整个集群进入FAIL状态，全部槽拒绝读写**，该分片数据丢失。只能重启原节点恢复，或手动剔除节点放弃数据。

### 哨兵机制

哨兵集群监控 Redis 主从；单哨兵超时无响应为主观下线；达到指定数量哨兵一致判定故障，进入客观下线；自动选从升主，其他从切换复制新主，完成故障转移；哨兵不提供分片功能。

### 集群模式下的脑裂

网络分区后被隔离的旧主不会自己退位，与新主同时接收写入

`cluster‑require‑full‑coverage`可以拒绝不完整槽的写请求做缓解，但不能完全消除。

1. **确认真实集群状态** 逐个连接**所有集群节点**，执行 `cluster nodes`。 统计输出结果：大多数节点共识的主、槽分配，就是集群真实状态；少数被隔离节点的视图直接忽略。

   识别旧主：节点自身认为自己持有哈希槽，但其他多数节点标记它为fail，就是分裂的旧主。

2. **隔离旧主** 防火墙阻断业务访问该旧主，仅保留运维访问，阻止继续写入脏数据，不要直接重启。

3. **业务全部切到真实集群** 业务使用集群客户端，禁止硬编码节点IP；确认不再访问隔离旧主。

4. **处理旧主数据**

   - 允许丢失隔离期间写入的数据：执行`cluster reset hard`清空旧主数据，再让它重新加入集群同步。

   - 不能丢数据：先备份旧主RDB，业务脚本人工比对合并脏数据，完成后再reset加入集群。

1. **事后加固** 开启`cluster‑require‑full‑coverage yes`；节点跨机架部署；调优`cluster‑node‑timeout`。

### 哨兵模式下的脑裂

普通主从无脑裂：网络分区时旧主与哨兵、从节点断连但进程存活。哨兵判定旧主下线，选举出新主；被隔离的旧主不知道自己已被罢免，仍接受写请求，集群出现两个可写主，引发数据不一致。

配置`min‑replicas‑to‑write N`，主节点必须有至少 N 个正常同步的从节点才允许写。隔离后旧主连不上从节点，主动拒绝写入。

1. **确认集群真实状态** 逐个连接**所有哨兵节点**，执行 `sentinel master mymaster`。 统计返回结果：大部分哨兵报出的主IP就是**合法新主**；少数哨兵返回旧主IP，该结果直接忽略。仍可写入、但不是合法新主的那台Redis，就是脑裂旧主。

2. **隔离脑裂旧主** 防火墙/安全组阻断业务机器访问旧主Redis，只保留运维登录权限，**不要直接重启旧主**，停止继续写入脏数据。

3. **业务切换** 全部业务统一走哨兵获取主节点地址，移除所有硬编码Redis IP，确认业务已经全部访问合法新主。

4. **处理旧主数据**

   - 可接受脑裂期间数据丢失：旧主执行 `replicaof 新主IP 端口`，自动全量同步成为从节点。

   - 不能丢数据：先备份旧主RDB，业务脚本人工对比合并两份数据，合并完成后再把旧主设为从。

1. **事后加固** 配置`min‑replicas‑to‑write`；哨兵跨机架部署，核对quorum参数。
