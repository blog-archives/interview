
Redis Cluster 是在主从复制之上构建的分布式分片方案，二者并不冲突，可以搭配使用。普通主从主要做读扩容和备份，写依旧受限于单个主节点；集群用来解决单实例内存和写的瓶颈，实现水平扩容。

集群固定有16384个哈希槽，key 通过 CRC16(key) % 16384 算出对应槽位，每个哈希槽归属于某一个主节点，从节点只做副本不持有槽。数据分散在各个主节点，理论负载均匀，但 hash‑tag 或者 key 哈希分布不均会造成数据倾斜。选择16384是2的14次方，槽位图体积小，可以降低Gossip协议的广播带宽开销。

集群无全局leader节点，槽初始化分配、reshard槽迁移依靠外部 redis‑cli 工具，节点不会自动做负载均衡；但故障转移是集群内部自治，主宕机后其余主节点通过投票将从节点升主接管槽。节点之间依靠Gossip协议互相传播节点状态、槽映射等元数据。客户端访问节点，如果key所属槽不在当前节点，不会代理转发，返回MOVED重定向让客户端访问正确节点，槽迁移阶段还会出现ASK临时重定向。一旦槽没有全部可用或者多数主节点失联，集群进入fail状态，拒绝读写，底层依旧沿用普通主从复制整套机制。

## Gossip 协议

Gossip 是一种**去中心化的信息扩散协议**，俗称八卦协议，不需要中心节点。

**做什么：** Redis Cluster 依靠它在节点之间同步集群元数据：节点存活状态、槽位归属、主从对应关系，让所有节点最终拥有一致的集群视图。

**怎么做：** 每个节点随机挑选部分其他节点，周期性互相交换自己已知的集群信息；收到新信息就更新本地，再继续传播给别的节点。信息像八卦一样逐步扩散到全部节点，最终达到集群所有节点状态收敛。

**关键特点：**

1. 无中心，部分网络消息丢失也不影响最终同步，具备容错能力。
2. 是**最终一致性**，短时间不同节点看到的集群状态可能不完全一样。
3. 只负责传播元数据，**不执行槽迁移、不执行故障转移投票**，投票是主节点另外的逻辑。

**一句话速记：** Gossip 就是集群节点互相闲聊同步元数据，保证大家最终拿到相同的集群视图，只管传播信息，不做决策执行。

## reshard 槽迁移

reshard 由外部 `redis‑cli --cluster reshard` 工具驱动，**集群节点本身不会自动触发**，工具只是下发指令，源、目标主节点负责实际搬数据。

整体流程：

1. redis‑cli 接收参数：要迁移多少个槽、源主节点、目标主节点。
2. 工具先修改集群元数据，标记这批槽**正在迁移状态**。此时槽一部分数据还在源节点，新归属标记为目标节点。
3. 源节点**逐个把槽内的 key 拷贝发送给目标节点**；key 拷贝完成后，源节点删除本地的这些 key。

> 注意：迁移的是真实 key 数据，不只是改映射表。

4. 迁移过程中客户端访问正在迁移的槽：

- key**已经迁移到目标节点**：访问目标节点。
- key**还留在源节点**：源节点返回 `ASK` 重定向，客户端临时去源节点取数据。

> ASK 是迁移过程临时重定向，和永久变更归属的 MOVED 不一样。

5. 槽内所有 key 全部迁移完毕，工具更新集群元数据：该槽**正式永久归属目标主节点**。后续访问就返回 MOVED。Gossip 把新的槽映射同步给集群全部节点。

关键点：

- 迁移是渐进式，逐个 key 搬运，不会阻塞 Redis 服务。
- 迁移期间集群依然对外可用，不会停写。
- 源节点不会立刻删除数据，要等 key 成功传到目标之后才删，避免丢数据。
- 从节点**不参与 reshard**，只跟随主节点复制同步数据。

## Redis‑Cluster 故障投票流程

> 前提：只有**主节点参与投票**，从节点没有投票权。底层是简单的**多数派投票机制**，不是Raft，没有日志复制，只做故障判定与升主。


1. **故障检测（Gossip）** 节点通过Gossip互相通信，如果一个主节点A长时间无响应，节点会先把A标记为 `PFAIL`（主观下线），只是**自己认为它挂了**，还不是集群公认。
2. **升级为客观下线 FAIL** 当**超过半数的主节点**，都收到A为PFAIL的消息，就把A标记为 `FAIL`（客观下线）。
    
    > 只有达到多数派，才公认这个主真正宕机，才允许做故障转移。
    
3. **发起投票，从节点竞选新主** 被标记FAIL的旧主的从节点，向集群内所有主节点发送投票请求，希望晋升成为新主。 每个主节点**最多投一票**，可以投给该从，也可以不投。
4. **竞选成功条件** 该从节点拿到 **半数以上主节点的选票** → 晋升为新主节点，**接管旧主全部哈希槽**。 晋升之后，Gossip把新主‑槽的映射同步给全部集群节点。旧主如果后续恢复，会降级变成新主的从节点。
5. **竞选失败** 拿不到多数选票，则无法升主；对应的哈希槽无人接管，整个集群进入 `fail` 状态，拒绝读写。

Q：投票是Raft算法吗？ A：不是。只是简单多数派投票，没有Raft的日志、任期这些复杂机制，只用于故障转移选主。

Q：从节点拥有投票权吗？ A：没有，只有集群中的主节点才有投票权。

Q：PFAIL 和 FAIL 的区别？ A：PFAIL：单个节点主观怀疑对方挂了；FAIL：半数以上主达成共识，客观确认宕机，允许故障转移。

Q：为什么要半数以上主节点确认？ A：防止网络分区脑裂，避免误判，防止错误的从节点升主。

Q：旧主节点恢复上线之后会发生什么？ A：发现槽已经归新主，旧主自动降级，成为新主的从节点。

Q：如果一个主有多个从节点，哪个从优先升主？ A：优先选**复制偏移量最大**的从（数据最接近旧主）；多个从偏移量相同，则随机。

Q：集群半数主节点本身不可达，会怎么样？ A：无法凑齐多数派选票，不能完成故障转移，集群fail不可读写。

Q：Gossip在投票里承担什么角色？ A：只传播PFAIL/FAIL状态消息；**投票、计票、升主逻辑是独立逻辑，Gossip不做决策**。

## 延伸问题

Q：Redis‑Cluster 的从节点会持有哈希槽吗？ A：不会，哈希槽只属于主节点；从节点仅做复制备份，不负责读写槽。

Q：Redis Cluster 可以自动做哈希槽负载均衡吗？ A：原生不可以，新增/删减主节点，必须手动通过 redis‑cli reshard 迁移槽，不会自动流转。

Q：reshard 槽迁移，是只修改元数据吗？ A：不是，既要更新槽归属元数据，还要把槽下真实 key‑value 数据从源节点拷贝到目标节点。

Q：MOVED 和 ASK 重定向核心区别？ A：MOVED：槽已经永久归属其他节点；ASK：槽正在迁移，key还在源节点，属于临时重定向。

Q：集群故障转移（从升主）需要外部 redis‑cli 工具参与吗？ A：不需要，集群内部主节点通过投票完成故障转移，属于集群自治。

Q：集群什么情况下会进入 fail 状态，拒绝读写？ A：16384个槽没有全部分配可用；或者半数以上主节点失联无法完成故障投票。

Q：hash‑tag 的作用与风险？ A：只对大括号内字符串计算槽，强制多个key落到同一个槽；风险是会造成数据、流量倾斜。

Q：为什么集群选择16384个哈希槽而不是65536？ A：16384用2048字节bitmap即可传递全部槽信息，降低Gossip协议广播带宽；65536带宽开销会成倍变大。

Q：集群模式下，底层主从复制的 replication‑buffer、repl‑backlog‑buffer 还生效吗？ A：完全生效，每个主从复制组依旧沿用整套主从复制逻辑。

Q：能不能向集群的从节点发起读请求？ A：默认会被重定向到主节点；客户端配置只读模式，可以访问从节点，但从节点的数据存在复制延迟。

Q：删除集群里一个主节点，槽会自动转移走吗？ A：不会，必须先把该主上所有槽 reshard 迁移完毕，才可以移出节点。

Q：Gossip 协议是用来做槽迁移、故障转移执行的吗？ A：不是，Gossip 只负责同步元数据（槽映射、节点状态）；槽迁移靠外部工具，故障转移靠主节点投票。

Q：Redis Cluster 能保证强一致性吗？ A：不能，依旧是异步复制，主写完立刻返回客户端，主宕机存在丢失少量已写入数据的风险。

Q：Redis‑Cluster（哈希槽集群）会不会脑裂？ A：**会，同样会发生脑裂**，和哨兵主从一样存在网络分区脑裂风险。

Q：Cluster脑裂典型场景是什么？ A：网络分裂，一部分客户端还能访问到老主；老主和大部分节点网络不通，集群这边选举出新主。于是同时存在新旧两个主节点，客户端有可能继续向旧主写入，产生脏数据。

Q：Cluster有没有类似min‑replicas‑to‑write的防护参数？ A：有，`min‑replicas‑max‑to‑write`，集群每个主节点的配置。主节点在线健康从节点达不到该数量，就拒绝写请求，限制往旧主写入。只是防护，不能彻底杜绝脑裂。

Q：Cluster故障判定和哨兵有什么不一样？ A：Cluster节点之间互相PING‑PONG，**数据节点自己互相投票，不需要第三方哨兵**。半数以上槽所在主节点认为某节点失联，标记FAIL，自动故障转移。

Q：Cluster脑裂和哨兵脑裂根源一样吗？ A：根源一样，都是网络分区；区别：哨兵靠第三方哨兵节点判定故障，Cluster由数据节点之间完成投票。

Q：旧主网络恢复之后会是什么状态？ A：旧主发现集群已经选出新主，自己会降级变成新主的从节点，旧主上独有的未同步写数据直接丢失。

Q：那Cluster有没有办法完全解决脑裂？ A：没有Redis层面完全根治方案。只能靠参数减少脏写；业务层面增加超时、重试、数据校验兜底。

口述速记： Redis Cluster也会脑裂，网络分区场景下可能新旧主同时存活。可以配置`min‑replicas‑max‑to‑write`，主节点从副本不够就拒绝写，降低脏写风险。Cluster不需要哨兵，由数据节点互相PING‑PONG完成故障投票；旧主网络恢复后自动降级为从，旧主独有的写入会丢失。该参数只是防护手段，不能彻底消除脑裂。

Q：Cluster的投票需要多少节点同意？ A：集群内**超过半数的主节点**达成共识，节点才会被标记FAIL，触发故障转移。

Q：哨兵和Cluster都会脑裂，那脑裂本质是什么？ A：网络断开，一个集群分裂成两个隔离小集群，两边都认为自己是合法集群，各自接受写入。
