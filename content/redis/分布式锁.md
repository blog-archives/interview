
单机分布式锁用`SET key value NX EX`加锁，value存唯一标识；释放锁使用Lua脚本校验value后删除，避免误删别人锁。业务执行时间超过锁过期时间，需要看门狗自动续期。主从架构存在锁还未同步从节点主就宕机，锁丢失风险，可以用Redlock解决，但部署复杂，实际用的不多。

Q：Redis分布式锁最基础实现命令？ A：`SET key value NX EX 过期时间`，NX保证原子加锁，EX设置锁自动过期。

Q：NX、EX各自含义？ A：NX：key不存在才设置，实现互斥；EX：设置key过期时间，防止死锁。

Q：value为什么不能写死固定值？ A：value存唯一标识（UUID/线程id），释放锁时校验，防止释放别人持有的锁。

Q：释放锁可以直接del吗？ A：不可以，会误删别人的锁；要Lua脚本：判断value匹配才删除，保证判断+删除原子性。

Q：简单说释放锁Lua脚本逻辑？ A：如果key存在并且value等于当前标识，就删除key返回1；否则返回0。

Q：锁过期了业务还没执行完怎么办？ A：会出现锁失效，并发安全被破坏；可以开启锁续期（看门狗），业务没执行完自动延长过期时间。

Q：看门狗一般什么组件自带？ A：Redisson客户端封装好了看门狗续期逻辑。

Q：Redis单机分布式锁有什么问题？ A：单机宕机锁直接丢失。

Q：哨兵环境下，主刚拿到锁还没同步到从就宕机会发生什么？ A：从晋升新主，锁丢失，多个客户端同时拿到锁，锁失效。

Q：怎么解决主从同步丢锁的问题？ A：Redlock红锁，向多个独立Redis实例加锁，过半实例加锁成功才算拿到锁；生产实际很少使用。

Q：Redlock缺点？ A：部署重，运维复杂，业界对安全性还有争议。

Q：可以用setnx + expire两条分开命令加锁吗？ A：不行，两条命令非原子，中间进程宕机会造成死锁。

Q：分布式锁一定要上Redlock吗？ A：大部分业务容忍极小概率锁失效，直接主从+Redisson即可；极高安全场景考虑其他方案如Zookeeper。
