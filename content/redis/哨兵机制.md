
哨兵是独立于 Redis 主从数据节点的第三方哨兵节点，本身不存储业务数据，负责监控主从实例存活。 单个哨兵探测主节点连不上只是主观下线，需要多个哨兵达成 quorum 共识，标记客观下线之后，才执行故障转移。 哨兵集群内部还要选出一个哨兵 leader，由 leader 执行切换。挑选新主的时候，会先看从节点优先级，再对比复制偏移量，优先选择数据最新的从晋升为主。其余从节点会重置，开始复制新主。

脑裂防护可以配置主节点参数`min‑replicas‑to‑write`：主节点在线可用从节点不足配置数量，就拒绝写请求。但它不会触发主从切换，只是拒绝写入，减少脑裂带来脏写问题。 哨兵集群建议部署奇数个，防止哨兵自己出现网络分裂。

Q：主观下线和客观下线区别？ A：主观下线是单个哨兵认为节点挂了；客观下线是哨兵集群多数达成共识，才认定故障。

Q：故障转移是谁来执行？ A：哨兵集群内部选举出哨兵 leader，只有 leader 执行切换操作。

Q：选主时复制偏移量作用？ A：偏移量代表从节点同步到的数据位置，越大代表数据越新。

Q：slave‑priority 为 0 代表什么？ A：该从节点永远不会被哨兵提升为主节点。

Q：min‑replicas‑to‑write 是哨兵配置吗？ A：不是，是 Redis 主实例配置，仅控制写权限，不做故障切换。

Q：哨兵数量为什么推荐奇数？ A：为了 quorum 投票，避免哨兵集群网络分区无法达成多数派。

Q：哨兵解决脑裂吗？ A：不能彻底杜绝脑裂；配合`min‑replicas‑to‑write`减少脏写风险。

Q：哨兵和 Redis Cluster 集群的区别？ A：哨兵只做主从高可用，**不做数据分片**；Cluster 才负责数据分片 + 内置主从高可用。

首先多个哨兵达成共识，主节点客观下线；哨兵之间投票选出一个 Leader 哨兵；Leader 按照优先级、复制偏移量选出最合适从节点晋升主；命令其余从节点跟随新主；旧主恢复后自动降级为从。
