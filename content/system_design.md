- 防止参数篡改 or 重放攻击

    1. 增加时间戳来过滤超时的接口，不需要额外的存储、实现简单，但是仍然很容易修改和攻击
    2. 预先请求接口获取一次性令牌，需要额外存储令牌的有效性，延长了整个业务的调用链路

- 一致性 hash 算法

    普通的 hash 算法通过 `hash(key) % N` 取模的方式来计算数据应该落在哪个节点上，当遇到节点扩容或者缩容时，会导致大部分数据需要重新迁移，影响性能。

    一致性 hash 算法会对节点与 key 分别计算哈希值，映射到同一个哈希圆环（0~2^32‑1）上。key 沿着圆环顺时针查找，遇到的第一个节点即为负责该数据的节点。因此节点的扩缩容只会影响一小部分的数据。

    但是这样会引入数据倾斜的问题，节点的不均匀分布会导致每个节点承担的数据量不同。可以加入虚拟节点的概念，每个物理节点拆分出若干个逻辑节点，通过额外的映射建立起关联，所有物理节点虚拟出来的逻辑节点共同参与哈希映射，理论上逻辑节点越多，数据分配的就更加均匀。

    另外一致性 hash 算法只解决数据的落点（路由）问题，如果数据需要持久化，在扩缩容切换路由之前应该由额外的中控服务来负责数据的迁移。

- 设计一个灰度发布系统

    优先独立部署新旧两套服务集群，实现物理隔离；请求进入后基于用户 ID 生成稳定流量标签；优先白名单分流，百分比灰度采用哈希取模选定固定区间用户访问新版；从小流量开始逐步放量，对比新旧版本指标观测运行情况；出现严重异常立刻切回 0% 流量完成回滚，无需停服，保留新版现场排查；全量后延后下线旧集群兜底。

- 设计一个秒杀功能

    限流、流量漏斗分层过滤无效请求、热点缓存 & 热点隔离、人机验证（验证码）、消息队列异步削峰解耦、Redis‑Lua 原子预扣库存、防超卖、防重复下单、接口幂等校验、超时未支付回补库存、定时库存对账

    1. 用户发起秒杀请求
    2. 网关限流 → Redis 校验库存、校验用户是否已经下单
    3. Lua 脚本扣减库存成功
    4. 投递下单消息进入 MQ
    5. 接口立刻返回「排队中 + requestId」
    6. 前端开启轮询查询订单状态
    7. MQ 消费者异步生成订单
    8. 用户轮询查到成功，跳转支付；超时未支付关闭订单、回补库存

- 订单超时取消

    延迟消息依靠持久化、ACK 保障可靠性；消费者通过幂等 + 订单状态校验防止误取消与重复消费；配置失败重试与死信队列；最后定时轮询兜底防消息丢失。

- 完整的下单流程

    网关层做好鉴权限流与防重复提交；下单前后端校验商品、库存、限购与价格，不信任前端价格；创建订单时通过数据库事务保证订单、库存操作原子性，依靠订单状态机 + 乐观锁防并发问题；下单成功发送延迟消息处理超时未支付自动取消，并且定时轮询兜底；支付以第三方异步回调为准，做好回调幂等，处理支付与超时取消并发冲突；支付成功后通过消息队列异步触发发货、发消息等下游业务；微服务场景使用可靠消息实现跨服务数据最终一致；最后定时对账，保障库存、订单、支付三方数据一致。
