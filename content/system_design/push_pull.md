## Push 模式

Push 是指消费者订阅队列后，由消息队列主动把新消息交给消费者。

### 优点

- **实时性好**：消息到达后可以立即交付。
- **空请求少**：消费者不需要反复询问是否有新消息。

### 缺点

- **容易给消费者造成压力**：如果消息到达速度超过消费速度，又没有合理的限流和背压，消费者可能被大量消息压垮。
- **流量控制更复杂**：需要通过 `prefetch`、未确认消息上限等机制限制交付速度。

Push 并不代表消息队列无法削峰。只要限制推送中的消息数量，超出消费者处理能力的消息仍然可以留在队列中等待消费。

## Pull 模式

Pull 是指消费者主动向消息队列请求消息，并决定每次拉取的数量和频率。

### 优点

- **消费节奏容易控制**：消费者可以根据自身处理能力决定拉取速度和批量大小。
- **适合批量处理**：一次拉取多条消息，可以提高整体吞吐量。

### 缺点

- **可能产生空请求**：短轮询时，即使没有消息，消费者也会不断发送请求。
- **实时性可能受影响**：轮询间隔越长，消息等待时间通常越长。
- **参数需要调节**：批量过小会增加请求开销，批量过大也可能压垮消费者。

## 长轮询

长轮询是对 Pull 的常见优化。消费者发起请求后，如果暂时没有消息，消息队列不会立即返回，而是等到有消息或达到超时时间后再返回。

这样既能减少空请求，又能让消息到达后立即返回，因此实时性可以接近 Push，同时仍由消费者控制拉取节奏。

## 简单对比

| 模式 | 谁控制消息交付 | 主要优点 | 主要缺点 |
| --- | --- | --- | --- |
| Push | 消息队列 | 实时性好，空请求少 | 需要做好背压和限流 |
| Pull | 消费者 | 消费节奏和批量容易控制 | 可能有空请求和轮询延迟 |
