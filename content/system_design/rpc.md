## 最简单模型

如果让我设计一个 **RPC 框架**，我会先从一个最简单的远程调用模型开始，然后再根据它存在的问题一步一步完善。

> **首先考虑一个最简单的远程调用。**

假设 Service A 需要调用 Service B，最简单的方式就是 Service B 暴露一个 HTTP 接口，Service A 把方法和参数通过 JSON 发送过去，Service B 执行完成以后再把结果返回。

这样实际上已经完成了一次最基础的远程调用。

但是这种方式距离一个真正好用、高性能的 RPC 框架还有一些差距，所以接下来需要逐步优化。

## 调用方式

> **首先要解决的是调用体验的问题。**

如果每次远程调用，业务代码都需要自己构造请求、序列化参数、发送网络请求再解析返回值，那么 RPC 的底层细节就会侵入业务代码。

所以 RPC 框架通常会提供一层 **Proxy / Stub**。

业务方看起来只是调用了一个普通的方法，而 Proxy 会在底层把这次方法调用转换成 RPC 请求，并完成后续的网络通信。

所以这一层解决的问题就是：

**屏蔽远程调用细节，让 RPC 调用尽可能像本地方法调用。**

## 序列化

> **接下来要考虑参数怎么通过网络传输。**

方法参数和返回值本身都是内存中的对象，而网络最终只能传输字节，所以需要进行序列化和反序列化。

最简单可以使用 JSON，但是 JSON 包含大量字段名，数据比较冗余，而且文本解析性能也相对较低。

RPC 往往是服务之间大量、高频的调用，所以一般会选择更加紧凑、高效的 **二进制序列化方案**，比如 Protobuf。

这一部分没有必要自己重新设计一套序列化算法，直接选择成熟方案即可。

## 网络传输

> **序列化解决以后，接下来就是怎么高效地把数据传过去。**

如果每次 RPC 调用都重新建立连接，会产生比较大的连接建立和关闭开销。

所以 RPC 一般会基于 **TCP 长连接** 来进行通信，在同一条连接上持续发送多个请求。

底层网络通信也没有必要从 Socket 开始自己实现，可以基于成熟的网络框架，例如 Java 里面常见的 Netty，来处理连接管理、数据收发以及异步 IO。

## RPC 协议

> **但是使用 TCP 以后，又会产生一个新的问题。**

TCP 本身只是一个字节流，它并不知道一条 RPC 消息从哪里开始、在哪里结束，也不知道收到的数据是什么类型、用了什么序列化方式。

所以我们需要在 TCP 之上定义一套自己的 **RPC 通信协议**。

协议一般会包含一些基础信息，比如：

- 协议版本；
- 消息类型；
- 序列化方式；
- Request ID；
- 消息体长度；
- 真正的消息内容。

这样服务端收到一段 TCP 数据以后，就知道应该按照什么规则解析它。

其中消息长度可以帮助我们确定消息边界，而 Request ID 则可以帮助我们关联一次请求和对应的响应。

## 并发请求

> **有了长连接以后，还要考虑同一条连接上的并发请求。**

客户端可能连续发送多个 RPC 请求，而服务端执行时间不同，Response 不一定会按照 Request 的发送顺序返回。

所以每一个请求都需要一个唯一的 **Request ID**。

客户端发送请求以后，会暂时保存 Request ID 和当前请求之间的关系；等 Response 返回时，再根据 Request ID 找到对应的请求，并把结果返回给调用方。

这样一条 TCP 长连接上就可以同时处理多个 RPC 请求。

## 服务端执行

服务端收到完整的 RPC 请求以后，会根据请求中的 **ServiceName 和 MethodName** 找到对应的服务实现和方法，执行完成以后生成 RpcResponse，再通过相同的序列化、协议编码和网络传输流程返回客户端。

这样一次完整的 RPC 调用链路就完成了：

**本地方法调用 → Proxy → 序列化 → RPC 协议编码 → TCP 传输 → 服务端执行 → 返回 Response。**

## 工业级扩展

如果继续把它做成一个完整的工业级 RPC 框架，还可以进一步考虑：

服务发现、负载均衡、超时重试、路由、熔断、限流、监控和链路追踪等能力。

但我认为这些更偏向 **服务治理能力**。

如果面试题只是问“如何设计一个 RPC 框架”，我会优先把 RPC 最核心的几个问题讲清楚：

**调用代理、序列化、网络传输、通信协议以及请求响应关联。**

## 总结

所以整体来说，我的设计思路就是：

**先通过一个最简单的 HTTP + JSON 模型实现远程调用；为了屏蔽网络调用细节，引入 Proxy / Stub，让业务方像调用本地方法一样使用 RPC；因为网络只能传输字节，同时 JSON 性能和数据体积不够理想，所以引入 Protobuf 等二进制序列化方案；为了减少频繁建立连接的开销，底层改成 TCP 长连接；而 TCP 只是字节流，因此需要在它之上定义 RPC 协议，解决消息边界、消息类型以及请求响应关联等问题；最后服务端根据请求中的服务名和方法名找到真正的方法执行，并把结果返回客户端。**

这样，一个 RPC 框架最核心的调用链路就完整了。
